## 一、Executive Summary

P0-7.1 建立了 FOX 第一条跨 EXE/DLL 的动态插件调用证据链：

```
LoadLibraryA("NTCDLLG")
    ↓ ModuleIdentity = NTCDLLG
    ↓ GetProcAddress(hModule, "Dgraph_f20")
    ↓ FunctionPointerIdentity = NTCDLLG!Dgraph_f20
    ↓ (function pointer stored in global struct)
```

## 三、Root Cause 分析

### 问题 1：CallGraph 不包含 LoadLibraryA/GetProcAddress

**现象**: CallGraph 中只有 81 个 external call 有 resolved_symbol，不包含 LoadLibraryA 和 GetProcAddress。

**根因**: x86 中调用导入函数使用 `call [IAT_addr]`（FF15 指令），CallGraph 的 external call 解析主要针对 x64 RIP-relative IAT，未完整覆盖 x86 绝对地址 IAT。

**修复**: 新增 `build_iat_map_from_imports()`，直接从 PE 导入表构建 `IAT_VA → "dll!func"` 映射。注意 `ImportFunction.iat_address` 是 RVA，需加 `image_base` 得到 VA。

### 问题 2：SSA 中 call 目标操作数格式

**现象**: `call [0x45609C]` 在 SSA 中目标操作数为 `Memory { description: "[+0x45609c]" }`。

**修复**: process_call 中同时检查：
1. `external_call_names`（按 call instruction address，来自 CallGraph）
2. `iat_map`（按 call target address，来自 PE 导入表）
   - `Constant(addr)` → 直接查
   - `Memory { description }` → 从 `[+0x...]` 提取十六进制地址

### 问题 3：PUSH 参数与 CALL 之间有大量其他指令

**现象**: `collect_preceding_pushes()` 遇到非 Push 指令就 break，但实际代码中 PUSH 和 CALL 之间可能有 30+ 条 Mov 指令。

**示例** (0x42f3b0 函数):
```
0x42f3b5: push 0x45B784        ; LoadLibraryA 参数
... (30条 Mov 指令)
0x42f46d: call [0x45609C]      ; LoadLibraryA
```

**修复**: 修改 `collect_preceding_pushes()`，跳过非 Push 指令继续向前搜索，限制最大扫描距离 64 条指令。

### 问题 4：GetProcAddress 通过寄存器间接调用

**现象**: GetProcAddress 不是直接 `call [IAT]`，而是：
```
mov esi, [0x4560B4]    ; esi = GetProcAddress (从 IAT 加载)
push lpProcName
push hModule
call esi               ; 通过寄存器调用
```

**修复**: 
1. 扩展 `TrackedValue` 添加 `ExternalFunction(String)` 变体
2. `process_mov` 中追踪 `mov reg, [IAT_addr]` → 如果 IAT 地址匹配，标记为 ExternalFunction
3. `process_call` 中如果目标寄存器持有 ExternalFunction("GetProcAddress")，按 GetProcAddress 处理

### 问题 5：GetProcAddress 参数顺序

**现象**: 初始实现中参数顺序反了。

**修复**: x86 stdcall 参数从右到左 PUSH：
```
push lpProcName   ; arg2 (先 PUSH，离 call 更远)
push hModule      ; arg1 (后 PUSH，离 call 更近)
call GetProcAddress
```
从 call 往前扫描：`pushes[0] = arg1 (hModule)`, `pushes[1] = arg2 (lpProcName)`。

### 问题 6：跨基本块追踪丢失

**现象**: LoadLibraryA 在 block0，GetProcAddress 在 jnz 后的新块，`reg_values` 每块 clear 导致 ModuleHandle 丢失。

**修复**: 块间保留 `ModuleHandle` / `FunctionPointer` / `ExternalFunction`（语义值不随块变化），只清除 `ConstantAddress`（块内临时值）。

### 问题 7：GetProcAddress 返回值版本追踪

**现象**: `find_next_register_version()` 只在当前块内搜索，call 后如果没有立即使用 eax 就返回 None。

**修复**: 扩展为搜索直接后继块。

## 四、Architecture

### DynamicPluginResolver

```rust
pub struct DynamicPluginResolver<'a> {
    external_call_names: &HashMap<u64, String>,  // CallGraph resolved symbols
    iat_map: &HashMap<u64, String>,              // PE imports IAT → func
    string_table: &HashMap<u64, String>,         // binary string table
    expr_engine: &ExpressionRecovery,
    resolutions: Vec<ResolvedDynamicCall>,
    reg_values: HashMap<(String, u32), TrackedValue>,
    stats: ResolverStats,
}
```

### TrackedValue 枚举

```rust
enum TrackedValue {
    ModuleHandle(String),           // HMODULE from LoadLibraryA
    FunctionPointer { module, symbol },  // from GetProcAddress
    ConstantAddress(u64),           // mov reg, offset string
    ExternalFunction(String),       // mov reg, [IAT] (e.g. GetProcAddress)
    Unknown,
}
```

### 证据链

```
LoadLibraryA call
  ├── IAT map identifies call as LoadLibraryA
  ├── collect_preceding_pushes finds PUSH constant
  ├── string_table resolves constant → "NTCDLLG"
  └── reg_values[eax] = ModuleHandle("NTCDLLG")

GetProcAddress call (via register)
  ├── process_mov tracks mov esi, [IAT] → ExternalFunction("GetProcAddress")
  ├── process_call sees call esi → ExternalFunction → handle_get_proc_address
  ├── pushes[0] = hModule → recover_push_as_module_handle → NTCDLLG
  ├── pushes[1] = lpProcName → recover_push_string_arg_at → "Dgraph_f20"
  └── reg_values[eax] = FunctionPointer { module: "NTCDLLG", symbol: "Dgraph_f20" }
```

## 六、为什么 Indirect Call 解析为 0

NtcMach.exe 中动态加载的函数指针**不通过寄存器直接调用**，而是：

```
GetProcAddress → eax
mov [global_struct + offset], eax    ; 保存到全局结构体
...
mov eax, [global_struct + offset]    ; 其他函数中加载
call eax                             ; 间接调用
```

当前 `DynamicPluginResolver` 只追踪寄存器值，不追踪内存存储/加载。因此：
- FunctionPointer 被记录到 `reg_values[eax]`
- 但 `mov [mem], eax` 不被追踪
- 后续 `mov eax, [mem]` 产生新的 eax 版本，不关联到 FunctionPointer
- 最终 `call eax` 无法匹配

**这是真实的架构限制，不是 bug。** 登记为 GAP。

## 九、已知 GAP

### GAP-P0-7.1-MEMORY-FUNCTION-POINTER 🔴
动态加载的函数指针通过全局/结构体内存传递，当前只追踪寄存器，不追踪内存。  
**影响**: Indirect call 解析为 0。  
**建议**: P0-7.2 实现 Memory SSA 层面的函数指针追踪（Store → Load → Call）。

### GAP-P0-7.1-CROSS-BLOCK-CONSTANT 🟡
`mov reg, offset string` 的常量传播只在块内有效，如果 mov 和 push 在不同块，无法追踪。  
**影响**: 2 个 LoadLibraryA 调用参数未恢复。  
**建议**: 扩展 ConstantAddress 跨块保留（类似 ModuleHandle）。

### GAP-P0-7.1-IAT-RESOLUTION 🟡
CallGraph 未解析 x86 `call [IAT]` 为 DirectExternal，当前通过 PE 导入表旁路解决。  
**影响**: 110 个 DirectExternal 中可能有部分未被 CallGraph 标记。  
**建议**: P0-5.2 后续修复 CallGraph 的 x86 IAT 解析。
