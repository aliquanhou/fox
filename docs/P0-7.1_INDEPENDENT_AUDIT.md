### 审计项 2: IAT → VA 地址空间 ✅ PASS

**要求**: 确认 iat_address (RVA) + image_base = VA，不与 SSA 中的 VA 混用。

**代码路径验证**:
1. PE 解析器 (`crates/fox-binary/src/pe/mod.rs:252`): `iat_addr = first_thunk + thunk_idx * entry_size`
   - `first_thunk` 来自 `read_u32(data, offset+16)` — 这是 PE 头中的 RVA
2. `build_iat_map_from_imports()` (`dynamic_plugin.rs:536-548`): `map.insert(image_base + func.iat_address, full_name)`
   - 正确加 image_base 转换为 VA
3. SSA 中 call 目标格式: `Memory { description: "[+0x45609c]" }` — 这是 VA
4. 匹配: `0x45609c = 0x400000 (image_base) + 0x5609c (RVA)` ✓

**真实验证**: IAT 0x45609c → KERNEL32.dll!LoadLibraryA，与反汇编 `call [0x45609C]` 一致。

**结论**: 地址空间正确，RVA/VA 无混用。

### 审计项 3: PUSH 扫描逻辑 ✅ PASS (带 NON-BLOCKING GAP)

**要求**: 确认 64 条扫描限制不会把其他调用的 PUSH 错配进来。

**代码分析** (`collect_preceding_pushes`, line 464-488):
- 从 call_idx 向前扫描，跳过非 Push 指令
- 最大扫描 64 条指令
- 按调用需要的参数数量收集 (LoadLibraryA=1, GetProcAddress=2)

**真实案例验证** (0x42f49C GetProcAddress):
```
0x42f491: push 0x45B778     ; PUSH (更远, arg2)
0x42f496: push eax          ; PUSH (更近, arg1)
0x42f497: mov [0x46BA40], eax  ; 非Push, 被正确跳过
0x42f49C: call esi          ; GetProcAddress
```
扫描结果: pushes[0]=push eax (arg1), pushes[1]=push 0x45B778 (arg2) ✓

**LoadLibraryA 案例** (0x42f46d):
- PUSH @ 0x42f3b5, CALL @ 0x42f46d，中间隔 30 条 Mov 指令
- 64 条限制足够覆盖 (30 < 64) ✓

**理论风险**: 如果两个调用之间少于 64 条指令且中间有 PUSH，可能错配。但 **fail-closed 保护**：错配的 PUSH 如果不在 string_table 中，`recover_push_string_arg_at` 返回 None，不会产生错误解析。

**结论**: 当前案例无错配。64 条限制合理。登记 NON-BLOCKING GAP。

### 审计项 4: GetProcAddress 参数顺序 ✅ PASS

**要求**: 用真实 x86 stdcall 证据确认参数顺序。

**x86 stdcall 规则**: 参数从右到左 PUSH
```
push lpProcName   ; arg2 (先 PUSH, 离 call 更远)
push hModule      ; arg1 (后 PUSH, 离 call 更近)
call GetProcAddress
```

**代码实现** (line 281-297):
- 注释明确说明右到左 PUSH 顺序
- `pushes[0]` = 最近的 PUSH = arg1 (hModule)
- `pushes[1]` = 更远的 PUSH = arg2 (lpProcName)
- `recover_push_as_module_handle(pushes[0])` → hModule ✓
- `recover_push_string_arg_at(pushes[1])` → lpProcName ✓

**真实反汇编验证** (0x42f49C):
```
0x42f491: push 0x45B778   ; "Dgraph_f20" (arg2, 先 PUSH)
0x42f496: push eax        ; hModule (arg1, 后 PUSH)
0x42f49C: call esi        ; GetProcAddress
```
解析结果: NTCDLLG!Dgraph_f20 ✓ (module=NTCDLLG from eax, symbol=Dgraph_f20 from 0x45B778)

**结论**: 参数顺序正确，与 x86 stdcall 一致。

### 审计项 5: 跨基本块状态传播 ✅ PASS (带 NON-BLOCKING GAP)

**要求**: 确认 ModuleHandle 不会错误跨控制流路径传播。

**代码分析** (`resolve`, line 112-130):
- 每个块开始时 `retain` 保留 ModuleHandle / FunctionPointer / ExternalFunction
- 清除 ConstantAddress (块内临时值)
- 依赖 SSA 版本号区分不同路径的寄存器值

**真实案例验证** (0x42f46d LoadLibraryA):
```
0x42f46d: call [0x45609C]    ; LoadLibraryA → eax = HMODULE
0x42f473: test eax, eax
0x42f47A: jnz 0x42f48A        ; 条件分支
0x42f47C: push 0x100          ; fallthrough 路径
0x42f481: call 0x427A70
0x42f486: add esp, 4
0x42f489: ret                  ; fallthrough 路径结束, 不到达 GetProcAddress
0x42f48A: push esi             ; taken 路径
0x42f491: push 0x45B778
0x42f496: push eax             ; eax 版本与 LoadLibraryA 后一致
0x42f49C: call esi             ; GetProcAddress
```
- fallthrough 路径是 ret，不会到达 GetProcAddress
- 只有 taken 路径到达 GetProcAddress
- eax 在 LoadLibraryA 后到 GetProcAddress 前无修改指令 (test/mov [mem],eax/jnz 均不修改 eax)
- SSA 版本号一致，ModuleHandle 正确匹配 ✓

**理论风险**: 如果两条路径都到达同一 GetProcAddress，SSA 应插入 phi 节点，版本号变化导致不匹配（安全失败）。当前 NtcMach 案例中不存在此情况。

**结论**: 当前案例安全。SSA 版本号提供保护。登记 NON-BLOCKING GAP。

## 四、额外代码审查发现

### 发现 1: `clear_return_register()` 是空实现 🟡 NON-BLOCKING

`dynamic_plugin.rs:528-531`:
```rust
fn clear_return_register(&mut self) {
    // eax gets overwritten by any call; we can't track it across unknown calls
    // But we keep other registers' tracked values
}
```

注释说要清除 eax，但实际什么都没做。依赖 SSA 版本号来区分调用前后的 eax。在当前 FOX SSA 实现中，call 指令的隐式返回值写入可能没有被显式版本化（从调试输出看 GetProcAddress 后 eax 版本为 0）。

**影响**: 如果两个 GetProcAddress 调用在同一块内且中间没有修改 eax，第二个调用的 eax 可能仍然匹配第一个的 FunctionPointer。但由于第二个 GetProcAddress 会覆盖 FunctionPointer 记录，所以不会产生错误解析（只是旧的被覆盖）。

**建议**: 非阻塞，未来可显式清除 eax 的 FunctionPointer/ModuleHandle 记录。

### 发现 2: `process_instruction` 只处理 Call 和 Mov 🟡 NON-BLOCKING

只处理 `"Call"` 和 `"Mov"`，不处理 Push、Pop、Add、Sub 等。这是有意的最小实现，但意味着：
- `pop eax` 不会更新 reg_values（如果 eax 被 pop 覆盖，旧的 FunctionPointer 可能残留）
- `add esp, 4` 不影响寄存器追踪（正确）

**影响**: 在当前 NtcMach 案例中未造成问题。未来如果遇到 `pop eax` 覆盖函数指针的场景，可能需要扩展。

### 发现 3: Evidence 字段未填充 🟡 NON-BLOCKING

`ResolvedDynamicCall.evidence` 中 `load_library_address`、`get_proc_address_address` 等均为 0（line 217-222）。报告中已说明 "Evidence tracking (simplified in first phase)"。

**影响**: 不影响解析正确性，但影响可追溯性。未来应填充真实证据地址。
