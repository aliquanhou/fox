## 0. 问题描述

P0-6.7 批量反编译发现：Structured IR 的输出顺序不符合 CFG 执行顺序。

以 `0x41F000` 为例，修复前的输出：

```c
void func_41F000() {
    if ((eax.v0 & eax.v0) == 0) {        // ← 控制结构先输出
        call_unknown(...);
        return ...;
    }
    /* UNKNOWN: ... */ goto loc_41F022;
    esp_1 = (esp.0 - 40);                 // ← 函数入口代码最后输出
    call_unknown(...);
    ...
}
```

函数入口代码（`esp -= 40`, `call`）跑到了控制结构之后，导致人无法阅读和理解函数。

---

## 1. 根因分析

### 1.1 原三阶段构建逻辑

**Phase 1:** 按 CFG 块构建扁平语句 → `block_statements: HashMap<block_id, Vec<Statement>>`

**Phase 2:** 按 `ControlStructure` 列表顺序（branch 指令地址排序）提升 If/Guard/Unknown，直接 `push` 到 `top_level`

**Phase 3:** 剩余未处理块按地址顺序追加到 `top_level`

### 1.2 问题根因

- Phase 2 按 ControlStructure 顺序输出，而 ControlStructure 按 branch 指令地址排序
- 函数入口块（block 0）通常不包含条件跳转，不在 ControlStructure 列表中
- 入口块的语句在 Phase 3 才被追加，而 Phase 3 在 Phase 2 之后
- **结果：所有控制结构先于函数入口代码输出**

---

## 2. 修复方案

### 2.1 核心思路

将 Phase 2 从"直接 push 到 top_level"改为"构建 branch_block → Statement 映射"，然后 Phase 3 改为从入口块 BFS 遍历，按执行顺序输出。

### 2.2 新四阶段构建逻辑

**Phase 1（不变）:** 按 CFG 块构建扁平语句

**Phase 2（修改）:** 遍历 ControlStructure，构建 `branch_to_structure: HashMap<block_id, Statement>`
- IfElse → 从 block_statements 中 remove then/else 块语句，构建 Statement::If
- GuardClause → remove body 块语句，构建 Statement::GuardClause
- Unknown → 构建 Statement::Unknown
- 记录 `structure_body_blocks: HashSet<block_id>`（then/else/body/return 块）

**Phase 3（新增）:** 从入口块（block 0）开始 BFS 遍历 CFG
- 建立 `address_to_block: HashMap<u64, usize>` 用于通过 edge.target_address 查找目标块
- 对每个访问的块：
  - 如果是 branch_block（在 branch_to_structure 中）：先输出该块自己的扁平语句（CMP/TEST 等），再输出控制结构
  - 否则如果不是 structure_body_block：输出该块的扁平语句
  - 将后继块加入 BFS 队列

**Phase 4（原 Phase 3 修改）:** 不可达块（未被 BFS 访问、非 body 块）按地址顺序追加

### 2.3 关键设计决策

1. **Branch 块先输出自己的语句，再输出控制结构** — 因为 CMP/TEST 在 branch 块内，Jcc 也在 branch 块内。先输出 CMP/TEST 的 Assign，再输出 if/guard/unknown，符合执行顺序。

2. **BFS 而非 DFS** — BFS 简单且对大多数函数正确。DFS 更接近执行顺序但处理循环和共享块更复杂。BFS 是第一版修复的合理选择。

3. **Body 块不单独输出** — then/else/body 块的语句已经被包含在控制结构的 body 中，标记为 structure_body_blocks 后在 BFS 中跳过。

4. **不可达块最后追加** — BFS 可能无法到达所有块（如异常处理块、jump table 目标），这些块按地址顺序追加在最后。

## 5. 已知限制

### 5.1 BFS 而非严格执行顺序

BFS 按层级遍历，对于 if/else 后的 merge 块，BFS 会在 then/else 块之后访问 merge 块，这是正确的。但对于更复杂的 CFG（如嵌套循环、异常处理），BFS 可能不是严格的执行顺序。

**影响：** 大多数函数输出顺序正确。极端复杂 CFG 可能有轻微顺序偏差。

**修复时机：** 后续可改为 DFS 或基于 Dominator Tree 的拓扑排序。

### 5.2 不可达块追加在最后

BFS 无法到达的块（如异常处理块、jump table 间接目标）按地址顺序追加在函数最后。这些块的输出位置可能不符合执行顺序。

**影响：** 少数函数可能有尾部不可达块。

**修复时机：** 后续可改进 CFG 遍历以覆盖间接跳转目标。

### 5.3 嵌套结构仍为 GAP

P0-6.6A 登记的 `GAP-P0-6.6A-NESTED-STRUCTURE`（控制结构无递归嵌套）未在本阶段修复。所有 if/guard 仍在顶层。

**影响：** 复杂函数的控制流是扁平的，但顺序正确。

**修复时机：** 后续阶段。
