## 二、当前架构：Call 语义证据链

FOX 当前与 Call 相关的模块及数据流：

```
Machine Instruction
    ↓
IR (IROp::Call)
    ↓
SSA (SSAInstruction { op: "Call", operands })
    ↓
CallGraph (CallGraphEdge: kind, caller, callee, resolved_symbol, evidence)
    ↓
DynamicPluginResolver (LoadLibraryA → GetProcAddress → FunctionPointer → Indirect Call)
    ↓
ExpressionRecovery (recover_use for PUSH args, recover_return_value)
    ↓
StructuredIRBuilder (CallStmt { target, arguments, arguments_complete })
    ↓
CLikeEmitter (C-like text output)
```

**关键观察**: Identity（调用了谁）已经从底层传到了 Emitter。但 Behavior（调用前后发生了什么）和 Semantics（这个调用干什么）没有显式的语义层。

## 四、15-Call 样本深度分析

### 4.1 Dynamic Plugin Calls（7 个，全部来自 P0-7.1B）

| Call | Function | Target | 调用后行为 |
|------|----------|--------|-----------|
| 0x421BD0 | 0x421B40 | NTCDLLC!DCompiler_f19 | 直接 Jump，无 return consumer |
| 0x42F5C0 | 0x42F3B0 | NTCDLLG!Dgraph_f00 | NTC_LoadAll 内，继续初始化 |
| 0x42F7E0 | 0x42F5D0 | NTCDLLM!DMachine_f00 | NTC_LoadAll 内 |
| 0x42FE60 | 0x42FC50 | NTCDLLC!DCompiler_f00 | NTC_LoadAll 内 |
| 0x4301C0 | 0x42FF20 | NTCDLLV!DAutoTape_f00 | NTC_LoadAll 内 |
| 0x4303F0 | 0x4301E0 | NTCDLLV!DVtest_f00 | NTC_LoadAll 内 |
| 0x43065A | 0x430410 | NTCDLLV!DFeed0_f00 | NTC_LoadAll 内 |

**关键观察**: 6/7 个 dynamic call 在 NTC_LoadAll 函数内，用于初始化函数指针表。只有 DCompiler_f19 @ 0x421BD0 是真正的业务调用，但其后直接 Jump，未使用返回值。

### 4.2 Direct External Calls（抽样 5 个）

| Call | Function | Target | 调用后行为 |
|------|----------|--------|-----------|
| 0x455EDE | 0x455E4C | MSVCRT.dll!_initterm | CRT 初始化 |
| 0x455F11 | 0x455E4C | MSVCRT.dll!_initterm | CRT 初始化 |
| 0x455F96 | 0x455E4C | MSVCRT.dll!_XcptFilter | CRT 初始化 |

**观察**: 抽样的 external call 集中在 CRT 入口函数。NtcMach 的 110 个 external call 主要是 MSVCRT 和 KERNEL32 运行时调用。

### 4.3 Return Value → Branch Consumer 样本（来自 0x421B40 函数）

以下 call 均满足 `call → test eax, eax → CondJump` 模式：

| Call @ | 后续指令 | 行为推断 |
|--------|---------|---------|
| 0x421D77 | `test eax,eax` → `CondJump` | 返回值用于成功/失败判断 |
| 0x421D84 | `test eax,eax` → `CondJump` | 返回值用于成功/失败判断 |
| 0x421DA4 | `test eax,eax` → `CondJump` | 返回值用于成功/失败判断 |
| 0x421DB4 | `test eax,eax` → `CondJump` | 返回值用于成功/失败判断 |

**FOX 当前能力**: SSA 已经记录了 `test eax.49, eax.49 → FLAGS.76` 和 `CondJump FLAGS.76`。ConditionRecovery (P0-6.3A) 可以恢复 `eax == 0` 条件。ControlStructure (P0-6.4B) 可以识别 GuardClause。

**但**: FOX 当前没有显式建立 `call X → return value eax → test → condition` 的语义链。这些是相邻指令的事实，没有被组织成"X 的返回值被用于错误判断"的语义结论。

### 4.4 Call → Memory Effect 样本

从 0x421B40 函数观察：

```
call @0x421CD4
  ↓ add esp, 4          (栈清理)
  ↓ mov [esi+0x18ad8], ebx  (Store: 写入全局状态)
  ↓ mov eax, [esi+0x18ad0]  (Load: 读取全局状态)
  ↓ cmp eax, ebx
  ↓ CondJump
```

**FOX 当前能力**: Memory SSA 记录了 Store 和 Load，但没有建立 `call → memory state change → subsequent load` 的因果关系。Memory SSA 是函数内的，不追踪 callee 的 side effects。

## 七、Identity → Behavior → Semantics 三层定位

### Layer 1: Identity — "调用了谁？"

**FOX 当前状态**: ✅ 基本完成

- Direct internal: 2700 calls 已知 target address
- Direct external: 110 calls 已知 symbol
- Dynamic plugin: 7 calls 已知 module!symbol
- Indirect: 679 calls 未知（GAP-1）

**进入 Layer 2 的最小缺口**: 无。Identity 层已经足够支撑 Behavior 分析。

### Layer 2: Behavior — "调用前后发生了什么？"

**FOX 当前状态**: 🟡 底层事实已存在，但未组织成语义

已有的底层事实：
- SSA 记录了 call 后的 eax 版本和消费者
- ConditionRecovery 可以恢复 `eax == 0` 条件
- ControlStructure 可以识别 GuardClause
- Memory SSA 记录了 call 前后的 Store/Load

缺失的语义组织：
- 没有显式的 `CallBehavior` 结构
- 没有建立 `call → return value → condition` 的因果链
- 没有 `call → memory effect` 建模
- 没有 `call → side effect summary`

**进入 Layer 2 的最小缺口**: 建立 Call Behavior Consumer Layer，将已有的 SSA/Condition/Memory 事实组织成结构化的调用行为描述。

### Layer 3: Semantics — "这个调用在程序中承担什么功能？"

**FOX 当前状态**: 🔴 完全不存在

- 没有业务语义推理
- 没有 API 知识库
- 没有函数功能分类
- 没有调用目的推断

**进入 Layer 3 的最小缺口**: 需要先完成 Layer 2，然后结合 DLL 导出函数的实际反编译结果，才能开始语义推断。当前不具备进入 Layer 3 的基础。

## 九、推荐的最小下一施工方向

### P0-7.2.1: Call Behavior Recovery（最小闭环）

**目标**: 建立第一个 Call Behavior 语义层，将已有的 SSA/Condition 事实组织成结构化的调用行为。

**最小范围**:
1. 建立 `CallBehavior` 结构，表达：
   - `ReturnUsedInCondition`: call 的返回值被 test/cmp + CondJump 使用
   - `ReturnIgnored`: call 的返回值未被使用
   - `HasMemoryEffectAfter`: call 后有 Store（仅记录事实，不推断 callee effect）
2. 针对 NtcMach 真实函数，统计：
   - 多少 call 的返回值被用于条件判断
   - 多少 call 的返回值被忽略
   - 多少 call 后有 memory store
3. 不做：跨函数分析、callee side effect 推断、业务语义

**为什么是这个**: GAP-4 是当前最容易闭合的缺口——底层事实（SSA + ConditionRecovery + ControlStructure）已经全部存在，只需要一个 Consumer Layer 将它们组织起来。这比 GAP-5（memory effect）或 GAP-6（cross-function）更容易实现，且能立即提升反编译结果的可读性。

**预期产出**: 从"call_unknown()"到"call_unknown() /* return used in condition */"或类似的行为标注。

## 十二、结论

**FOX 当前处于 Layer 1（Identity）基本完成，Layer 2（Behavior）底层事实已具备但未组织，Layer 3（Semantics）完全不存在。**

最关键的发现：
1. **Identity 层已经足够**: 2817/3496 (80.6%) calls 有已知 target
2. **Behavior 层的底层事实已经存在**: SSA + ConditionRecovery + ControlStructure + Memory SSA 都能提供调用行为的原始数据，但没有语义层将它们组织起来
3. **Return value → condition 是最容易闭合的缺口**: 大量 call 满足 `call → test eax → jcc` 模式，FOX 已有所有底层事实
4. **Memory effect 和 cross-function 是更大的缺口**: 需要新的分析能力，不是简单的 Consumer Layer

**推荐下一步**: P0-7.2.1 Call Behavior Recovery——建立最小 Consumer Layer，将已有的 return value + condition 事实组织成结构化的调用行为标注。
