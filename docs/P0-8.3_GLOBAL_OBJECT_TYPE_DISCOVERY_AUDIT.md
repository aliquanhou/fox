## 2. 核心发现

### 2.1 global_46E920 是一个大型全局结构体指针

**证据链**：

```
mov reg, [0x46E920]     → reg = global_46E920
mov [reg + 0xDBE21C], x → global_46E920->field_0xDBE21C
```

**关键数据**：

| 指标 | 数值 |
|------|------|
| 直接访问 [0x46E920] | 1,946 次 |
| 加载到寄存器的位置 | 920 处 |
| 最大字段偏移 | **0xDBE21C** (~14.4 MB) |
| 典型子对象地址计算 | `global_46E920 + 0xDBB3B0` |
| 14376688 十进制 = 0xDBB3B0 | 结构体子对象偏移 |

**结论**: global_46E920 指向一个**至少 14MB 的大型结构体**。这不是普通全局变量，而是 NtcMach 的核心运行时对象/设备上下文/全局状态中心。

### 2.2 使用模式

从反编译输出观察：

```c
// 模式 1: 加载后作为函数参数
ecx_7 = global_46E920;
call_unknown(...);

// 模式 2: 计算子对象地址后传参
edx_29 = (global_46E920 + 14376688);  // global_46E920 + 0xDBB3B0
call_432100((global_46E920 + 14376688));

// 模式 3: 直接字段访问（显示为原始寄存器）
eax_4 = ecx->field_0xDBE21C;  // ecx 实际 = global_46E920
al_5 = ecx->field_0xDBD418;
```

### 2.3 初始化位置

- **第一次写入**: func_0x427880 @ 0x4278AC
- 这很可能是 NtcMach 的初始化/启动函数
- 需要进一步分析写入值的来源（malloc? 静态分配?）

## 3. 为什么没有看到 `global_46E920->field_XX`

当前输出中，加载 global_46E920 后，后续字段访问显示为：
```c
ecx_7 = global_46E920;
// 后续:
eax_4 = ecx->field_0xDBE21C;  // 用的是 ecx，不是 ecx_7
```

**原因**: SSA 寄存器版本追踪没有把 `ecx_7 = global_46E920` 和后续的 `ecx->field_XX` 关联起来。后续的字段访问用的是原始寄存器名 `ecx`，不是 SSA 版本 `ecx_7`。

**这是 GAP**: 需要简单的寄存器值传播（全局加载 → 后续字段访问合并），才能输出 `global_46E920->field_XX`。

## 5. GAP Registry

### GAP-P0-8.3-REGISTER-PROPAGATION（P0）
**问题**: `ecx_7 = global_46E920` 后，`[ecx+0xDBE21C]` 仍显示为 `ecx->field_0xDBE21C`，而非 `global_46E920->field_0xDBE21C`。
**影响**: 1,004+ 个 global_46E920 访问中，大部分字段访问无法追溯到全局对象。
**最小修复**: 在 emitter 中做简单的寄存器值追踪：如果寄存器的值来自 global_XXXXXX，则后续字段访问显示为 `global_XXXXXX->field_YY`。

### GAP-P0-8.3-INIT-ANALYSIS（P1）
**问题**: 未分析 [0x46E920] 第一次写入的值来源。
**需要**: 追踪 func_0x427880 中写入 [0x46E920] 的值是否来自 malloc/new。

### GAP-P0-8.3-STRUCT-LAYOUT（P2）
**问题**: 未聚类字段偏移形成结构体布局。
**已知**: 至少有 0xDBE21C、0xDBD418、0xDBC6F0、0xDBB3B0 等大偏移字段。
**需要**: 统计所有字段访问频率，形成 struct global_46E920 { ... }。
