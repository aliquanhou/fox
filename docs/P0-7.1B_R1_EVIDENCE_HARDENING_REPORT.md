## 一、架构师审计发现的两个 Blocking GAP

### GAP-1: ResolvedDynamicCall.evidence 四地址全为 0

P0-7.1B 中 `DynamicCallEvidence` 结构体已定义，但生成 `ResolvedDynamicCall` 时四个字段全部硬编码为 `0`：

```rust
evidence: DynamicCallEvidence {
    load_library_address: 0,
    get_proc_address_address: 0,
    module_name_address: 0,
    symbol_name_address: 0,
}
```

**根因**: Evidence 没有沿 Value Flow 传播。`TrackedValue::ModuleHandle` 和 `FunctionPointer` 只携带语义名称，不携带产生它们的指令地址和字符串地址。

### GAP-2: Heap Function Pointer 仅以 offset 作为跨函数 identity

```rust
heap_offset_values: HashMap<i64, TrackedValue>
```

这会产生 `object A + 0xDBCB04` 和 `object B + 0xDBCB04` 被视为同一个 slot 的风险。禁止仅凭 same offset 恢复 FunctionPointer。

## 二、任务 1：Evidence Chain 真正保存

### 2.1 TrackedValue 扩展（携带 Evidence）

```rust
pub enum TrackedValue {
    ModuleHandle {
        module: String,
        load_library_address: u64,      // LoadLibraryA 调用地址
        module_name_address: u64,       // 模块名字符串地址
    },
    FunctionPointer {
        module: String,
        symbol: String,
        load_library_address: u64,      // 从 ModuleHandle 继承
        module_name_address: u64,       // 从 ModuleHandle 继承
        get_proc_address_address: u64,  // GetProcAddress 调用地址
        symbol_name_address: u64,       // 符号名字符串地址
    },
    ConstantAddress(u64),
    ExternalFunction(String),
    GlobalBasePointer(u64),            // 新增：全局基址指针（用于 Heap identity）
    Unknown,
}
```

### 2.2 Evidence 传播路径

```
LoadLibraryA("NTCDLLG") @ 0x42F46D
    ↓ module_name_address = 字符串地址
    ↓ ModuleHandle { module, load_library_address, module_name_address } in eax
    ↓
GetProcAddress(hModule, "Dgraph_f00") @ 0x42F49C
    ↓ 从 hModule (ModuleHandle) 继承 load_library_address + module_name_address
    ↓ symbol_name_address = 符号字符串地址
    ↓ FunctionPointer { ..., get_proc_address_address, symbol_name_address } in eax
    ↓
Store → Memory → Load → Register  (Evidence 不丢失)
    ↓
call eax @ 0x42F5C0
    ↓
ResolvedDynamicCall.evidence = 全部四个真实地址
```

### 2.3 关键代码位置

| 位置 | 作用 |
|------|------|
| `handle_load_library()` | 保存 `inst.address` 和 `str_addr` 到 ModuleHandle |
| `handle_get_proc_address()` | 从 ModuleHandleInfo 继承 Evidence，保存 `inst.address` 和 `sym_addr` |
| `recover_push_as_module_handle()` | 返回 `ModuleHandleInfo`（含完整 Evidence） |
| `process_call()` indirect call | 从 FunctionPointer 提取 Evidence 填入 ResolvedDynamicCall |

## 三、任务 2：Heap Alias Fail-Closed

### 3.1 HeapBaseIdentity 枚举

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub enum HeapBaseIdentity {
    /// 基址寄存器从特定全局地址加载（如 mov ecx, [0x46E920]）
    /// Store 和 Load 具有相同 (global_addr, offset) 即证明同一对象槽位
    Global(u64),
    /// 基址无法证明 → fail-closed，不解析
    Unknown,
}
```

### 3.2 Heap slot key 从 `i64` 改为 `(HeapBaseIdentity, i64)`

```rust
// 旧：仅 offset
heap_offset_values: HashMap<i64, TrackedValue>

// 新：(base_identity, offset)
heap_offset_values: HashMap<(HeapBaseIdentity, i64), TrackedValue>
```

### 3.3 GlobalBasePointer 追踪

当遇到 `mov reg, [global_addr]` 且该地址不是 IAT 也不是 function pointer slot 时：

```rust
mov ecx, [0x46E920]  →  reg_values[(ecx, ver)] = GlobalBasePointer(0x46E920)
```

### 3.4 resolve_heap_base()

从 Memory description 如 `"[ecx+0xdbcb04]"` 解析：
1. 提取基址寄存器名（`ecx`）
2. 在 reg_values 中查找该寄存器是否持有 GlobalBasePointer
3. 如果是 → `HeapBaseIdentity::Global(global_addr)`
4. 如果不是 → `HeapBaseIdentity::Unknown`

### 3.5 Fail-Closed 行为

| 场景 | 行为 |
|------|------|
| Store base = Global(0x46E920), Load base = Global(0x46E920), same offset | ✅ 解析 |
| Store base = Global(0x46E920), Load base = Global(0x46A180), same offset | ❌ 不匹配，Unknown |
| Store base = Unknown, Load base = Global(0x46E920) | ❌ Store 时 base 未知，不记录 |
| Store base = Global(0x46E920), Load base = Unknown | ❌ Load 时 base 未知，不查找 |
| 跨函数传播 | 仅 Global base identity 的 slot 进入 cross-function map |

### 3.6 NtcMach 中的证明

对于 7 个恢复结果，典型证据链：

```
NTC_LoadAll:
  mov ecx, [0x46E920]          → ecx = GlobalBasePointer(0x46E920)
  mov [ecx+0xDBCB04], eax      → Store key=(Global(0x46E920), 0xDBCB04) = Dgraph_f00

其他函数:
  mov ecx, [0x46E920]          → ecx = GlobalBasePointer(0x46E920)
  mov eax, [ecx+0xDBCB04]      → Load key=(Global(0x46E920), 0xDBCB04) → Dgraph_f00
  call eax                     → resolved: NTCDLLG!Dgraph_f00
```

Store base 和 Load base 都证明来自同一个全局地址 `0x46E920`，因此是同一结构对象。

## 十、P0-7.1B-R1.1 — Heap Base SSA Version Exactness（追加修复）

### 10.1 架构师审计发现

`resolve_heap_base()` 原实现扫描寄存器**所有历史版本**，找到第一个 GlobalBasePointer 就使用，而不是使用当前指令对应的精确 SSA version。

潜在风险：
```
ecx.3 = GlobalBasePointer(0x46E920)
ecx.4 = something_else        ← 寄存器被覆盖
load [ecx.4 + 0xDBCB04]       ← 应该 Unknown，但旧代码可能找到 ecx.3
```

### 10.2 修复

`resolve_heap_base()` 签名从 `(description)` 改为 `(ssa, block_id, inst_idx, description)`：

1. 从 description 提取基址寄存器名（如 `ecx`）
2. 调用 `find_latest_register_version(ssa, block_id, inst_idx, reg_name)` 获取当前指令之前该寄存器的**精确最新版本**
3. 用 `(name, exact_version)` 在 reg_values 中精确查找
4. 如果该精确版本不是 GlobalBasePointer → Unknown（不扫描其他版本）

### 10.3 新增单元测试（3 个）

| 测试 | 场景 | 预期 |
|------|------|------|
| `heap_base_overwritten_register_must_be_unknown` | ecx.1=GlobalBasePointer, ecx.2=Unknown, 在 inst 2(ecx.2) 查询 | Unknown |
| `heap_base_exact_version_must_resolve` | ecx.1=GlobalBasePointer, 在 inst 1(ecx.1) 查询 | Global(0x46E920) |
| `heap_base_no_global_pointer_must_be_unknown` | reg_values 为空 | Unknown |

### 10.4 对 NtcMach 真实结果的影响

| 指标 | R1 | R1.1 | 变化 |
|------|-----|------|------|
| Indirect calls resolved | 7 | **7** | 不变 |
| Heap Slots (cross-function) | 77 | **62** | -15（排除版本不匹配的 slot） |
| 7 个 Regression Gate | PASS | **PASS** | 不变 |

精确版本匹配排除了 15 个版本不匹配的 heap slot，但 7 个真实结果全部保留，证明它们的基址版本确实正确。
