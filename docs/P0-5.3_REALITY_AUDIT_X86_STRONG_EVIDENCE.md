## 2. Current Confidence System Audit

### 2.1 Confidence Calculation Formula

```
confidence = max_weight + 0.1 * (evidence_count - 1) * (1.0 - max_weight)
```

- `max_weight`: highest single evidence weight
- `evidence_count`: total number of evidence items
- Diminishing returns: each extra evidence adds only 10% of remaining gap

### 2.2 Confidence Tier Thresholds

| Tier | Threshold |
|------|-----------|
| Confirmed | >= 0.85 |
| High | >= 0.65 |
| Probable | >= 0.40 |
| Unknown | >= 0.15 |
| Rejected | < 0.15 |

### 2.3 Current Evidence Weights (Function Discovery)

| Evidence Kind | Weight | Source Phase | x86 Available? |
|---------------|--------|-------------|----------------|
| EntryPoint | 0.95 | Phase 1 | ✅ (1 function) |
| ExportEntry | 0.90 | Phase 1 | ❌ (NtcMach.exe has 0 exports) |
| PdataEntry | 0.85 | Phase 1.5 | ❌ (x64 only) |
| CallReference (>=3 calls) | 0.70 | Phase 3 | ✅ |
| CallReference (<3 calls) | 0.50 | Phase 3 | ✅ |
| ValidFunctionBody | 0.60 | Phase 4.5 | ✅ |

| CallReference (additional) | 0.30 | Phase 3 | ✅ |

### 2.4 Root Cause Analysis

For a typical x86 function discovered via call target:

```
Evidence items:
  1. CallReference (count >= 3)  [weight 0.70]
  2. ValidFunctionBody            [weight 0.60]
  3. TailCall                     [weight 0.30]  (if applicable)
  4. FunctionPrologue             [weight 0.40]  (if matched)

max_weight = 0.70
evidence_count = 3-4
bonus = 0.1 * (2-3) * (1.0 - 0.70) = 0.06 - 0.09
confidence = 0.76 - 0.79  →  High (>= 0.65, < 0.85)
```

**To reach Confirmed (>= 0.85) with max_weight = 0.70:**
```
0.70 + 0.1 * extra * 0.30 >= 0.85
0.03 * extra >= 0.15
extra >= 5
evidence_count >= 6
```

This would require 6+ independent evidence items, which is unrealistic for most functions. The diminishing-returns formula makes it mathematically very difficult for any function without a single strong evidence (>= 0.80) to reach Confirmed.

**For x64 functions with .pdata:**
```
max_weight = 0.85 (PdataEntry)
confidence = 0.85 + bonus  →  Confirmed (>= 0.85)
```

This is why x64 ground truth samples have many Confirmed functions, while x86 NtcMach.exe has only 1.

## 3. x86-Specific Strong Evidence Candidates

### 3.1 SEH / Exception Registration (FS:[0] chains)

**Mechanism**: x86 Windows uses `FS:[0]` linked-list exception registration. A function that sets up SEH (`push offset handler; push fs:[0]; mov fs:[0], esp`) has a very strong function boundary signal.

**Reliability**: HIGH — SEH setup only occurs at function entry. MSVC x86 with /EHa or C++ exceptions generates this pattern.

**Current status**: NOT IMPLEMENTED. FOX does not detect SEH registration patterns.

**Coverage estimate**: NtcMach.exe likely has 20-40 functions with SEH (C++ exception handling, security cookie).

### 3.2 Relocation Entries Pointing to Code

**Mechanism**: PE base relocations (`.reloc` section) contain entries that point to addresses needing fixup. If a relocation entry points into an executable section at a function-aligned boundary, it's strong evidence of a function entry (e.g., function pointer in a jump table or vtable).

**Reliability**: MEDIUM-HIGH — relocations pointing to code are almost always function or code-label references. Need to distinguish function entries from internal labels (jump table targets, etc.).

**Current status**: NOT IMPLEMENTED. FOX parses relocations but does not use them as function evidence.

**NtcMach.exe**: 0 relocations (per P0-5.1 audit), so this won't help for this specific binary. But it's valuable for DLLs with relocations.

### 3.3 Data-Section Cross-References (Function Pointer Tables)

**Mechanism**: Scan `.data`/`.rdata` sections for pointers that point into executable sections. These are function pointer tables (vtables, callback arrays, dispatch tables). Each referenced address is a strong function candidate.

**Reliability**: MEDIUM — data pointers to code are likely function entries, but could also be jump table targets or internal labels. Need alignment and instruction validation.

**Current status**: PARTIALLY IMPLEMENTED. `discover_address_taken_functions` (Phase 3.5) scans for LEA reg, [rip+disp] in code, but does NOT scan data sections for function pointers.

**Coverage estimate**: NtcMach.exe likely has vtables and function pointer tables in .data/.rdata.

### 3.4 Recursive Descent Reachability from Entry Point

**Mechanism**: Starting from the entry point, recursively follow CALL targets and CFG edges. Any function reachable via this traversal has strong evidence of being a real function (it's actually called from the entry point's call graph).

**Reliability**: HIGH — if a function is reachable from the entry point via direct CALL chains, it's almost certainly a real function.

**Current status**: NOT IMPLEMENTED as evidence. FOX builds CFG and CallGraph, but does not add `ReachableFromEntry` evidence to discovered functions. The `EvidenceKind::ReachableFromEntry` exists in the enum but is never used in Function Discovery.

**Coverage estimate**: NtcMach.exe — most functions called from the entry point's call graph would be reachable. Could cover 100-200 functions.

### 3.5 Code Section Boundary / Padding Analysis

**Mechanism**: Functions often start after `int3` (0xCC) padding or at section boundaries. A function that starts immediately after padding, with a valid prologue, has stronger boundary evidence.

**Reliability**: LOW-MEDIUM — padding is common but not universal. MSVC uses /INCREMENTAL padding, but release builds may not have padding between functions.

**Current status**: PARTIALLY IMPLEMENTED. `discover_orphan_leaf_functions` uses int3 padding, but only for tiny leaf functions (RET after padding). Not used as general boundary evidence.

### 3.6 Compiler-Specific Patterns (/GS Cookie, etc.)

**Mechanism**: MSVC x86 with /GS generates a security cookie check at function entry:
```asm
mov eax, dword ptr [___security_cookie]
xor eax, esp
push eax
lea eax, [esp+...]
call @__security_check_cookie@4
```
The presence of `___security_cookie` reference at function entry is a strong MSVC function boundary signal.

**Reliability**: HIGH for MSVC-compiled binaries with /GS. But not all functions have /GS (small functions, leaf functions may be exempt).

**Current status**: NOT IMPLEMENTED.

**Coverage estimate**: NtcMach.exe — likely 50-70% of non-trivial functions have /GS cookie.

### 3.7 Import Thunk Exclusion (Negative Evidence)

**Mechanism**: P0-5.2 already identifies import thunks (`jmp [IAT]`) and classifies them as `IdentityKind::ImportThunk`. This removes false positives from the function pool, improving precision.

**Reliability**: HIGH (already implemented and verified).

**Current status**: IMPLEMENTED (P0-5.2). But it's identity-layer, not confidence-layer. Import thunks still appear in function list with High/Probable confidence.

**Impact**: Doesn't increase Confirmed count, but reduces false positives.

## 5. Architecture Gap Analysis

### 5.1 Current Architecture Limitation

The current confidence system has a structural issue:

```
Single strong evidence (>= 0.85)  →  Confirmed
Multiple medium evidence (0.6-0.7) →  capped at ~0.79 (High)
```

The diminishing-returns formula (`0.1 * extra * (1 - max)`) means that without a single strong evidence, no amount of medium evidence can push confidence above ~0.85.

This is actually **by design** — it prevents false positives from accumulating weak heuristics. But it means x86 functions are structurally locked out of Confirmed status unless a new strong evidence source is added.

### 5.2 What "Confirmed" Should Mean

Confirmed should mean: "FOX has independent, strong evidence that this is a real function with correct boundaries."

For x64, `.pdata` provides this (Windows exception handling metadata is authoritative).
For x86, we need equivalent authoritative sources:
- SEH registration (Windows exception handling metadata equivalent)
- /GS cookie (compiler-generated security mechanism)
- ReachableFromEntry (call graph provenance)

### 5.3 What Should NOT Be Done

❌ **Do NOT lower the Confirmed threshold from 0.85.** This would weaken the meaning of Confirmed and increase false positives.

❌ **Do NOT inflate CallReference or ValidFunctionBody weights.** These are medium evidence and should stay that way.

❌ **Do NOT add prologue pattern zoo.** More prologue patterns don't create strong evidence; they create more medium evidence that still can't reach Confirmed.

❌ **Do NOT modify Ground Truth to make x86 look better.** The 1/359 Confirmed rate is a real finding, not a test failure.

## 6. Recommended P0-5.3 Implementation Scope

Based on this audit, P0-5.3 implementation should focus on **high-reliability, low-false-positive evidence sources**:

### Priority 1 (HIGH reliability, LOW false positive):

1. **ReachableFromEntry evidence** — LOWEST cost, already have CFG/CallGraph. Add evidence to any function reachable via direct CALL from entry point's call graph. Weight: 0.80.

2. **SEH Registration detection** — Scan for `push offset handler; push fs:[0]; mov fs:[0], esp` pattern at function entry. Weight: 0.85 (equivalent to .pdata for x86 exception handling).

3. **/GS Security Cookie detection** — Scan for `mov reg, [___security_cookie]; xor reg, esp` pattern at function entry. Weight: 0.80.

### Priority 2 (MEDIUM-HIGH reliability):

4. **Data-section function pointer scan** — Scan .data/.rdata for pointers to executable section, validate target has valid prologue. Weight: 0.65 (medium, needs validation).

### Priority 3 (Negative evidence / precision):

5. **ImportThunk confidence adjustment** — Import thunks (P0-5.2) should not be counted as High/Probable native functions. They should have a separate identity-based confidence or be excluded from native function statistics.

### NOT in P0-5.3 (deferred):

- Relocation→Code evidence (NtcMach.exe has 0 relocations; useful for DLLs but not this binary)
- Code boundary/padding analysis (too unreliable for strong evidence)
- Confidence formula changes (keep current formula)
- x86 .pdata equivalent (doesn't exist for x86)

## 7. Expected Impact

If Priority 1 evidence sources are implemented:

| Evidence | Est. Coverage (NtcMach) | Weight |
|----------|--------------------------|--------|
| ReachableFromEntry | 100-200 funcs | 0.80 |
| SEH Registration | 20-40 funcs | 0.85 |
| /GS Cookie | 150-250 funcs | 0.80 |

A function with ReachableFromEntry (0.80) + CallReference (0.70) + ValidFunctionBody (0.60):
```
max = 0.80
extra = 2
bonus = 0.1 * 2 * 0.20 = 0.04
confidence = 0.84  →  just below Confirmed (0.85)
```

A function with SEH (0.85) + anything:
```
max = 0.85
confidence >= 0.85  →  Confirmed
```

A function with /GS (0.80) + ReachableFromEntry (0.80) + ValidFunctionBody (0.60):
```
max = 0.80
extra = 2
bonus = 0.1 * 2 * 0.20 = 0.04
confidence = 0.84  →  just below
```

With /GS (0.80) + ReachableFromEntry (0.80) + CallReference (0.70) + ValidFunctionBody (0.60):
```
max = 0.80
extra = 3
bonus = 0.1 * 3 * 0.20 = 0.06
confidence = 0.86  →  Confirmed
```

**Expected Confirmed count after P0-5.3**: 80-150 functions (up from 1), primarily via SEH + /GS + ReachableFromEntry combinations.

**Important**: This is an estimate, not a target. The actual number depends on real binary analysis. If fewer functions reach Confirmed, that's acceptable — the goal is evidence reliability, not a number.

## 8. Test Strategy

### 8.1 Ground Truth Validation

- Use existing 10 ground truth samples (x86 + x64, O0 + O2)
- Verify new evidence sources don't break existing Confirmed/High/Probable distribution
- Verify no false positives: new evidence only applied to real functions

### 8.2 NtcMach.exe Commercial Validation

- Before/after comparison of confidence tier distribution
- Verify ReachableFromEntry evidence traces to real call graph paths
- Verify SEH patterns match actual exception handling setup
- Verify /GS patterns match `___security_cookie` imports

### 8.3 Negative Tests

- Functions without SEH/GS should NOT get SEH/GS evidence
- Data pointers to internal labels should NOT get function-level evidence
- Import thunks should NOT get native function evidence

### 8.4 Evidence Traceability

- Every new evidence must trace to:
  - Instruction address (for SEH/GS patterns)
  - Call graph path (for ReachableFromEntry)
  - Data section offset (for function pointers)

## 10. Audit Conclusion

**P0-5.3 Reality Audit: COMPLETE**

### Key Findings:

1. **Root cause identified**: x86 functions are structurally locked out of Confirmed (>= 0.85) because the strongest available evidence is CallReference (0.70) or ValidFunctionBody (0.60), and the diminishing-returns formula caps multi-medium-evidence confidence at ~0.79.

2. **x64 advantage**: .pdata (0.85) gives x64 functions an immediate Confirmed path. x86 has no equivalent metadata.

3. **High-reliability candidates identified**: SEH Registration (0.85), /GS Cookie (0.80), ReachableFromEntry (0.80) — all with low false-positive risk.

4. **Architecture principle confirmed**: Do NOT lower thresholds or inflate medium evidence. Add strong evidence sources instead.

### Implementation Readiness:

P0-5.3 is ready for Architecture + Implementation phase. The audit has identified:
- 3 Priority 1 evidence sources (high reliability, low FP risk)
- 1 Priority 2 evidence source (medium reliability)
- 1 Priority 3 improvement (import thunk statistics)
- Clear test strategy
- Expected impact estimate (not a target)

**No implementation has been performed in this audit phase.** All findings are based on code review and NtcMach.exe analysis.
