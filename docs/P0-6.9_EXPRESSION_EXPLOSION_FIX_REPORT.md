## 0. 问题描述

P0-6.7 批量反编译发现：NtcMach.exe 359 个函数总输出 **~80MB**，其中单个函数 `0x4539B0` 输出 **20.4MB**（188 statements，平均 108KB/statement）。

根因：Expression Recovery 生成的嵌套 Phi / Binary 表达式在 Display 时无输出截断，单个表达式可达数万字符。

**影响：** 反编译结果无法用普通文本编辑器打开，人无法阅读。

---

## 1. 根因分析

### 1.1 Expression Recovery 已有预算（但不够）

| 预算 | 值 | 作用范围 |
|---|---|---|
| `max_depth` | 64 | 单表达式递归深度 |
| `max_nodes` | 10,000 | 单表达式节点数 |
| `function_total_budget` | 100,000 | 仅 `recover_all_definitions()` 使用 |

**问题：** Structured IR Builder 使用 `recover_definition()`（单表达式路径），每个表达式独立使用 `max_nodes=10000`，不共享 function_total_budget。188 个 statement × 10000 nodes = 潜在 188 万节点。

### 1.2 Display 无输出截断

`Expression::Display`（expression.rs line 876-912）递归格式化整个表达式树，**无任何输出长度限制**。Phi 的 incoming 值可以是嵌套 Phi / Binary，导致指数级展开。

### 1.3 Phi 是最大爆炸源

`Expression::Phi { incoming }` 的 Display 遍历所有 incoming 值并递归格式化每个值。当 incoming 中包含其他 Phi 时，形成递归爆炸。

## 2. 修复方案

### 2.1 核心原则

- **不修改已封板的 Expression Recovery**（expression.rs 🔒 SEALED）
- **在 Emitter 层（presentation layer）增加截断**
- 截断是 fail-closed：超过限制时输出 `/* expr truncated */`，不猜测

### 2.2 新增 EmitterConfig 字段

```rust
pub struct EmitterConfig {
    // ... 已有字段 ...
    /// Maximum characters per expression before truncation.
    pub max_expression_chars: usize,    // 默认 400
    /// Maximum recursion depth for expression formatting.
    pub max_expression_depth: usize,    // 默认 8
}
```

### 2.3 新增截断格式化方法

`CLikeEmitter::format_expr(expr) -> String`：
- 递归格式化表达式，但在每一步检查：
  - 累计输出长度 ≥ `max_expression_chars` → 停止，标记 truncated
  - 递归深度 ≥ `max_expression_depth` → 输出 `...`，标记 truncated
- Phi 特殊处理：
  - 最多显示 3 个 incoming（超过显示 `...N more`）
  - Phi 值的递归深度限制为 2（防止 Phi→Phi→Phi 爆炸）
- Call 参数最多显示 4 个（超过显示 `...N more`）
- 截断后追加 `/* expr truncated */` 注释

### 2.4 替换所有 Expression Display 调用

在 `emit_statement()` 中，所有直接使用 `{}` Display 格式化 Expression 的地方替换为 `self.format_expr(expr)`：

| 位置 | 修复前 | 修复后 |
|---|---|---|
| Assign.rhs | `rhs` | `self.format_expr(rhs)` |
| GuardClause.return_value | `val` | `self.format_expr(val)` |
| Return.value | `val` | `self.format_expr(val)` |
| PhiAssign.incoming.value | `p.value` | `self.format_expr(&p.value)` |
| AssignTarget::Memory.address | `address` | `self.format_expr(address)` |

## 6. 已知限制（非阻塞）

### 6.1 截断是 presentation layer，不修改 Expression 数据

截断只影响 Emitter 的输出文本，Expression 数据结构本身仍然完整。后续如果需要精确表达式分析（如 Type Recovery），可以直接使用 Expression 数据而非截断后的文本。

### 6.2 截断标记 `/* expr truncated */` 可能出现在表达式中间

当递归深度或字符数在表达式中间达到限制时，截断标记会出现在当前位置。这是预期行为（fail-closed），后续可优化为更优雅的截断点。

### 6.3 max_expression_chars=400 是经验值

400 字符对于大多数表达式足够，对于极端嵌套的 Phi 会触发截断。如果后续发现 400 太严格或太宽松，可通过 EmitterConfig 调整。
