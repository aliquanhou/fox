## 4. Memory SSA 最小架构提案

### 4.1 核心抽象

```rust
/// A memory variable identity — the "variable" being versioned in Memory SSA.
/// Two memory operations reference the same MemoryVariable if they MAY alias.
pub enum MemoryVariable {
    /// Stack slot: base register + displacement (exact identity)
    Stack { base: String, displacement: i64 },
    /// Global: exact address (exact identity)
    Global { address: u64 },
    /// Heap: conservative — all heap accesses may alias (single variable per function)
    Heap,
    /// Unknown: conservative — may alias with anything (single variable)
    Unknown,
}

/// A memory definition (Store or ReadWrite).
pub struct MemoryDefinition {
    pub block_id: usize,
    pub inst_index: usize,
    pub address: u64,
    pub variable: MemoryVariable,
    pub kind: MemoryOperationKind,  // Store or ReadWrite
    pub source_register: Option<String>,
    pub evidence: String,
}

/// A memory use (Load or ReadWrite).
pub struct MemoryUse {
    pub block_id: usize,
    pub inst_index: usize,
    pub operand_index: usize,
    pub address: u64,
    pub variable: MemoryVariable,
    pub kind: MemoryOperationKind,  // Load or ReadWrite
    pub destination_register: Option<String>,
    pub evidence: String,
}
```

### 4.2 Memory SSA 构造

```
MemorySSAConstructor::construct(ir_func, memory_analysis)
  │
  ├── 1. Build MemoryVariable identity from MemoryOperation.location
  │     Stack{base,disp} → exact
  │     Global{addr} → exact
  │     Heap → conservative (all heap = one variable)
  │     Unknown → conservative
  │
  ├── 2. Collect memory definition blocks (from Store/ReadWrite operations)
  │     def_blocks: HashMap<MemoryVariable, HashSet<block_id>>
  │
  ├── 3. Reuse existing DominatorTree (no recomputation)
  │
  ├── 4. Phi placement at dominance frontiers (same algorithm as Register SSA)
  │     for each MemoryVariable with multiple def blocks
  │
  ├── 5. Dominator-tree DFS renaming with per-MemoryVariable version stack
  │     Store → new MemoryVersion (definition)
  │     Load → use current MemoryVersion
  │     MemoryPhi → new version at join point
  │
  ├── 6. Build memory use-def / def-use chains
  │     MemoryUse → MemoryDefinition (via version)
  │
  └── 7. Evidence trace per version/phi
```

### 4.3 与 Register SSA 共存

```
SSAFunction (existing, register-only)
  └── register phi / versions / use-def

MemorySSAFunction (new, P0-4.3)
  ├── memory_variables: Vec<MemoryVariable>
  ├── memory_phi_nodes: Vec<MemoryPhiNode>
  ├── memory_versions: HashMap<MemoryVariable, u32>
  ├── memory_use_def: HashMap<(block, inst, op), (def_block, def_inst, version)>
  ├── memory_def_use: HashMap<(block, inst), Vec<(use_block, use_inst, op)>>
```

**两者平行存在，不互相替代。** FunctionAnalysisContext 将同时持有 `ssa`（register）和 `memory_ssa`（新）。

## 5. 关键设计决策

### 5.1 MemoryVariable 身份策略

- **Stack**: `(base_register, displacement)` 作为精确身份。`[rsp+8]` 和 `[rsp+8]` 是同一个 variable。`[rsp+8]` 和 `[rbp+8]` 是不同 variable（保守，不合并）。
- **Global**: `address` 作为精确身份。
- **Heap**: 所有 Heap 访问合并为一个保守 variable。这意味着 `mov [rax], 1` 和 `mov [rbx], 2` 会被视为可能互相 kill — 保守但安全。
- **Unknown**: 所有 Unknown 合并为一个保守 variable。

### 5.2 为什么 Heap 要保守合并？

没有 Alias Analysis 时，两个 heap 访问 `[rax+8]` 和 `[rbx+8]` 可能指向同一位置。保守合并保证 Memory SSA 不会错误地认为它们独立。精确 alias 留给后续阶段。

### 5.3 复用现有基础设施

- **DominatorTree**: 直接复用，不重新实现
- **Phi placement 算法**: 与 Register SSA 相同的迭代 dominance frontier 算法
- **Renaming**: 与 Register SSA 相同的 dominator-tree DFS + version stack
- **MemoryAnalysis**: 作为 MemoryDefinition/MemoryUse 的来源（不重新解析 IR）
