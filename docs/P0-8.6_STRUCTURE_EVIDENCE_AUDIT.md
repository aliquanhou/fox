## 3. 关键发现

### 3.1 连续 DWORD 是主流（gap=4 占 60/111 ≈ 54%）

这说明 global_46E920 确实是一个大型结构体，大部分字段是连续 DWORD 布局。**结构聚类算法方向正确。**

### 3.2 跨函数证据不足（MEDIUM 仅 13/96 = 13.5%）

83/96 函数只有 LOW 置信度，说明：
- 大部分函数只访问 1-2 个字段
- 单函数内无法确认结构布局
- **需要跨函数汇总才能提高置信度**

### 3.3 数组检测未触发（0 个 possible array）

当前算法要求单函数内 8+ 连续字段才标记为 possible array。NtcMach 中没有函数在一个函数内访问这么多连续字段。这说明：
- 数组访问可能分散在多个函数中
- 或者数组访问通过索引寄存器动态计算，不被识别为连续 offset

### 3.4 字段分布范围

字段偏移范围：0x000 ~ 0xDBE21C
这说明 global_46E920 指向一个非常大的对象（至少 ~14MB 地址空间被访问）。

## 4. 风险评估

### 4.1 误把连续内存当结构体的风险

**低**。原因：
- gap=4 占 54%，但这是在 156 个字段中的分布
- 单函数内 cluster 数量少（18/96）
- 大部分函数只有 LOW 置信度，不会过度声称

### 4.2 字段合并错误风险

**低**。原因：
- 按 object 分组，不同 global 对象不会合并
- 按 offset 精确匹配，不会跨对象污染

### 4.3 数组误判风险

**当前算法保守**。只在 8+ 连续字段时标记 possible array，实际未触发。

## 5. GAP 登记

### GAP-P0-8.6-CROSS-FUNCTION-AGGREGATION（P1）
当前统计在单函数内进行。跨函数字段汇总后，置信度会大幅提升：
- 字段 X 在 5 个函数中都出现 → 置信度提升
- 字段 X 和 Y 在 3 个函数中同时出现 → 它们可能属于同一子结构

### GAP-P0-8.6-LOOP-AWARE-ARRAY（P2）
当前数组检测基于"连续 offset 数量"，不检测循环索引模式。
真正的数组可能是 `base + i*4` 动态计算，不被识别。

### GAP-P0-8.6-READ-WRITE-DISTINCTION（P2）
当前只记录总访问次数，不区分读/写。
读写模式可以帮助区分：
- 配置字段（写少读多）
- 状态字段（读写均衡）
- 计数器（写多读少）

- ✅ 字段聚类没有明显误判
