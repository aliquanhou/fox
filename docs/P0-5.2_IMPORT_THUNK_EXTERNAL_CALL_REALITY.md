## 1. Implementation Summary

P0-5.2 resolves the identity chain for x86 import thunks. Before this stage, FOX treated `jmp [IAT]` stubs as ordinary canonical functions, and CALLs to those stubs were classified as DirectInternal with no resolved symbol. After this stage:

- Import thunks are recognized via **Pattern + PE/IAT Evidence** (Fail-Closed).
- They receive `IdentityKind::ImportThunk` with source symbol `DLL!FunctionName`.
- CALLs to import thunks are classified as `DirectExternal` with resolved symbol.
- Evidence chain: CALL instruction → thunk address → JMP [IAT] → IAT entry → imported DLL/function.

**NtcMach.exe result**: DirectExternal 0 → 110; DirectInternal 2035 → 1925 (delta = 110, consistent).

## 2. Architecture Before

```text
CALL 0x455E40 (thunk code address)
  ↓
CallGraph::classify_call
  ├── iat_map.get(&0x455E40) → miss (key is IAT entry VA, not thunk code VA)
  ├── func_by_addr.get(&0x455E40) → hit (thunk discovered as function)
  └── CallEdgeKind::Direct (internal), resolved_symbol = None

Identity:
  0x455E40 → IdentityKind::Canonical (wrong — it's an import thunk)
```

## 3. Architecture After

```text
CALL 0x455E40 (thunk code address)
  ↓
CallGraph::classify_call
  ├── import_thunks.get(&0x455E40) → hit! ("KERNEL32.dll", "SomeFunction")
  ├── CallEdgeKind::External
  ├── resolved_symbol = "KERNEL32.dll!SomeFunction"
  └── Evidence: ImportEntry @ 0x455E40, weight=0.95

Identity:
  0x455E40 → IdentityKind::ImportThunk
           → source_symbols = ["KERNEL32.dll!SomeFunction"]
           → SourceFunctionIdentity mapping created
```


## 6. Fail-Closed Principles

1. **Pattern ≠ Identity**: `jmp [mem]` alone is NOT sufficient. Must prove target ∈ IAT.
2. **IAT membership is canonical**: Only PE Import Address Table entries qualify.
3. **Non-IAT indirect JMP remains ordinary**: `jmp [global_ptr]`, `jmp [rax]`, `jmp [table]` are NOT import thunks.
4. **Unresolved IAT → ExternalUnknown**: If IAT entry exists but symbol cannot be resolved, mark as external without fabricating a name.
5. **No Function Discovery scoring changes**: x86 discovery heuristics untouched. Import thunk classification is identity-layer only.

## 11. What FOX Can Prove

- Import thunk identity when `jmp [IAT]` pattern + IAT membership is established.
- External call resolution for CALLs targeting identified import thunks.
- Evidence chain from CALL instruction → thunk → IAT → imported symbol.
- Fail-closed behavior: non-IAT indirect JMPs are NOT misclassified as import thunks.

## 12. What FOX Cannot Determine

- Indirect call targets (`call rax`, `call [rcx+18h]`) — classification only, no resolution.
- x86 function boundary strong evidence (no .pdata equivalent).
- Mixed-mode binaries (CLR + native code interleave).
- Delay-load imports (not yet parsed).

## 13. What FOX Currently Guesses

- Nothing in the import thunk path — all classifications are evidence-based.
- Function Discovery confidence tiers remain heuristic-based (unchanged from P0-3.4R).
