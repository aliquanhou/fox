## 一、实现了什么

在 `CallStmt` 中新增 `behavior: Option<CallBehavior>` 字段，自动检测 call 的返回值（eax）在 call 之后的消费方式。

### CallBehavior 枚举

```rust
pub enum CallBehavior {
    /// call → test/cmp eax → CondJump
    ReturnUsedInCondition {
        condition: ConditionRecovery,  // 复用 P0-6.3A
        consumer_instruction: u64,     // test/cmp 地址
        branch_instruction: u64,       // CondJump 地址
    },
    /// call → mov/push/etc 使用 eax
    ReturnUsedByInstruction {
        consumer_instruction: u64,
        consumer_op: String,
    },
    /// 扫描窗口内无消费者
    NoConsumer,
}
```

### 检测逻辑 (`detect_call_behavior`)

1. 从 call 指令后开始，同 block 内向前扫描最多 8 条指令
2. 找到第一条使用 eax 的指令
3. 如果是 Test/Cmp 且下一条是 CondJump → `ReturnUsedInCondition`（调用 `recover_condition`）
4. 如果是其他指令 → `ReturnUsedByInstruction`
5. 未找到 → `NoConsumer`

## 三、Return → Consumer 怎么连接

```
Call instruction @0x421D77
    ↓ detect_call_behavior() 扫描后续指令
    ↓ 找到 @0x421D79 Test eax.49, eax.49
    ↓ 确认下一条 @0x421D7B 是 CondJump
    ↓ 调用 recover_condition(ssa, block, inst_idx_of_CondJump)
    ↓ 得到 ConditionRecovery::Resolved(Condition { operator: NotEqual, ... })
    ↓
CallBehavior::ReturnUsedInCondition {
    condition: Resolved(...),
    consumer_instruction: 0x421D79,
    branch_instruction: 0x421D7B,
}
```

---

## 四、Evidence 怎么保存

每个 `ReturnUsedInCondition` 包含：
- `condition`: 完整 ConditionRecovery（含 FLAGS producer 地址、branch 地址、操作数）
- `consumer_instruction`: test/cmp 指令地址
- `branch_instruction`: CondJump 指令地址

CallStmt 本身的 `StatementEvidence.instruction_addresses` 包含 call 地址。

完整证据链：`call @0x421D77 → test @0x421D79 → FLAGS → jcc @0x421D7B → condition`

## 十二、下一步真正阻碍"完整项目反编译"的问题

1. **跨 block return consumer**: 当前只扫描同 block，大量 call 的 return consumer 可能在下一个 block
2. **`result = call()` 结构化**: 当前只有注释，未来应输出 `v1 = call(...); if (v1 == 0) {...}`
3. **Call → Memory Effect**: call 的 side effects 完全未建模
4. **Cross-function dataflow**: callee 的行为不影响 caller 分析
5. **679 indirect calls 仍未知 target**
