## 1. Executive Summary

P0-5.5 established the Evidence → Claim semantic layer. P0-5.6 asks the foundational question:

> **FOX 到底应该如何定义"一个函数真实存在"这件事？**

The audit finds that the current `Function` struct is **overloaded**: it simultaneously represents a discovery candidate, a validated body, an aggregate confidence, and a CFG container — without separating Start/Body/End/Identity into independent reality dimensions.

**Core finding**: A function's reality has **four independent dimensions** — Start, Body, End, Identity — each with its own evidence, claims, and uncertainty. The current single `confidence_tier` collapses these into one number, making it impossible to express "Start=Confirmed, Body=High, End=Unknown, Identity=Canonical."

**P2 root cause confirmed**: `Evidence` has a single `address` field. PdataEntry stores `begin_va` in `address`, but `end_va` is only in `Function.end_address`, not in the Evidence. The FunctionEnd claim's subject therefore points to begin_va. This is not a Claim bug — it's a **data model gap**: Evidence cannot carry a range.

**Recommended canonical model**: `FunctionReality` with four independent `BoundaryReality` dimensions (Start/Body/End) + `IdentityReality`, each carrying positive/negative evidence and claims. `Function.confidence_tier` remains as a derived aggregate for backward compatibility. Evidence gains an optional `end_address` field to solve the P2 precisely.

## 2. Current Model Audit

### 2.1 Function Struct (fox-analysis/src/lib.rs:123)

```rust
pub struct Function {
    pub name: String,
    pub address: Address,              // Start (implicit)
    pub end_address: Option<Address>,  // End (often None for x86)
    pub size: Option<usize>,
    pub basic_blocks: Vec<BasicBlock>,
    pub calls: Vec<u64>,
    pub called_by: Vec<u64>,
    pub confidence_tier: FunctionConfidence,  // SINGLE scalar
    pub validation: FunctionValidation,       // has estimated_end (separate)
}
```

**Problems**:
1. `address` is implicitly "start" but has no confidence or evidence dimension
2. `end_address` is `Option`, often None for x86 (no .pdata)
3. `validation.estimated_end` is a **third** end concept (separate from `end_address`)
4. `confidence_tier` is one number for the entire function
5. No identity field (identity is in separate `FunctionIdentityTable`, keyed by address)
6. No positive/negative evidence separation (both in `WithEvidence.evidence`)

### 2.2 FunctionConfidence (single scalar, 5 tiers)

```
Confirmed >= 0.85
High      >= 0.65
Probable  >= 0.40
Unknown   >= 0.15
Rejected  < 0.15
```

Derived from `EvidenceList::confidence()` = `max_weight + 0.1 * extra_count * (1 - max_weight)`.

**Problem**: This formula treats all evidence as supporting the same claim ("this is a function"). It cannot express dimensional uncertainty.

### 2.3 FunctionValidation (body validation only)

```rust
pub struct FunctionValidation {
    pub validated: bool,
    pub valid_entry: bool,
    pub has_return: bool,
    pub has_tail_call: bool,
    pub instruction_count: usize,
    pub estimated_end: Option<u64>,   // linear sweep estimate
    pub failure_reason: Option<String>,
    pub termination_kind: TerminationKind,
}
```

**Problem**: `estimated_end` is a linear-sweep estimate, not an evidence-backed boundary. It's separate from `Function.end_address` (which is set from .pdata for x64). Two end concepts, no unification.

### 2.4 FunctionDiscovery Pipeline (8 phases)

```
Phase 1:   Seed (entry point + exports)          → Strong Start evidence
Phase 1.5: .pdata (x64)                          → Strong Start + End
Phase 2:   Scan CALL targets                     → Supporting Start
Phase 3:   Add CALL targets as functions
Phase 3.5: Address-Taken (LEA + data pointers)   → Weak Start candidate
Phase 4:   Prologue patterns                     → Contextual Start
Phase 4.2: Orphan leaf (int3 + RET)              → Contextual Start
Phase 4.3: Thunk following                       → Supporting Start
Phase 4.5: Validate bodies                       → Body evidence (+/-)
Phase 5:   Negative evidence                     → Negative
Phase 6:   Assign confidence tiers (single scalar)
```

**Key observation**: Every phase produces evidence that feeds the **same** confidence number. Start evidence (CALL target, prologue), Body evidence (valid body, RET), and End evidence (.pdata EndAddress, tail-call) are all mixed together.

### 2.5 Identity Model (separate table)

```rust
pub enum IdentityKind {
    Canonical, Thunk, ImportThunk, Folded, Alias, Unknown,
}

pub struct BinaryFunctionIdentity {
    pub address: u64,
    pub kind: IdentityKind,
```

**Good**: Identity is separate from Boundary. Identity ≠ Function.
**Problem**: Identity has no confidence. An ImportThunk identified by IAT evidence is 100% certain, but a "Canonical" function with only prologue match is uncertain. No way to express this.

**Good**: Claims have independent type/subject/strength.

## 3. The Core Question: How Should FOX Define "A Function Truly Exists"?

### 3.1 The Four Reality Dimensions

A function "truly exists" when **all four dimensions** have sufficient evidence:

| Dimension | Question | Strong Evidence (x64) | Strong Evidence (x86) |
|-----------|----------|----------------------|----------------------|
| **Start** | Is this address a function entry? | .pdata BeginAddress, EntryPoint, Export | EntryPoint, Export (rare), CALL target (supporting) |
| **Body** | Do the bytes form valid code? | Valid disassembly + RET/tail-call | Same |
| **End** | Where does the function end? | .pdata EndAddress | RET, tail-call, next function boundary (estimate) |
| **Identity** | What kind of entity is this? | IAT mapping (ImportThunk), JMP chain (Thunk) | Same |

### 3.2 The Reality Hierarchy

```
Definitely Function
  = Start >= Confirmed AND Body >= High AND Identity != ImportThunk/Thunk

Likely Function
  = Start >= High AND Body >= Probable

Possible Function
  = Start >= Probable AND Body >= Probable

Not Function
  = NegativeBoundary claim OR Body = Rejected

Unknown
  = insufficient evidence either way
```

### 3.3 Why Single Confidence Fails

A function with:
- Start = Confirmed (.pdata, weight 0.85)
- Body = High (valid body, weight 0.6)
- End = Unknown (no .pdata on x86, linear sweep estimate only)

Current model: confidence = 0.85 + 0.1*1*(1-0.85) = 0.865 → Confirmed.

But the End is **Unknown**! The function is "Confirmed" even though FOX doesn't know where it ends. This is misleading for Decompiler.

A function with:
- Start = Probable (prologue only, weight 0.4)
- Body = High (valid body + RET, weight 0.6)
- End = High (RET found, weight 0.3)

Current model: max = 0.6, extra = 2, bonus = 0.1*2*0.4 = 0.08, conf = 0.68 → High.

But the Start is only **Probable**! The function might start at the wrong address. "High" doesn't tell you which dimension is weak.

## 4. P2 Root Cause Analysis: PdataEntry FunctionEnd Subject

### 4.1 The Problem

In `discover_from_pdata()` (lib.rs:314):

```rust
Evidence::new(EvidenceKind::PdataEntry)
    .with_address(rf.begin_va)           // ← only begin address
    .with_detail(format!(".pdata: [0x{:X}, 0x{:X})", rf.begin_va, rf.end_va))
    .with_weight(0.85)
```

The `end_va` is:
1. Stored in `Function.end_address` (line 335/340)
2. Stored as a **string** in `Evidence.detail` (not structured)
3. **NOT** stored in any structured Evidence field

In P0-5.5 Claim mapping:
```rust
EvidenceKind::PdataEntry => vec![
    EvidenceClaim::new(FunctionStart, sub, Strong, ...),  // sub = Address(begin_va) ✅
    EvidenceClaim::new(FunctionEnd, sub, Strong, ...),    // sub = Address(begin_va) ❌
],
```

The FunctionEnd claim's subject is `begin_va`, not `end_va`.

### 4.2 Why This Is a Data Model Gap

`Evidence` has:
```rust
pub address: Option<u64>,  // single address
```

It has no `end_address` or `range` field. The `detail: Option<String>` can carry the range as text, but text is not a stable, queryable subject.

### 4.3 Solution (for P0-5.6 implementation, not this audit)

Add `end_address: Option<u64>` to `Evidence`:
```rust
pub struct Evidence {
    pub kind: EvidenceKind,
    pub address: Option<u64>,       // start / primary address
    pub end_address: Option<u64>,   // end / secondary address (for range evidence)
    pub detail: Option<String>,
    pub weight: f64,
    pub claim: Option<EvidenceClaim>,
}
```

Then PdataEntry can set both:
```rust
Evidence::new(PdataEntry)
    .with_address(rf.begin_va)
    .with_end_address(rf.end_va)    // NEW
```

And the Claim mapping can use `end_address` for FunctionEnd:
```rust
EvidenceKind::PdataEntry => vec![
    Claim(FunctionStart, Address(begin_va), Strong),
    Claim(FunctionEnd, Address(end_va), Strong),  // ✅ precise
],
```

This is a **minimal, non-breaking** change (Option field with serde default).

## 5. x86 vs x64 Reality Comparison

| Dimension | x64 | x86 |
|-----------|-----|-----|
| Start Strong Evidence | .pdata BeginAddress (0.85) | EntryPoint (0.95, 1 func), Export (0.9, rare) |
| Start Supporting | CALL target (0.7), Prologue (0.4) | CALL target (0.7), Prologue (0.4) |
| Body Strong | ValidFunctionBody (0.6) | ValidFunctionBody (0.6) |
| End Strong | .pdata EndAddress (authoritative) | **None** — only RET/tail-call/estimate |
| End Supporting | RET, tail-call | RET, tail-call, next function boundary |
| Identity | ImportThunk (IAT), Thunk (JMP) | Same |
| Confirmed count | High (.pdata covers all functions) | Low (1 in NtcMach.exe) |

**Key insight**: x64 and x86 have **different evidence sources** but should have the **same Reality Model**. The model must allow End=Unknown for x86 while End=Confirmed for x64.

## 6. Negative Evidence Gap

Current negative evidence (4 kinds):
- NegativeNonExecutableSection
- NegativeInvalidInstructionBoundary
- NegativeUnreachable
- NegativeDataAddress
- InvalidFunctionBody (validation failure)

**Missing negative claims** (needed for Function Reality):
- `NotFunctionStart` — address is inside another confirmed function's body
- `InternalBasicBlock` — address is a JMP/JCC target within a function (1179 in NtcMach)
- `SwitchTarget` — address is a jump table case target
- `SEHHandler` — address is an exception handler, not normal entry
- `OutlinedCode` — address is compiler-outlined code region
- `CompilerHelper` — address is a compiler-generated helper

These are critical for x86 where Start evidence is weak. Negative evidence helps prevent false positives.

## 7. Recommended Canonical Model: FunctionReality

### 7.1 Data Model

```rust
/// A single dimension of function reality (Start, Body, or End).
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct BoundaryReality {
    /// Status of this dimension
    pub status: RealityStatus,
    /// Numeric confidence [0,1] for this dimension only
    pub confidence: Confidence,
    /// Positive claims supporting this dimension
    pub positive_claims: Vec<EvidenceClaim>,
    /// Negative claims refuting this dimension
    pub negative_claims: Vec<EvidenceClaim>,
    /// The address this dimension applies to (start addr for Start, end addr for End)
    pub address: Option<u64>,
}

/// Reality status for a single dimension.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum RealityStatus {
    Confirmed,   // Strong evidence, authoritative
    High,        // Multiple supporting evidence
    Probable,    // Single supporting evidence
    Unknown,     // Insufficient evidence
    Rejected,    // Negative evidence dominates
}

/// Identity reality (separate from boundary).
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct IdentityReality {
    pub kind: IdentityKind,
    pub confidence: Confidence,
    pub claims: Vec<EvidenceClaim>,
}

/// The complete function reality model.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct FunctionReality {
    pub start: BoundaryReality,
    pub body: BoundaryReality,
    pub end: BoundaryReality,
    pub identity: IdentityReality,
    /// Derived aggregate (for backward compatibility)
    pub aggregate_confidence: Confidence,
    pub aggregate_tier: FunctionConfidence,
}
```

### 7.2 Integration with Existing Function

```rust
pub struct Function {
    // ... existing fields ...
    pub confidence_tier: FunctionConfidence,  // KEEP: derived aggregate
    pub validation: FunctionValidation,       // KEEP: body validation details
    /// P0-5.6: Multi-dimensional function reality (optional, populated when available)
    #[serde(default)]
    pub reality: Option<FunctionReality>,
}
```

**Non-breaking**: `reality` is `Option`, defaults to None. Existing code unchanged.

### 7.3 How It Solves the P2

With `Evidence.end_address` added:
```
PdataEntry Evidence
  address = 0x140001000 (begin)
  end_address = 0x140001200 (end)
  ↓
FunctionReality.start
  status = Confirmed
  address = 0x140001000
  positive_claims = [Claim(FunctionStart, Address(0x140001000), Strong, PdataEntry)]

FunctionReality.end
  status = Confirmed
  address = 0x140001200  ← ✅ precise!
  positive_claims = [Claim(FunctionEnd, Address(0x140001200), Strong, PdataEntry)]
```

### 7.4 How It Expresses x86 Uncertainty

For a typical x86 function in NtcMach.exe:
```
FunctionReality.start
  status = High (CALL target + prologue)
  confidence = 0.72

FunctionReality.body
  status = High (valid instructions + RET)
  confidence = 0.68

FunctionReality.end
  status = Probable (linear sweep estimate, no .pdata)
  confidence = 0.45  ← honestly uncertain

FunctionReality.identity
  kind = Canonical
  confidence = 0.80

aggregate_tier = High (derived)
```

The Decompiler can now see: "End is only Probable — decompile with caution, may run into next function."

## 8. Architecture Alternatives

### Option A: Keep Single Confidence (Status Quo)

- Pros: Simple, no changes
- Cons: Cannot express dimensional uncertainty; P2 unfixable; Decompiler cannot make informed decisions
- **Verdict: REJECT**

### Option B: Add reality: Option<FunctionReality> to Function (RECOMMENDED)

- Pros: Non-breaking, incremental, solves P2, enables Decompiler
- Cons: Two confidence sources (aggregate + dimensional) during transition
- **Verdict: RECOMMENDED**

### Option C: Replace Function.confidence_tier with FunctionReality

- Pros: Clean, single model
- Cons: Breaking change, all consumers must update, risky
- **Verdict: LATER** (after Option B is proven, deprecate aggregate)

### Option D: Separate FunctionCandidate from FunctionReality

- Pros: Clean separation of discovery from reality
- Cons: Large refactor, two parallel structures
- **Verdict: LATER** (may emerge naturally from Option B)

## 10. Decompiler Implications

### Decompiler Gate (future)

```
CanDecompile =
  reality.start.status >= High
  AND reality.body.status >= Probable
  AND reality.identity.kind != ImportThunk
  AND reality.identity.kind != Thunk

PartialDecompile (with warning) =
  reality.end.status < High
  → "Function end uncertain, decompilation may be incomplete"
```

### What Decompiler Needs from Reality

1. **Start certainty**: If Start < High, decompilation may start at wrong address → refuse or warn
2. **Body validity**: If Body < Probable, IR may be garbage → refuse
3. **End certainty**: If End < High, decompilation may overlap next function → partial output with warning
4. **Identity**: If ImportThunk/Thunk, don't decompile as native → show redirect instead

## 15. Final Answer: "How Should FOX Define 'A Function Truly Exists'?"

> **A function truly exists when its Start, Body, and End dimensions each have sufficient positive evidence and no dominating negative evidence, and its Identity is not a non-function entity (ImportThunk, Thunk, data, internal BB).**

FOX should express this as **four independent reality dimensions**, each with its own status, confidence, positive claims, and negative claims — not as a single aggregate number.

- **Start = Confirmed** means: authoritative metadata (.pdata/entry/export) or overwhelming evidence says this is a function entry
- **Body = High** means: valid disassembly + proper termination
- **End = Confirmed** means: authoritative boundary (.pdata EndAddress) or precise RET/tail-call
- **Identity = Canonical** means: not a thunk, not an import, not an internal BB

A function can be "Start=Confirmed, Body=High, End=Unknown, Identity=Canonical" — and that is **honest**. It tells the Decompiler exactly what is known and what is not.

**Uncertainty is not failure. It is information.**
