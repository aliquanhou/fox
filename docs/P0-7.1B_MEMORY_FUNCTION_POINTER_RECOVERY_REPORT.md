## 二、Root Cause 分析

P0-7.1 Phase 1 中 Indirect call = 0 的根因：

```
GetProcAddress → eax = Dgraph_f20
    ↓
mov [ecx+0xDBCB04], eax    ← 函数指针存储到全局结构体（Heap 类型）
    ↓
... 其他函数 ...
    ↓
mov eax, [ecx+0xDBCB04]    ← 从内存加载函数指针
    ↓
call eax                    ← Indirect Call，无法解析
```

Phase 1 只追踪寄存器传播（`mov esi, eax`），不追踪内存 Store/Load。  
而 NtcMach 的函数指针通过**全局结构体内存**传递，不是寄存器直接传递。

## 三、现有能力审计（不重复建设）

### Memory SSA（P0-4 系列，已封板）

| 结构 | 用途 |
|------|------|
| `MemoryDef` | Store 操作，含 `variable`、`source_register`、`block_id`、`inst_index` |
| `MemoryUse` | Load 操作，含 `variable`、`destination_register` |
| `MemoryVariable::Global { address }` | 精确全局地址（无别名风险） |
| `MemoryVariable::Heap` | 保守堆地址（所有 heap 可能别名） |
| `use_def_chains` / `def_use_chains` | 内存 use-def 链 |

`FunctionAnalysisContext.memory_ssa: Option<MemorySSAFunction>` 已可用。

### 关键发现

1. **SSA 中单操作数 Store**: `mov [0x46A180], eax`（x86 A3 操作码）在 SSA 中只有一个 Memory 操作数，源寄存器被丢弃。Memory SSA 的 `MemoryDef.source_register` 也为 None（因为 A3 编码源隐含为 eax）。
2. **双操作数 Store**: `mov [ecx+0xDBCB04], eax` 在 SSA 中有两个操作数，Memory SSA 的 `source_register=Some("eax")`，但 `variable=Heap`。
3. **函数指针存储位置**: GetProcAddress 返回值存储在 `[ecx+0xDBCB04]`（Heap 类型，偏移 0xDBCB04），不是直接全局地址。
4. **ModuleHandle 存储位置**: LoadLibraryA 返回值存储在 `[0x46A180]`、`[0x46BA40]` 等直接全局地址（Global 类型）。

## 四、实现方案

### 4.1 两阶段扫描（Cross-Function Propagation）

函数指针的 Store 在 NTC_LoadAll 中，Load+Call 在其他函数中。因此需要两阶段：

```
Pass 1: 扫描所有函数
  ├── 收集 Global 地址 → TrackedValue（ModuleHandle）
  └── 收集 Heap 偏移 → TrackedValue（FunctionPointer）
        ↓
Pass 2: 扫描所有函数（传入 Pass 1 的全局映射）
  ├── Load 从 Global 地址 → 传播 ModuleHandle
  ├── Load 从 Heap 偏移 → 传播 FunctionPointer
  └── call reg → 解析为 NTCDLL*!symbol
```

### 4.2 数据结构扩展

```rust
// DynamicPluginResolver 新增字段
memory_values: HashMap<MemoryVariable, TrackedValue>,      // 函数内 Global
heap_offset_values: HashMap<i64, TrackedValue>,            // 函数内 Heap 偏移
global_fp_slots: &HashMap<u64, TrackedValue>,              // 跨函数 Global
global_heap_slots: &HashMap<i64, TrackedValue>,            // 跨函数 Heap
```

### 4.3 Store 处理（process_store）

两种情况：

**Case A: 双操作数 Store** (`mov [ecx+off], eax`)
- SSA 有 dst=Memory, src=Variable
- 直接从 src 获取寄存器名和版本

**Case B: 单操作数 Store** (`mov [0x46A180], eax`)
- SSA 只有 dst=Memory
- 从 Memory SSA `MemoryDef.source_register` 获取源寄存器
- 如果 source_register=None（A3 编码），默认源为 eax（x86 指令集编码保证）
- 通过 `find_latest_register_version()` 查找寄存器最新版本，找不到则回退 version 0

**MemoryVariable 分类追踪**:
- `Global { address }`: 精确地址，直接追踪
- `Heap`: 用 Memory description 中的数字偏移作为 key（如 `[ecx+0xDBCB04]` → offset=0xDBCB04）
- `Stack` / `Unknown`: 不追踪（别名风险太高）

### 4.4 Load 处理（process_mov 中）

`mov reg, [mem]` 时：
1. 检查 IAT map（外部函数 thunk）— 已有逻辑
2. 检查函数内 memory_values（Global）
3. 检查跨函数 global_fp_slots（Global）
4. **新增**: 检查函数内 heap_offset_values（Heap 偏移）
5. **新增**: 检查跨函数 global_heap_slots（Heap 偏移）

### 4.5 偏移提取（extract_heap_offset）

从 Memory description 如 `"[ecx+0xdbcb04]"` 提取数字偏移：
- 找到 `+` 或 `-` 位置
- 跳过可选的 `0x` 前缀
- 取后续十六进制数字
- 支持正负偏移

**修复的 Bug**: 初版未跳过 `0x` 前缀，`'x'` 被当作非十六进制字符终止，导致 offset=0。

### 5.4 GetProcAddress 解析率提升原因

GetProcAddress 从 4/67 → 63/67，是因为 ModuleHandle 的跨函数传播：
- Phase 1: 只有 NTC_LoadAll 函数内的 GetProcAddress 能解析（ModuleHandle 在同函数内）
- P0-7.1B: ModuleHandle 存储到 Global 地址后，其他函数中的 GetProcAddress 调用通过 Load ModuleHandle 也能解析

## 六、Evidence 链

每个恢复的 indirect call 都有完整 Evidence 链：

```
LoadLibraryA("NTCDLLG") @ 0x42f46d
    ↓ ModuleHandle("NTCDLLG") in eax
    ↓ mov [0x46BA40], eax @ 0x42f497  (Global Store)
    ↓
GetProcAddress(hModule, "Dgraph_f00") @ 0x42f49c
    ↓ FunctionPointer("NTCDLLG", "Dgraph_f00") in eax
    ↓ mov [ecx+0xDBCB04], eax @ 0x42f4a9  (Heap Store, offset=0xDBCB04)
    ↓
[其他函数] mov eax, [ecx+0xDBCB04]  (Heap Load, offset=0xDBCB04)
    ↓ FunctionPointer propagates to eax
    ↓
call eax @ 0x42F5C0
    ↓
Resolved: NTCDLLG!Dgraph_f00
```
