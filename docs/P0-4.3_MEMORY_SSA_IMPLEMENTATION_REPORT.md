## 1. Implementation Summary

P0-4.3 实现了第一版可验证、可追踪的 Memory SSA。核心目标：每个 MemoryUse 必须能追溯到具体的 MemoryDef（block, instruction, version），而不是只有版本号。

**新增模块：** `crates/fox-analysis/src/memory_ssa/mod.rs`

**核心类型：**

```rust
pub enum MemoryVariable {
    Stack { base: String, displacement: i64 },  // 精确身份
    Global { address: u64 },                     // 精确身份
    Heap,                                        // 保守合并
    Unknown,                                     // 保守合并
}

pub struct MemoryDef { block_id, inst_index, address, variable, kind, source_register, evidence }
pub struct MemoryUse { block_id, inst_index, operand_index, address, variable, kind, destination_register, evidence }
pub struct MemoryPhiNode { block_id, variable, incoming: Vec<(pred_block, version)>, result_version }
pub struct MemorySSAFunction {
    memory_variables, phi_nodes, variable_versions,
    definitions, uses,
    use_def_chains,   // (block, inst, op) -> (def_block, def_inst, version)
    def_use_chains,   // (block, inst) -> Vec<(use_block, use_inst, op)>
    evidence,
}
```

## 2. Architecture

### 2.1 MemoryVariable 身份策略

| 类型 | 身份 | 说明 |
|------|------|------|
| Stack | (base_register, displacement) | 精确：`[rsp+8]` 和 `[rsp+8]` 同一 variable |
| Global | address | 精确：RIP-relative 或绝对地址 |
| Heap | 单变量 | 保守：所有 heap 访问合并，可能互相 kill |
| Unknown | 单变量 | 保守：所有 unknown 合并 |

**为什么 Heap 保守合并？** 没有 Alias Analysis 时，`[rax+8]` 和 `[rbx+8]` 可能指向同一位置。保守合并保证 Memory SSA 不会错误地认为它们独立。

### 2.2 构造算法

```
MemorySSAConstructor::construct(ir_func, mem_analysis)
  │
  ├── 1. Map MemoryOperation → (block_id, inst_index) by address
  ├── 2. Build MemoryVariable from MemoryLocation
  ├── 3. Separate defs (Store/ReadWrite) and uses (Load/ReadWrite)
  ├── 4. Collect def_blocks per variable
  ├── 5. Reuse existing DominatorTree (no recomputation)
  ├── 6. Phi placement at dominance frontiers (iterative algorithm)
  ├── 7. Dominator-tree DFS renaming with per-variable version stacks
  │     ├── Phi at block entry → new version
  │     ├── MemoryUse → current version + use-def trace
  │     └── MemoryDef → new version + def-use record
  ├── 8. Fill phi incoming edges from block_exit_versions
  └── 9. Evidence
```

### 2.3 与 Register SSA 共存

```
FunctionAnalysisContext
 ├── ssa: Option<SSAFunction>           ← Register SSA (existing, unchanged)
 ├── dataflow: Option<CfgDataFlowResult> ← Register DataFlow (existing, unchanged)
 ├── memory: Option<MemoryAnalysis>     ← P0-4.2 semantics (unchanged)
 └── memory_ssa: Option<MemorySSAFunction> ← NEW: P0-4.3
```

**不修改现有 Register SSA 语义。** 两者平行存在。

## 3. 关键正确性验证

### 3.1 Linear Store → Load

```
mov [rsp+8], rax   → MemoryDef v1 (block 0, inst 0)
mov rcx, [rsp+8]   → MemoryUse v1
                        ↓ use-def traces to (block 0, inst 0, version 1)
```

**不是** "Load → version=1" 这种只有编号的伪 SSA。

### 3.2 If-Else → Memory Phi

```
          Store [rsp+8], RAX (b1)    Store [rsp+8], RBX (b2)
                    \                        /
                     \                      /
                      MemoryPhi at b3 (incoming: b1→v1, b2→v2)
                              │
                         Load [rsp+8] (b3)
                              ↓ use-def traces to phi (block 3, inst=MAX)
```

### 3.3 Loop → Memory Phi at Header

```
b0 (pre-header) → b1 (loop header, preds=[b0,b2])
                     Store [rsp+8] → b2
                   b2 (body) → Load [rsp+8] → b1, b3
```

b1 有 2 个 predecessor → MemoryPhi at b1，incoming 来自 b0（pre-header）和 b2（回边）。

## 8. Known Limitations

1. **Heap 保守合并**：所有 heap 访问视为同一 variable，可能产生过多 MemoryPhi。精确 alias 留给 P0-4.4。
2. **operand_index 近似**：MemoryUse 的 operand_index 当前设为 0（memory operand 位置），未精确映射到 IR operand index。
3. **Unknown 操作**：`MemoryOperationKind::Unknown` 被保守地同时视为 def 和 use。
4. **无 Memory Reaching Definitions**：use-def 基于 SSA version 追溯，不是独立的 iterative reaching definitions 分析。
5. **MemoryLocation::Unknown 几乎无进入路径**（P0-4.2R 已记录 GAP）。
