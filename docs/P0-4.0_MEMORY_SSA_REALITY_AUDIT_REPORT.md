## 1. 十三个审计问题的回答

### Q1: Value SSA 当前覆盖范围

**结论：Register-only SSA，Memory 完全未版本化。**

| 维度 | 状态 | 说明 |
|------|------|------|
| Register SSA | ✅ Proper | Dominator Tree DFS + version stack + Phi placement + renaming |
| Memory SSA | ❌ 不存在 | `SSAOperand::Memory { description: String }` 只是字符串描述 |
| Phi for Memory | ❌ 不存在 | PhiNode.variable 只接受 register name |
| Use-Def (register) | ✅ 存在 | `use_def_chains` / `def_use_chains` |
| Use-Def (memory) | ❌ 不存在 | 无 memory definition 概念 |
| 集成到 analyze_binary | ❌ 未集成 | SSA 只能通过 `fox ssa <addr>` 单函数手动调用 |

**关键代码证据**（`crates/fox-analysis/src/ssa/mod.rs:87-88`）：
```rust
/// This is a simplified SSA construction for registers only.
/// Memory operands are preserved as-is (P0-2.6+ will add memory SSA).
```

### Q2: Load / Store 在 IR 中如何表达

**结论：IROp::Load/Store 存在但从未被 L1 翻译产生；Memory 只是 operand 类型。**

| 维度 | 状态 | 说明 |
|------|------|------|
| IROp::Load 定义 | ✅ 存在 | `crates/fox-ir/src/lib.rs:25` |
| IROp::Store 定义 | ✅ 存在 | `crates/fox-ir/src/lib.rs:26` |
| L1 产生 Load | ❌ 不产生 | `map_mnemonic("mov") → IROp::Mov`（无条件） |
| L1 产生 Store | ❌ 不产生 | 同上 |
| Memory operand | ✅ 结构化 | base/index/scale/disp/size/access/is_rip_relative/effective_address |
| Load/Store 区分 | ⚠️ 隐式 | 通过 operand.access（Read=load, Write=store）推断，不是显式 IR op |

**问题**：`mov eax, [rbx]` 和 `mov [rbx], eax` 都是 `IROp::Mov`，区别只在 operand 的 access 字段。这导致：
- SSA 无法区分 "this instruction defines a register" vs "this instruction defines a memory location"
- DataFlow 的 GEN/KILL 只看 register writes，完全忽略 memory stores

### Q3: Memory Location 统一表示

**结论：MemoryLocation 模型已建立，但属于死代码——未被任何分析模块使用。**

| 维度 | 状态 | 说明 |
|------|------|------|
| MemoryLocation enum | ✅ 存在 | Stack / Global / Heap / Unknown |
| classify_memory() | ✅ 存在 | 将 IR memory operand 分类为 MemoryLocation |
| MemoryOperation | ✅ 存在 | load/store + location + data_register |
| MemoryAnalysis | ✅ 存在 | 收集 operations / stack_slots / globals / heap_accesses |
| **被其他模块使用** | ❌ **死代码** | Grep 全 crates：MemoryAnalysis 只在 memory.rs 自身出现 |
| 集成到 SSA | ❌ 未集成 | SSA 的 Memory operand 是 `{ description: String }`，不是 MemoryLocation |
| 集成到 DataFlow | ❌ 未集成 | DataFlow 只跟踪 register Definition |

**这是 P0-4 最大的架构发现之一**：Memory 模型在 P0-3.4 被建立，但从未接入任何下游分析。它是一个"建好但没通电"的模块。

### Q4-Q6: Stack / Global / .rdata / .data 建模

**结论：分类逻辑存在（在死代码中），但主管线完全不使用。**

| Memory 类型 | 分类规则 | 状态 |
|-------------|----------|------|
| **Stack** | base ∈ {RSP, RBP, ESP, EBP, SP, BP} + no index | ✅ classify_memory 中实现 |
| **Global (RIP-relative)** | is_rip_relative=true → effective_address | ✅ 实现 |
| **Global (absolute)** | no base + no index → displacement as address | ✅ 实现 |
| **Heap / pointer** | 其他所有情况（RBX, RCX, RDI, etc.） | ✅ 实现（保守） |
| **.rdata 区分** | ❌ 不区分 | Global 不区分 .rdata / .data / .text |
| **.data 区分** | ❌ 不区分 | 同上 |
| **Stack slot 合并** | ❌ 不合并 | `[rsp-0x20]` 和 `[rsp-0x18]` 是独立 location，不做 frame 分析 |
| **RBP 帧重建** | ❌ 不存在 | 不分析 `sub rsp, N` 来建立 stack frame layout |

**Real-world 验证**（kernel32.dll）：
- `.text` 524KB, `.rdata` 213KB, `.data` 5KB, `.pdata` 22KB
- 当前 FOX 分析 kernel32.dll 时，所有 RIP-relative access 都被归为 Global，但不区分是在 .rdata（只读常量/IAT）还是 .data（可写全局变量）
- 这对后续 Function Pointer 分析很重要：.rdata 中的指针表 vs .data 中的函数指针变量

### Q7: Alias Analysis 现状

**结论：保守的 may_alias() 存在于死代码中，主管线无 Alias Analysis。**

| 维度 | 状态 | 说明 |

| Heap | ⚠️ 与一切 may_alias | 保守但正确 |
| Unknown | ⚠️ 与一切 may_alias | 保守但正确 |
| **集成到分析** | ❌ 未集成 | 死代码 |
| **No-alias 利用** | ❌ 不存在 | 即使知道两个 stack slot 不 alias，也不用于优化分析 |

### Q8: Memory Def-Use 现状

**结论：完全不存在。**

| 维度 | 状态 |
|------|------|
| Memory Definition 概念 | ❌ 不存在 |
| Memory Use 概念 | ❌ 不存在 |
| Memory Reaching Definitions | ❌ 不存在 |
| Memory Live Variables | ❌ 不存在 |
| Store → Load 转发 | ❌ 不存在 |
| Register Def-Use | ✅ 存在（SSA 中） |

**DataFlow 模块审计**（`crates/fox-analysis/src/dataflow/mod.rs`）：
- `Definition { block_id, inst_index, address, register: String }` — 只有 register

### Q10: Function Pointer 当前数据流能力

**结论：静态 Pattern 匹配，不是数据流分析。**

| 能力 | 状态 | 说明 |
|------|------|------|
| LEA → executable address 检测 | ✅ 存在 | 扫描 `lea reg, [rip+disp]`，若 disp 指向 .text → AddressTaken evidence |
| .rdata 函数指针扫描 | ✅ 存在 | 扫描 .rdata 中 8 字节值，若指向 .text → AddressTaken |
| AddressTaken → Function Candidate | ✅ 存在 | EvidenceKind::AddressTaken，weight 0.4-0.55 |
| **通过 Memory 追踪函数指针** | ❌ 不存在 | 无法追踪 `lea → store → load → call` 链 |
| **Data-flow-based resolution** | ❌ 不存在 | 无 Memory SSA，无法做值流分析 |

**典型失败场景**（09_function_pointer_O2 的实际模式）：
```asm
lea rax, [rip+thunk_addr]     ; ← FOX 检测到 AddressTaken
mov [rsp+0x20], rax             ; ← 存入栈，FOX 不追踪
...
mov rcx, [rsp+0x20]             ; ← 从栈加载，FOX 不知道值来自哪里
jmp rcx                          ; ← tail call，FOX 只知道是 indirect
```

FOX 通过 AddressTaken 发现了函数入口，但**无法证明这个 indirect call 调用的就是那个函数**。中间的 Memory 数据流是断的。

### Q11: Indirect Call Resolution 当前能力

**结论：IAT 已解决；其他间接调用只有 Classification，没有 Resolution。**

| 间接调用类型 | Classification | Resolution | 说明 |
|-------------|---------------|------------|------|
| `call [rip+disp]` (IAT) | ✅ IAT | ✅ DLL!Symbol | P0-3.4 已解决 |
| `call reg` | ✅ Register | ❌ Unknown | 无法追踪寄存器值 |
| `call [reg]` | ✅ Memory | ❌ Unknown | 无法追踪内存值 |
| `call [reg+disp]` | ✅ VtableCandidate | ❌ Unknown | 只标记，不解析 vtable |
| `jmp reg` (tail call) | ⚠️ 部分 | ⚠️ Thunk following | 只跟随首指令 JMP，不追踪寄存器 |

**IndirectCallKind 分类**（`crates/fox-core/src/edge.rs`）：
```rust
pub enum IndirectCallKind {
    Register,        // call rax
    Memory,          // call [rax]
    VtableCandidate, // call [rax+0x18]
    IAT,             // call [rip+disp] → resolved
    Unknown,
}
```

**关键区分**：Classification ≠ Resolution。当前 6 个 IndirectUnknown 调用只是被分类，目标完全未知。

### Q13: Evidence 如何贯穿 Memory SSA

**结论：当前 Evidence 系统不覆盖 Memory 层；需要扩展。**

| Evidence 层 | 当前状态 | Memory SSA 需要 |
|-------------|----------|-----------------|
| Instruction Evidence | ✅ ValidInstructionDecoded, BlockTerminator | MemoryLoad / MemoryStore |
| BasicBlock Evidence | ✅ 入口/终止符证据 | MemoryPhi location |
| CFG Edge Evidence | ✅ JumpTarget / Fallthrough | 不需要 |
| Function Evidence | ✅ Prologue / Pdata / CALL / AddressTaken | 不需要 |
| SSA Evidence | ⚠️ 只有 DataFlowAnalysis | MemoryDefinition / MemoryUse / MemoryPhi |
| DataFlow Evidence | ⚠️ 只有 DataFlowAnalysis | ReachingMemoryDef / LiveMemory |
| Type Evidence | ⚠️ MemoryAccessWidth | PointerDereference / MemoryType |

**需要新增的 EvidenceKind**（P0-4 设计，不实现）：
- `MemoryLoad { location, address }`
- `MemoryStore { location, address }`
- `MemoryDefinition { location, version, instruction }`
- `MemoryPhi { location, predecessors }`
- `AliasDecision { location_a, location_b, may_alias }`

**Evidence 链目标**：
```
Type = pointer
  ↓ TypeRecovery rule: "used as base in memory dereference"
  ↓ MemoryLoad at 0x14001234: base=RAX, location=Heap{base=RAX}
  ↓ Instruction: mov rcx, [rax+8] @ 0x14001234
  ↓ Binary offset
```

## 2. 重大架构发现：Pipeline Integration Gap

**这是本次审计最重要的发现，比任何单个 GAP 都关键。**

### 当前 analyze_binary() 实际执行的管线

```rust
pub fn analyze_binary(binary: &Binary) -> AnalysisResult {
    let functions = FunctionDiscovery::discover(binary);        // ✅
    let cfg = ControlFlowGraph::build(...);                       // ✅
    let call_graph = CallGraph::build(...);                       // ✅
    let identity_table = build_identity_table(...);               // ✅
    AnalysisResult { functions, cfg, call_graph, identity_table }
}
```

### 存在但**未被主管线调用**的模块

| 模块 | 位置 | 调用方式 |
|------|------|----------|
| IR Translation | `fox-ir/src/l1.rs` | 仅 CLI `fox ir` / `fox disasm` |
| SSA Construction | `fox-analysis/src/ssa/mod.rs` | 仅 CLI `fox ssa <addr>` |
| DataFlow Analysis | `fox-analysis/src/dataflow/mod.rs` | 仅 CLI `fox dataflow <addr>` |
| Type Recovery | `fox-analysis/src/type_recovery/mod.rs` | 仅 CLI `fox types <addr>` |
| Memory Analysis | `fox-ir/src/memory.rs` | **死代码，无任何调用** |

### 影响

1. **FOX 的"分析结果"实际上只有 Function + CFG + CallGraph + Identity**
2. SSA / DataFlow / TypeRecovery 是"独立工具"，不是"分析管线的一部分"
3. 它们之间**没有数据连接**：SSA 的输出不传给 DataFlow，DataFlow 的输出不传给 TypeRecovery
4. Memory SSA 要接入，必须先解决这个集成问题

### P0-4 必须先解决的架构问题

在实现 Memory SSA 之前，必须先建立统一的 **Per-Function Analysis Pipeline**：

```
Function
  ↓ Disassemble (instructions)
  ↓ IR Translation (IRFunction)
  ↓ Basic Block + CFG (per function)
  ↓ Memory Location Classification
  ↓ Memory SSA (P0-4)
  ↓ Register SSA (existing)
  ↓ DataFlow (existing, needs memory extension)
  ↓ Type Recovery (existing, needs memory extension)
  ↓ Analysis Result (per function)
```

## 5. Memory SSA Architecture Proposal

### 5.1 设计原则

1. **复用现有 MemoryLocation 模型**（不重写，从死代码中激活）
2. **先 Stack + Global，后 Heap**（Stack/Global alias 关系明确，Heap 保守处理）
3. **Conservative by default**（不确定就 may_alias，不做激进优化）
4. **Evidence-first**（每个 memory definition 都可追溯到 instruction）
5. **与 Register SSA 并行**（不替换 Register SSA，增加 Memory SSA 维度）

### 5.2 核心数据结构（设计，不实现）

```rust
/// Memory SSA function — 与 SSAFunction 并行
pub struct MemorySSAFunction {
    pub function_address: u64,
    /// Memory definitions: (block_id, inst_index) -> MemoryDefinition
    pub definitions: Vec<MemoryDefinition>,
    /// Memory uses: (block_id, inst_index) -> Vec<MemoryUse>
    pub uses: Vec<MemoryUse>,
    /// Memory phi nodes at join points
    pub phi_nodes: Vec<MemoryPhiNode>,
    /// Memory versions per location
    pub location_versions: HashMap<MemoryLocation, u32>,
    /// Memory def-use chains
    pub def_use_chains: HashMap<MemoryDefId, Vec<MemoryUseId>>,
    /// Memory use-def chains
    pub use_def_chains: HashMap<MemoryUseId, Vec<MemoryDefId>>,
    /// Alias decisions made during construction
    pub alias_decisions: Vec<AliasDecision>,
    pub evidence: Vec<Evidence>,
}

/// A memory definition (store)
pub struct MemoryDefinition {
    pub id: MemoryDefId,
    pub block_id: usize,
    pub inst_index: usize,
    pub address: u64,
    pub location: MemoryLocation,
    pub version: u32,
    /// Value being stored (register SSA version or constant)
    pub value: MemoryValue,
    pub evidence: Evidence,
}

/// A memory use (load)
pub struct MemoryUse {
    pub id: MemoryUseId,
    pub block_id: usize,
    pub inst_index: usize,
    pub address: u64,
    pub location: MemoryLocation,
    /// Destination register (SSA version)
    pub dest_register: Option<(String, u32)>,
    pub evidence: Evidence,
}

/// Memory phi at join point
pub struct MemoryPhiNode {
    pub block_id: usize,
    pub location: MemoryLocation,
    /// Incoming: (predecessor_block_id, memory_version)
    pub incoming: Vec<(usize, u32)>,
    pub result_version: u32,
}
```

### 5.3 Memory SSA 构建算法（设计）

```
Phase 1: Memory Location Classification
  For each instruction in each basic block:
    If instruction has Memory operand with access=Write → MemoryDefinition candidate
    If instruction has Memory operand with access=Read → MemoryUse candidate
    Classify each into MemoryLocation (Stack/Global/Heap/Unknown)

Phase 2: Alias Analysis (conservative)
  For each pair of memory locations in the same function:
    Compute may_alias() using existing MemoryLocation::may_alias
    Record AliasDecision for evidence

Phase 3: Memory Definition Numbering
  For each basic block (in dominator-tree DFS order):
    For each MemoryDefinition:
      Assign version = location_versions[location] + 1
      Kill previous definitions of may-aliasing locations in same block
      Record def-use chain

Phase 4: Memory Phi Placement
  Compute dominance frontier for each memory location
  Place MemoryPhiNode at join points where different definitions merge
  (Similar to Cytron et al., but for memory locations)

Phase 5: Memory Renaming
  For each MemoryUse:
    Find reaching MemoryDefinition (or MemoryPhi)
    Record use-def chain
    Assign version

Phase 6: Evidence Attachment
  Each MemoryDefinition → Evidence: MemoryStore { location, instruction }
  Each MemoryUse → Evidence: MemoryLoad { location, instruction }
  Each MemoryPhi → Evidence: MemoryPhi { location, predecessors }
  Each AliasDecision → Evidence: AliasDecision { loc_a, loc_b, may_alias }
```

### 5.4 IR 扩展（最小范围）

**不需要重写 IR，只需要增加一个后处理 pass**：

```
IRFunction (现有, mov + memory operand)
    ↓ IR Memory Normalization Pass (新增)
IRFunction with explicit Load/Store:
  - mov reg, [mem] → IROp::Load (reg = load(mem))
  - mov [mem], reg → IROp::Store (store(mem, reg))
  - 其他指令保持不变
```

这样：
- 现有 IR 翻译不需要修改
- Memory SSA 在 normalized IR 上工作
- 向后兼容

### 5.5 与现有模块的集成

```
analyze_binary()
  ↓
FunctionDiscovery → CFG → CallGraph → Identity (现有, 不变)
  ↓
For each Confirmed function:
  ↓ Disassemble
  ↓ IR Translation (现有)
  ↓ IR Memory Normalization (P0-4.1 新增)
  ↓ Memory Location Classification (激活现有 classify_memory)
  ↓ Memory SSA (P0-4.1/4.2 新增)
  ↓ Register SSA (现有, 不变)
  ↓ DataFlow (现有, 扩展 memory reaching definitions)
  ↓ TypeRecovery (现有, 扩展 memory-based type inference)
```

## 9. 当前能力总结

### 已具备（P0-3.4R SEALED）

```
Binary → PE Parser → Disassembly → Basic Block → CFG → Function Discovery
    → Call Graph → IAT Resolution → Function Identity → Evidence System
```

- Function Discovery Recall: 100% (20 GT 样本)
- GT-region Precision: 41.94% (Binary-wide: N/A)
- CFG: 基础正确（含 Jump Table）
- Call Graph: Direct + IAT External 正确
- Identity: Canonical/Thunk/Folded/Alias 分类
- Evidence: Function/CFG/CallGraph 全链路可追溯

### 未具备（P0-4 目标）

```
Memory Location → Memory Definition → Memory Use → Memory SSA → Memory Phi
    → Memory Def-Use → Alias Analysis → Function Pointer Flow
    → Indirect Call Resolution → Vtable Resolution
```

- Memory SSA: ❌ 完全不存在
- Memory DataFlow: ❌ 完全不存在
- Function Pointer 数据流解析: ❌ 只有 pattern 匹配
- Indirect Call (non-IAT) 解析: ❌ 只有 classification
- Vtable 解析: ❌ 只有标记

### 关键架构债务

1. **Pipeline Integration Gap**：SSA/DataFlow/TypeRecovery 未接入 analyze_binary
2. **MemoryAnalysis 死代码**：已建模型未使用
3. **IR 无显式 Load/Store**：需要 normalization pass

## 10. 风险与注意事项

| 风险 | 严重程度 | 缓解措施 |
|------|----------|----------|
| Memory SSA 复杂度高，容易引入 bug | 🔴 High | 先 Stack/Global，Heap 保守处理；大量 Ground Truth |
| Alias Analysis 过于保守导致 SSA 版本爆炸 | 🟡 Medium | 限制每个 location 的最大版本数；Heap 用单一保守版本 |
| Pipeline 集成可能破坏现有 P0-3 能力 | 🔴 High | per-function analysis 独立于 analyze_binary；不修改现有路径 |
| Ground Truth 中 memory expected fixture 生成困难 | 🟡 Medium | 先用简单样本（store/load/phi），逐步复杂化 |
| Real-world DLL 可能触发未覆盖的 memory pattern | 🟡 Medium | robustness 测试；不 crash 优先于正确性 |
| 为了追求数字而过度优化 alias | 🔴 High | 保守优先；Evidence 必须支持每个 alias decision |

## 11. 审计结论

**P0-4.0 Reality Audit 完成。**

核心发现：
1. FOX 当前的"分析管线"实际上只有 Function + CFG + CallGraph + Identity
2. SSA / DataFlow / TypeRecovery 是独立工具，未集成到主管线
3. Memory 模型已建立（MemoryLocation / MemoryAnalysis）但是死代码
4. Memory SSA / Memory DataFlow / Memory Def-Use 完全不存在
5. Function Pointer 和 Indirect Call 只有 pattern matching，没有数据流解析
6. 这正是 P0-4 需要解决的核心问题

**P0-4 的正确切入点不是"实现 Memory SSA 算法"，而是：**
1. 先建立 Per-Function Analysis Pipeline（解决集成债务）
2. 激活现有 MemoryLocation 模型（解决死代码）
3. 增加 IR Memory Normalization Pass（解决 Load/Store 区分）
4. 然后才是 Memory SSA 算法本身
