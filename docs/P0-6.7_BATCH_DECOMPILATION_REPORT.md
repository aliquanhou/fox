## 1. 批量反编译方法

### 1.1 配置

| 参数 | 值 | 说明 |
|---|---|---|
| Structured IR max_statements | 2000 | 批量保守设置（dogfood 用 5000） |
| Expression Recovery | 默认配置 | max_depth=64, max_nodes=10000, function_total=100000 |
| Emitter 模式 | clean（无证据注解） | 减少输出体积 |
| Phi 输出 | elide | 默认不输出 Phi |

### 1.2 处理流程

```
对每个函数:
  1. 获取 CFG + SSA
  2. recover_control_structures() → If/Guard/Unknown
  3. StructuredIRBuilder.build() → DecompilerFunction
  4. CLikeEmitter.emit() → C-like pseudocode
  5. 统计: statements, if/guard/unknown, output size, status
```

### 1.3 Status 分类标准

| Status | 条件 |
|---|---|
| **OK** | output ≥ 20 chars 且至少有 if/guard/return/call/assign 之一 |
| **Degraded** | output ≥ 20 chars 但无任何有效语句（只有函数签名和花括号） |
| **Failed** | output < 20 chars 或 SSA 不可用 |

4. **小函数/碎片（2个）** — 可能是只有几条指令的碎片函数。

## 5. 表达式爆炸问题（P0 级阻塞）

### 5.1 现象

Top 10 最大函数的输出量：

| 排名 | 地址 | 输出字符 | Statements | 平均 chars/stmt | Blocks | if | guard | unknown |
|---|---|---|---|---|---|---|---|---|
| 1 | 0x4539B0 | **20,444,179** | 188 | **108,746** | 64 | 47 | 3 | 12 |
| 2 | 0x452BC0 | 18,526,876 | 247 | 74,999 | 89 | 55 | 5 | 16 |
| 3 | 0x421F30 | 10,309,439 | 520 | 19,826 | 299 | 130 | 5 | 61 |
| 4 | 0x452180 | 4,056,133 | 295 | 13,750 | 146 | 78 | 11 | 15 |
| 5 | 0x41BBD0 | 3,370,652 | 102 | 33,046 | 69 | 48 | 5 | 3 |
| 6 | 0x430680 | 2,698,397 | 235 | 11,483 | 94 | 53 | 11 | 7 |
| 7 | 0x453400 | 2,659,949 | 130 | 20,461 | 80 | 44 | 8 | 7 |
| 8 | 0x402B30 | 2,155,336 | 116 | 18,580 | 70 | 39 | 17 | 4 |
| 9 | 0x4214A0 | 1,735,691 | 64 | 27,120 | 48 | 37 | 4 | 0 |
| 10 | 0x425800 | 1,518,965 | 454 | 3,346 | 72 | 49 | 6 | 1 |

### 5.2 根因

**0x4539B0 单函数输出 20MB，但只有 188 个 statements。平均每个 statement 108KB。**

这不是正常的伪 C 代码量。根因是：

1. **Phi 表达式嵌套爆炸** — 在 0x401390 的 dogfood 中已观察到单行 Phi 表达式可达数千字符。Top 函数的 Phi 嵌套更深。
2. **循环表达式未截断** — Expression Recovery 有 cycle detection（输出 `<?cycle detected at ...>`），但循环检测可能只在深度超限时触发，而表达式节点数预算（max_nodes=10000）是**单表达式**预算，不是全函数预算。
3. **DAG 展开为 Tree** — SSA 天然是 DAG，Expression Recovery 展开为 Tree 时重复子表达式被复制，导致指数级膨胀。

### 5.3 影响

- 20MB 单函数输出无法人工阅读
- 批量反编译总输出 80MB，无法作为项目交付物
- 后续 Variable Recovery / Type Recovery 如果基于这些表达式，会继承爆炸问题

### 5.4 建议修复方向

1. **Expression 输出截断** — 单个 Expression 输出超过 N 字符时截断为 `(...) /* expression too large */`
2. **Phi elimination** — 在 Emitter 阶段 elide Phi（已默认 elide，但 Phi 表达式仍出现在 Assign 的 rhs 中）
3. **DAG sharing** — Expression Recovery 内部支持共享节点，输出时用临时变量代替重复子表达式
4. **全函数表达式节点预算** — 目前 function_total_budget=100000 是 Structured IR 的 statements 预算，不是 Expression 节点预算。需要增加 Expression 节点的全函数预算。

## 6. 输出顺序错乱问题（P0 级阻塞）

### 6.1 现象（架构师已指出）

0x41F000 的输出顺序：

```c
void func_41F000() {
    if ((eax.v0 & eax.v0) == 0) {   // ← 先输出 GuardClause
        call_unknown(...);
        return ...;
    }
    /* UNKNOWN: ... */ goto loc_41F022;  // ← 再输出 Unknown
    esp_1 = (esp.0 - 40);            // ← 最后才输出函数入口代码
    call_unknown(...);
    ...
}
```

但 0x41F000 的实际执行顺序是：
```
0x41F000: esp -= 40          ← 函数入口
0x41F008: call ...
0x41F010: test eax, eax      ← GuardClause 条件
0x41F015: jz  ...
0x41F020: test ..., ...      ← Unknown 条件
0x41F025: jz  ...
```

### 6.2 根因

Structured IR Builder 的三阶段构建：
1. **Phase 1:** 按 CFG 块构建扁平语句 → `block_statements: HashMap<block_id, Vec<Statement>>`
2. **Phase 2:** 按 ControlStructure 列表顺序提升 If/Guard/Unknown → 从 HashMap 中 remove 对应块的语句
3. **Phase 3:** 剩余未处理块按地址顺序追加到 top_level

**问题：** Phase 2 按 ControlStructure 的顺序输出，而 ControlStructure 的顺序是按 branch 指令地址排序的。函数入口块（0x41F000）不包含条件跳转，所以不在 ControlStructure 列表中，它的语句在 Phase 3 才被追加。

**结果：** 包含条件跳转的块（0x41F010, 0x41F020）的控制结构先输出，函数入口块（0x41F000）的语句后输出。

### 6.3 影响

- 输出的伪 C 不符合执行顺序，人工阅读时会困惑
- 后续 Variable Recovery / Type Recovery 如果基于语句顺序分析，会得到错误结果
- 这是 Structured IR 的架构问题，不是 Emitter 的问题

### 6.4 修复方向

**Phase 2 不应该直接 push 到 top_level，而应该建立块→语句的映射，然后按 CFG 可达性顺序（从入口块开始的 BFS/DFS 顺序）输出。**

或者更简单：**Phase 3 的"剩余块"应该包含所有块，按 CFG 遍历顺序输出，控制结构在其 branch 块的位置插入。**

## 10. 外部引擎交叉分析建议

### 10.1 FOX 不擅长的部分

基于批量反编译结果，FOX 当前不擅长：

1. **巨型 switch / 间接跳转函数** — 0x405800(292blk), 0x4334E0(821blk) 完全无法反编译
2. **循环恢复** — 无 loop detection，循环区域全部变成 UNKNOWN + goto
3. **变量/类型/参数恢复** — 全部是 SSA 占位变量名，无类型，无参数
4. **表达式简化** — Phi 嵌套爆炸，无公共子表达式消除
5. **输出顺序** — 不按 CFG 执行顺序

### 10.2 建议引入外部引擎的时机

| 外部引擎 | 擅长 | 建议引入时机 | 用途 |
|---|---|---|---|
| **Ghidra** | Variable Recovery, Type Recovery, Decompiler, Switch Recovery | **现在** | 交叉验证 FOX 的 Function Discovery / CFG；补充 Variable/Type；处理 FOX 无法反编译的巨型函数 |
| **rev.ng** | 二进制 lifting, 精确 CFG, 间接跳转 | P0-6.10 | 处理 0x405800/0x4334E0 这类间接跳转密集函数 |
| **RetDec** | 轻量级反编译, 函数签名 | P0-7 | 快速函数签名恢复，交叉验证 |

### 10.3 交叉分析架构建议

```
NtcMach.exe
    │
    ├── FOX Analysis (已封板)
    │   ├── Function Discovery (359 functions)
    │   ├── CFG / SSA / Memory SSA
    │   ├── Expression / Condition / Control Structure
    │   └── Structured IR → C-like Pseudocode (94.4% OK)
    │
    ├── Ghidra (建议引入)
```

## 11. 下一步建议

### 立即执行（P0-6.8）

**修复输出顺序错乱。** 这是最影响人工阅读的问题，修复后所有函数的伪 C 立即变得可读。

修复方案：Structured IR Builder 改为按 CFG 入口块开始的 BFS 顺序输出，控制结构在其 branch 块位置插入。

### 紧接着（P0-6.9）

**表达式爆炸修复。** 增加 Expression 输出截断 + Phi elision + 全函数表达式节点预算。

### 然后（P0-6.10）

**0x405800 / 0x4334E0 专项审计。** 确定 SSA 构造失败的根因，决定是修复 FOX 还是直接用 Ghidra/rev.ng 处理。

### 并行（外部引擎）

**引入 Ghidra 做交叉分析。** 用 Ghidra 反编译 NtcMach，与 FOX 输出对比，补充 Variable/Type，处理 FOX 无法反编译的函数。

## 12. 总结

FOX 已经从"分析器"跨越到"能产生伪 C 的反编译器"：

- **94.4% 的函数可以产生可读伪 C**
- **0 崩溃 / 0 OOM**（54秒处理 359 函数）

- **调用覆盖：** 69.1% 函数含 call
- **返回覆盖：** 59.3% 函数含 return

但距离"把 NtcMach 项目搞出来"还有明确的差距：

1. 输出顺序不对（P0）
2. 表达式爆炸（P0）

4. 近一半函数含 UNKNOWN 控制流（P1）

**FOX 的事实/证据层已经足够扎实，下一步应该：修复输出顺序 + 表达式爆炸，然后引入 Ghidra 做交叉分析和 Variable/Type 补充，而不是继续在 FOX 内部从零建设 Variable Recovery。**
