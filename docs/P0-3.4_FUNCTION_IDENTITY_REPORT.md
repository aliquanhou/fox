## 2. 核心突破一：Address-Taken Function Discovery

### 2.1 发现的问题

09_function_pointer_O2 的 gt_apply 函数无法被发现。反汇编揭示：

```asm
gt_dispatch:
  lea rax, [0x140002A3B]    ; 加载 thunk 地址（gt_add）
  mov [rsp+0x20], rax        ; 存入函数指针表
  lea rax, [0x1400012F8]    ; gt_sub thunk
  mov [rsp+0x28], rax
  lea rax, [0x1400012AD]    ; gt_mul thunk
  mov [rsp+0x30], rax
  ...
  mov rcx, [rsp+rcx*8+0x20]  ; 从表加载函数指针
  jmp 0x140001294             ; tail call gt_apply (thunk)
```

函数地址通过 `lea reg, [rip+disp]` 加载，存入栈上的函数指针表，然后间接调用。FOX 当前不扫描 LEA 中的可执行地址。

### 2.2 实现

新增 `FunctionDiscovery::discover_address_taken_functions()`（Phase 3.5）：

1. **LEA 扫描**：遍历所有可执行 section，识别 `lea reg, [rip+disp]`，若 effective address 指向可执行 section，则标记为 address-taken candidate
2. **数据段扫描**：遍历只读数据段（.rdata 等），扫描 8 字节指针，若指向可执行 section，则标记为 address-taken candidate
3. **Evidence**：`AddressTaken` (weight 0.4-0.55，取决于引用次数)
4. **多次引用加权**：被引用 ≥2 次的地址获得更高权重

### 2.3 新增 EvidenceKind

- `EvidenceKind::AddressTaken` — 函数地址被引用（LEA 或数据指针）

## 3. 核心突破二：Tail-Call Thunk Following

### 3.1 发现的问题

即使有了 Address-Taken Discovery，gt_apply 仍然缺失。原因：gt_dispatch 内部的 tail call `jmp 0x140001294`（gt_apply thunk）没有被跟随。当前 thunk following 只检查函数**首指令**是否为 JMP，不扫描函数体内的 JMP。

### 3.2 实现

修改 `follow_thunks()`：
- 在开始时，遍历所有已发现函数的前 512 字节指令
- 收集所有无条件 JMP 的 target
- 将这些 target 加入 to_follow 列表
- 现有的 thunk 解析逻辑会自动跟随 JMP 链

## 4. 核心突破三：Function Identity Model

### 4.1 架构

新建 `crates/fox-core/src/identity.rs`：

```
FunctionIdentityTable
├── BinaryFunctionIdentity (keyed by address)
│   ├── kind: Canonical / Thunk / Folded / Alias / Unknown
│   ├── thunk_target: Option<u64>
│   ├── source_symbols: Vec<String>  (ICF: multiple source → one binary)
│   ├── thunk_addresses: Vec<u64>    (thunks pointing here)
│   ├── address_taken: bool
│   └── call_reference_count: usize
├── SourceFunctionIdentity (keyed by name)
│   ├── binary_address: Option<u64>  (None = inlined/removed)
│   ├── inlined: bool
│   ├── removed: bool
│   └── folded_with: Vec<String>
└── relations: Vec<IdentityRelation>
    ├── ThunkRedirect { from, to }
    ├── IcfFold { from, to, binary_address }
    └── Alias { from, to }
```

### 4.2 集成

`analyze_binary()` 现在构建 `FunctionIdentityTable`：
- 自动识别 thunk（首指令为 JMP）并记录 ThunkRedirect 关系
- 记录 address-taken 状态
- 对命名函数（非 sub_*）记录 SourceFunctionIdentity
- ICF 检测：多个 source symbol 映射到同一 binary address

### 4.3 AnalysisResult 新增字段

```rust
pub struct AnalysisResult {
    pub functions: Vec<WithEvidence<Function>>,
    pub cfg: ControlFlowGraph,
    pub call_graph: CallGraph,
    pub identity_table: FunctionIdentityTable,  // NEW
```

## 5. 核心突破四：Indirect Call 分类增强

### 5.1 新增 IndirectCallKind

```rust
pub enum IndirectCallKind {
    Register,        // call rax
    Memory,          // call [rax] / call [rsp+0x20]
    VtableCandidate, // call [reg+disp] (object + vtable offset)
    Iat,             // call [rip+disp] → IAT
    Unknown,
}
```

### 5.2 CallGraphEdge 新增字段

```rust
pub struct CallGraphEdge {
    // ... existing fields
    pub indirect_kind: Option<IndirectCallKind>,  // NEW
}
```

### 5.3 分类逻辑

- `call rax` → Register
- `call [rax]` → Memory
- `call [rsp+0x20]` → Memory
- `call [rcx+0x18]` → VtableCandidate
- `call [rip+disp]` → IAT（若命中 IAT）或 Memory
- 其他 → Unknown

### 6.3 Precision 双口径说明

当前 Precision=41.94% 是 **GT-relative Precision**：
- 分母 = FOX 发现的所有函数（~4260）
- 分子 = 与 Ground Truth 匹配的函数（~26）
- Ground Truth 只包含 2-5 个 gt_* 函数，二进制实际有 ~4200 个真实函数（CRT/runtime）

**Binary-wide Precision**（FOX 发现的函数中有多少是真实函数）需要更完整的 Ground Truth 才能测量。当前 FOX 发现的 ~4260 个函数中，绝大多数是 CRT/runtime 真实函数，不是误报。

## 10. 已知限制

1. **ICF 检测当前基于命名函数**：完整的 ICF 检测需要 PDB 或 linker map 中的 source symbol 信息。当前只对非 sub_* 命名函数建立 SourceIdentity。
2. **Binary-wide Precision 无法精确测量**：需要包含所有应用函数（不仅 gt_*）的完整 Ground Truth。
3. **Vtable 检测是启发式的**：`call [reg+disp]` 被标记为 VtableCandidate，但不验证是否真的是 vtable。
4. **Address-Taken 扫描有 FP 风险**：LEA 加载的可执行地址可能是代码标签（basic block target）而非函数入口。当前通过 Evidence 权重控制，不直接产生 Confirmed。
