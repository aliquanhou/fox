## 3. 审计发现

### 3.1 问题 1（P1）：IfElse common-successor 直接后继过窄

**代码位置:** `find_common_successor()` line 249-262

**当前实现:**
```rust
fn find_common_successor(cfg, a, b) -> Option<usize> {
    let a_succs = cfg.blocks[a].successors.iter()
        .filter_map(|e| e.target_block).collect();
    let b_succs = cfg.blocks[b].successors.iter()
        .filter_map(|e| e.target_block).collect();
    a_succs.intersection(&b_succs).next().copied()
}
```

只检查 T 和 F 的**直接后继**交集。

**问题:** 对于多 block if/else：
```
       B
      / \
     T   F
     |   |
     T1  F1
      \ /
       M  (真正的 merge)
```
`successors(T) = {T1}`, `successors(F) = {F1}`, 交集 = ∅ → 返回 None → 进入 GuardClause 检测或 Unknown。

**NtcMach 实证:**
- 148 个 Unknown 分支中，**全部 148 个（100%）** 在 8 步传递可达范围内存在共同 merge block。
- 这意味着当前所有 Unknown 实际上都是多 block if/else，被直接后继检测漏检。
- 示例：`func@0x42AE70 branch@0x42B02E`: true=block[246], false=block[17], transitive_merge=block[18]

**影响:** IfElse 召回率被人为压低（1317 vs 实际应更多），多 block if/else 被错误降级为 GuardClause 或 Unknown。

**严重度:** P1（架构性缺陷，影响召回率和分类正确性）

### 3.2 问题 2（P0）：GuardClause shortest-return-distance 大规模误报

**代码位置:** `detect_guard_clause()` line 274-297, `shortest_return_distance()` line 303+

**当前实现:**
```rust
let true_dist = shortest_return_distance(cfg, true_target, 15);
let false_dist = shortest_return_distance(cfg, false_target, 15);

match (true_dist, false_dist) {
    (Some(t), Some(f)) if t < f => GuardClause(return=true_path),
    (Some(t), Some(f)) if f < t => GuardClause(return=false_path),
    (Some(_), Some(_)) => GuardClause(return=true_path), // tiebreaker
    (Some(_), None) => GuardClause(return=true_path),
    (None, Some(_)) => GuardClause(return=false_path),
    _ => None,
}
```

**核心缺陷:** 只要两个分支都能到达 Return（在 MAX_DEPTH=15 内），且距离不同，就分类为 GuardClause。但在一个正常函数中，**几乎所有路径最终都会到达 Return**——这是函数的正常行为，不是 guard clause。

**真正的 GuardClause 应该是:** 一个分支在极短路径内（通常 1-2 个 block）直接 return，而另一个分支继续执行较长的正常逻辑。当前实现没有设置"显著差异"阈值。

**NtcMach 实证:**
- 3754 个 GuardClause 中，**3346 个（89.1%）** 的 body_block 也能在 10 步内到达 Return。
- 2459 个（65.5%）的 body_block 能到达 return_block（交叉可达性）。
- 这意味着绝大多数 "GuardClause" 实际上是普通 if/else，两个分支都继续执行并最终 return，只是返回路径长度不同。

**反例模式（普通 if/else 被误判为 GuardClause）:**
```
       B
      / \
     T   F
     |   |
    ...  ... (不同长度的正常逻辑)
     |   |
    ret  ret
```
T 路径 3 步到 return，F 路径 5 步到 return → 被分类为 GuardClause(return=T)。但这实际上是一个正常的 if/else，两个分支都是函数的正常执行路径。

**严重度:** P0（大规模误报，72% 分支被错误分类为 GuardClause，其中 89% 是误报）

### 3.3 问题 3（P1）：equal-distance tiebreaker 语义过度声明

**代码位置:** `detect_guard_clause()` line 287-292

**当前实现:**
```rust
// Equal distance: both paths reach return.
(Some(_), Some(_)) => Some((false_target, true_target, true)),
```

当两个分支返回距离相等时，默认 taken (ConditionalTrue) 分支为 early-return。

**问题:**
1. 机器码本身没有告诉我们哪个分支是 "error/guard"。两个分支等距返回，可能是：
   - 正常 if/else 两分支都 return（如 `if (x) return a; else return b;`）
   - 也可能是 guard clause，但无法从 CFG 距离判断
2. 报告将此描述为 "convention-based tiebreaker, not a guess about semantics"，但实际上 `return_is_taken_branch=true` 就是一个语义声明——它声称 taken 分支是 early-return 路径。
3. 当两个分支等距返回时，更诚实的分类应该是 **IfElse（如果有 transitive merge）** 或 **Unknown（如果无法确定结构）**，而不是强行标注为 GuardClause。

**NtcMach 实证 — 0x41F000 第二个 GuardClause:**
- branch @ 0x41F020 (jz)
- true (taken) → block[3] (error block, 有 Return 边) → distance = 0
- false (fallthrough) → block[2] (indirect call + ret, 有 Return 边) → distance = 0
- **两个分支距离都是 0，完全依赖 tiebreaker 分类为 GuardClause**
- 实际上这是一个 `if (result == 0) goto error; else return callback(arg);` 的模式，两个分支都直接 return。分类为 GuardClause 可以接受，但 "return_is_taken_branch=true" 的语义声明缺乏证据支撑——两个分支都是 return，无法从 CFG 判断哪个是 "guard"。

**严重度:** P1（语义过度声明，在等距情况下无证据地选择一侧为 early-return）

## 5. 必须修复的问题

### P0-1: GuardClause 误报（必须修复）
**根因:** shortest-return-distance 没有设置"显著差异"阈值，导致普通 if/else（两分支都最终 return）被误判为 GuardClause。

**修复方向（建议，不强制）:**
- GuardClause 应要求 return 路径显著短于 body 路径（例如 return_dist ≤ 2 且 body_dist ≥ return_dist + 3）
- 或者要求 return 路径在 1 个 block 内直接 return（single-block return）
- 不满足显著差异的 → 检查 transitive merge → IfElse 或 Unknown

### P1-1: IfElse 直接后继过窄（必须修复）
**根因:** find_common_successor 只检查直接后继，漏检多 block if/else。

**修复方向（建议，不强制）:**
- 改为 BFS 传递可达 merge 检测（在合理深度内，如 8-10 步）
- 找到第一个两个分支都能到达的 block 作为 merge

### P1-2: tiebreaker 语义过度声明（必须修复）
**根因:** 等距返回时无证据地选择 taken 为 early-return。

**修复方向（建议，不强制）:**
- 等距返回时，如果有 transitive merge → IfElse
- 等距返回且无 merge → Unknown（不强行标注 GuardClause）
- 或者保留 GuardClause 但 `return_is_taken_branch` 标记为 `None` / 不确定
