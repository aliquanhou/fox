## 0. 总裁决

**P0-6.6A = CONDITIONAL PASS**

实现达到了 P0-6.6A 声明的目标（线性+最小结构、Unknown 一等公民、Evidence 可追溯、资源预算 fail-closed），但存在一个 **P1 GAP**：控制结构嵌套只有一层深，46 个 If 全部在顶层，没有真正的递归嵌套。

此 GAP 不阻塞 P0-6.6A 的核心目标（"第一阶段只做线性+最小结构"），但必须在 P0-6.6B（C-like Emitter）之前或同时修复，否则 Emitter 输出的控制流结构将是扁平的，无法正确表达嵌套 if/else。

### 1.2 7种 Statement 语义审计

| Statement | 语义正确性 | 审计结果 |
|---|---|---|
| `Assign` | 来自 SSA definition + Expression Recovery，lhs 来自 destination_operand_idx | ✅ 正确 |
| `If` | 来自 ControlStructure::IfElse，then/else body 包含对应块的语句 | ⚠️ body 只有扁平语句，无嵌套控制结构 |
| `GuardClause` | 来自 ControlStructure::GuardClause，body 包含 continuation 块语句，return_value 来自 return 块 | ✅ 正确表达 early-return |
| `Return` | 来自 CFG Return edge，value 来自 recover_return_value | ✅ 正确 |
| `CallStmt` | 来自 SSA Call 指令，arguments_unresolved=true 硬编码 | ✅ 不偷偷恢复参数 |
| `Unknown` | 来自 ControlStructure::Unknown，保留 reason + goto_target | ✅ fail-closed，不编造 if |
| `PhiAssign` | 来自 SSA Phi node，标记为 SSAPlaceholder | ✅ 不伪装成恢复变量 |

### 1.3 三阶段构建算法审计

**Phase 1: 线性语句构建（按 CFG 块）**
- 遍历每个 CFG 块对应的 SSA 块
- Phi → PhiAssign，Call → CallStmt，有 destination 的指令 → Assign
- CFG Return edge → Return
- 结果存入 `block_statements: HashMap<block_id, Vec<Statement>>`

✅ 正确

**Phase 2: 控制流结构提升**
- 遍历 `Vec<ControlStructure>`
- IfElse → `take_block_statements(then_block)` + `take_block_statements(else_block)` → Statement::If
- GuardClause → `take_block_statements(body_block)` + `extract_return_from_block(return_block)` → Statement::GuardClause
- Unknown → Statement::Unknown（reason + goto_target）
- 已处理块标记为 `processed_blocks`

⚠️ **关键发现：`take_block_statements` 使用 `HashMap::remove()`，确保块只被消费一次。但嵌套只有一层深——如果 then_block 本身包含另一个 If，那个内层 If 在 Phase 2 中被提升到 top_level，而不是嵌套在外层 If 的 then_body 内。**

**Phase 3: 剩余块语句补充**
- 按地址顺序遍历未 processed 的 CFG 块
- 将其语句添加到 top_level

✅ 正确

### 1.4 资源预算审计

```rust
fn allocate(&mut self) -> bool {
    if self.current_statements >= self.max_statements {
        self.exhausted = true;
        return false;
    }
    self.current_statements += 1;
    true;
}
```

- `allocate()` 在**每个** Statement 生成前调用（PhiAssign/CallStmt/Assign/Return/If/Guard/Unknown）
- 共享计数器跨所有 Phase
- `is_exhausted()` 在循环边界检查
- 预算耗尽 → 优雅停止，不 panic，不 OOM

✅ **真正的 fail-closed，不是只限制 Vec 大小**

实测验证：
- `max_statements=10` + 0x401390 → 0 statements, budget_exhausted=true
- `max_statements=5000`（默认）+ 0x401390 → 204 statements, budget_exhausted=false

### 2.3 关键发现：Max Nesting Depth = 1

**所有 46 个 If 和 13 个 GuardClause 都在 top_level，没有任何一个嵌套在另一个 If/Guard 的 body 内。**

原因：Phase 2 按顺序处理 ControlStructure 列表。当处理 If1 时，`take_block_statements(then_block)` 只取出 then_block 的**扁平语句**（Assign/Call/Return/Phi）。如果 then_block 包含一个条件跳转形成 If2，If2 在后续迭代中被提升到 top_level，而不是嵌套在 If1.then_body 内。

**影响：**
- 对于单层控制流的函数，输出正确
- 对于嵌套控制流的函数（如 0x401390），输出是扁平的控制结构列表，不能正确表达 `if (A) { if (B) { ... } }` 的嵌套关系
- P0-6.6B C-like Emitter 如果直接消费这个 IR，输出的 if/else 将没有正确的嵌套缩进和作用域

### 2.4 6 个 If 两个 body 都为空

审计发现 6 个 If 的 then_body 和 else_body 都为空。

**根因分析：** 这些 If 的 then_block 或 else_block 只包含条件跳转指令（CondJump），而 CondJump 没有 destination_operand_idx（不产生 Assign），也不是 Call/Return/Phi。因此这些块的扁平语句为空。

这些块的条件跳转本身形成了其他控制结构（If/Guard/Unknown），被提升到 top_level。

**这不是 Bug，是嵌套缺失的表现。** 在真正嵌套的模型中，这些内层控制结构应该出现在外层 If 的 body 内。

### 2.5 Block 覆盖率

- 114 个 CFG 块中，85 个被 statements 引用
- 29 个未被引用：可能是 merge 块、branch 块（只含跳转）、或语句为空的块

⚠️ **需要关注：** 29/114 = 25% 的块未出现在输出中。虽然这些块可能不产生语句（只含跳转），但对于 Emitter 来说，merge 块的语句应该出现在 if/else 之后。当前 Phase 3 只添加未 processed 的块，但 merge 块没有被标记为 processed，所以 merge 块的语句应该会被添加。需要进一步验证。

## 6. 核心判断：真正嵌套结构 vs 扁平包装

### 问题

> Structured IR 是真正的第一代 Decompiler IR，还是只是把已有结果包装了一层？

### 判断

**介于两者之间，但更接近"真正的 IR"。**

**它做到了：**
1. 统一了 7 种 Statement 类型，不再是各自独立的分析结果
2. If/GuardClause 的 body 包含对应块的语句（Assign/Call/Return/Phi），不是空壳
3. Unknown 是一等公民，保留 reason 和 goto_target
4. 每个 Statement 有 Evidence，可追溯到指令地址
5. 资源预算 fail-closed
6. 纯 Consumer，不修改已封板模块

**它没做到：**
1. **控制结构没有递归嵌套** — 所有 If/Guard 在顶层，body 内只有扁平语句
2. 这意味着对于嵌套控制流的函数，IR 不能正确表达程序结构
3. 6 个 If 两个 body 都为空，正是因为内层控制结构被"提升"到了顶层

### 结论

对于 P0-6.6A 声明的目标（"第一阶段只做线性+最小结构"），这个实现是**合格的**。它建立了 Statement 数据模型、Evidence 追溯、资源预算、Unknown fail-closed 等基础设施。

但嵌套缺失是一个**必须在 P0-6.6B 之前修复的 P1 GAP**，否则 C-like Emitter 无法正确输出嵌套 if/else。

## 7. GAP 登记

### P1 GAP-1: 控制结构无递归嵌套

- **现象:** Max nesting depth = 1，所有 If/Guard 在顶层
- **根因:** Phase 2 按顺序处理 ControlStructure，内层控制结构被提升到 top_level 而非嵌套
- **影响:** 嵌套控制流函数的 IR 结构不正确，Emitter 无法正确输出
- **修复方向:** Phase 2 应递归处理——如果 then_block/else_block/body_block 包含其他控制结构，应将其嵌套在 body 内，而非提升到顶层
- **修复时机:** P0-6.6B 之前或同时

### P2 GAP-2: 6 个 If 两个 body 都为空

- **现象:** 6 个 If 的 then_body 和 else_body 都为空
- **根因:** 这些块只含条件跳转，扁平语句为空；内层控制结构被提升到顶层
- **影响:** 与 P1 GAP-1 同源，修复嵌套后此问题自动解决
- **修复时机:** 随 P1 GAP-1 一起修复

### P2 GAP-3: 29/114 块未被引用

- **现象:** 0x401390 有 25% 的 CFG 块未出现在 statements 中
- **根因:** 可能是只含跳转的块、merge 块、或语句为空的块
- **影响:** 需要验证 merge 块的语句是否正确出现在 if/else 之后
- **修复时机:** P0-6.6B Emitter 阶段验证

### Non-GAP: PhiAssign 数量较多 (78/204)

- 0x401390 有 78 个 PhiAssign，占总语句的 38%
- 这是正常的——大函数有大量 Phi 节点
- Emitter 可以选择 elide PhiAssign（SSA Phi 在高级语言中不直接对应语句）

**不阻塞 P0-6.6A 的核心目标**（"第一阶段只做线性+最小结构"），但阻塞 P0-6.6B 的直接开工。
