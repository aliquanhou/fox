## 1. Executive Summary

P0-5.3A proved that x86 has no universal Strong Evidence equivalent to x64 .pdata. This audit addresses the consequent architectural question: **how should FOX represent function reality when function-start metadata is absent?**

**Core finding**: The current `Function` model collapses three independent uncertainty dimensions (Start, Body, End) into a single scalar `confidence_tier`. This prevents FOX from honestly expressing "Start is certain but End is unknown" — a common situation in x86 commercial binaries.

**Recommended canonical model**: Introduce a **Claim-typed Evidence layer** as a non-breaking extension, where each Evidence carries a `Claim` (what it proves) and a `Subject` (which dimension it addresses). This enables multi-dimensional confidence without breaking the existing single-scalar API. A full `FunctionReality` struct with Start/Body/End sub-confidence is recommended as a **LATER** phase, not now.

**Key decisions**:
- Function Model: KEEP (for now), add Claim layer
- Evidence Model: CHANGE NOW (add Claim type)
- Confidence Model: LATER (multi-dimensional after Claim layer is in place)
- Start/Body/End separation: CHANGE LATER (depends on Claim layer)
- Function Candidate vs Reality: LATER (depends on Claim layer)

## 2. Current Model Audit

### 2.1 Function Data Model

```rust
pub struct Function {
    pub name: String,
    pub address: Address,              // Start address (implicit)
    pub end_address: Option<Address>,  // End address — often None
    pub size: Option<usize>,
    pub basic_blocks: Vec<BasicBlock>,
    pub calls: Vec<u64>,
    pub called_by: Vec<u64>,
    pub confidence_tier: FunctionConfidence,  // SINGLE scalar for entire function
    pub validation: FunctionValidation,       // has estimated_end (separate from end_address)
}
```

**Problems identified**:

| Problem | Detail | Severity |
|---------|--------|----------|
| Start/Body/End merged | `confidence_tier` is one enum for all three dimensions | P1 |
| `end_address` often None | 359 functions in NtcMach.exe, most have no reliable end | P1 |
| Dual end concept | `end_address` and `validation.estimated_end` are separate | P2 |
| No Start certainty | `address` is assumed correct, no confidence on start | P1 |
| No Body certainty | body validity is in `validation`, not in confidence | P2 |
| Identity not embedded | Identity is in separate `FunctionIdentityTable`, keyed by address | P2 |

### 2.2 FunctionConfidence (single scalar)

```rust
pub enum FunctionConfidence {
    Confirmed,   // >= 0.85
    High,        // >= 0.65
    Probable,    // >= 0.40
    Unknown,     // >= 0.15
    Rejected,    // < 0.15
}
```

This enum answers "how confident is FOX that this address is a function?" — but cannot answer:
- "How confident is the start address?"
- "How confident is the body extent?"
- "How confident is the end address?"

### 2.3 Evidence Model

```rust
pub struct Evidence {
    pub kind: EvidenceKind,   // ~40 variants
    pub address: Option<u64>,
    pub detail: Option<String>,
    pub weight: f64,          // single weight, feeds one confidence number
}
```

**Critical gap**: Evidence has **no Claim type**. A `ValidFunctionBody` evidence (weight 0.6) and a `CallReference` evidence (weight 0.7) both feed the same scalar confidence, but they prove fundamentally different things:
- `ValidFunctionBody` proves: "bytes here disassemble to valid instructions + RET" → **Body claim**
- `CallReference` proves: "this address is a CALL target" → **Start candidate claim**
- `PdataEntry` proves: "PE metadata says this is a function start+end" → **Start + End claim**
- `EntryPoint` proves: "PE header says this is entry" → **Start + Identity claim**

### 2.4 Confidence Formula

```
confidence = max_weight + 0.1 × (evidence_count - 1) × (1 - max_weight)
```

This formula:
- Treats all evidence as supporting the SAME claim ("this is a function")
- Cannot distinguish "strong start evidence + weak end evidence" from "weak start + strong end"
- Creates diminishing returns that prevent medium evidence from reaching 0.85 (proven in P0-5.3A)

### 2.5 Identity Model

```rust
pub enum IdentityKind {
    Canonical, Thunk, ImportThunk, Folded, Alias, Unknown,
}

pub struct BinaryFunctionIdentity {
    pub address: u64,
    pub kind: IdentityKind,
    pub thunk_target: Option<u64>,
    pub source_symbols: Vec<String>,
    pub thunk_addresses: Vec<u64>,
    pub address_taken: bool,
    pub call_reference_count: usize,
}
```

Identity is stored in a **separate** `FunctionIdentityTable`, keyed by address. It is NOT embedded in `Function`. This means:
- A `Function` and its `BinaryFunctionIdentity` are linked only by address
- No confidence on identity classification
- Identity and Boundary are decoupled (good), but the connection is implicit (bad)

### 2.6 Negative Evidence

Current negative evidence kinds (only 4):
- `NegativeNonExecutableSection`
- `NegativeInvalidInstructionBoundary`
- `NegativeUnreachable`
- `NegativeDataAddress`

**Missing negative categories**:
- `NotFunctionStart` (address is inside another confirmed function)
- `InternalBasicBlock` (address is a JMP/JCC target within a function)
- `SwitchTarget` (address is a jump table case target)
- `SEHHandler` (address is an exception handler, not normal entry)
- `ImportThunk` (address is an import thunk, not native function)
- `Thunk` (address is an internal thunk)
- `OutlinedCode` (address is compiler-outlined code)
- `CompilerHelper` (address is a compiler helper function)

## 3. Identity vs Boundary Analysis

### 3.1 Entity Taxonomy

Real x86 binaries contain these distinct entity types:

| Entity | Is Function? | Has Boundary? | Identity Kind | Current Model |
|--------|-------------|---------------|---------------|---------------|
| Normal Function | ✅ | ✅ Start+Body+End | Canonical | Function |
| Import Thunk | ❌ (redirect) | ✅ 1 instruction | ImportThunk | Function (misclassified) |
| Internal Thunk | ❌ (redirect) | ✅ 1 instruction | Thunk | Function (misclassified) |
| Tail-Call Target | ✅ | ✅ | Canonical | Function |
| Folded Function (ICF) | ✅ | ✅ | Folded | Function |
| Alias | ✅ | ✅ | Alias | Function |
| SEH Handler | 🟡 (special) | ✅ | (missing) | Function (misclassified) |
| Compiler Helper | ✅ (special) | ✅ | (missing) | Function |
| Outlined Code | 🟡 (part of func) | ✅ | (missing) | Function (misclassified) |
| Internal Basic Block | ❌ | N/A | N/A | Not a function (correct) |
| Switch Target | ❌ | N/A | N/A | Not a function (correct) |
| Unknown Code Region | ❓ | ❓ | Unknown | Function/Rejected |

### 3.2 Key Finding: Identity and Boundary Are Different Questions

- **Identity**: "What IS this address?" (Canonical? Thunk? ImportThunk? Handler?)
- **Boundary**: "Where does this function start/end?"

A function can have:
- Certain Identity (Canonical) + Uncertain End
- Certain Identity (ImportThunk) + Certain Boundary (1 instruction) + NOT a real function
- Uncertain Identity + Certain Start (CALL target) + Uncertain End

Current model cannot express these combinations.

### 3.3 Recommendation: KEEP Identity separate, ADD identity confidence

The current separation of `FunctionIdentityTable` from `Function` is architecturally correct. Identity should remain a separate dimension. But:
- Identity classification should carry its own confidence
- Function should reference its identity (not just implicit by address)
- Identity should NOT be conflated with boundary confidence

## 4. Start / Body / End Analysis

### 4.1 Q1: Can Body=HIGH, Start=PROBABLE, End=UNKNOWN?

**YES — this is common in x86.**

Example from NtcMach.exe: a function discovered via prologue scan:
- Start = Probable (prologue match, weight 0.4)
- Body = High (valid instructions + RET, weight 0.6)
- End = Unknown (no reliable end, `end_address` = None)

Current model forces this into a single `confidence_tier = Probable`, losing the information that Body is actually High.

### 4.2 Q2: Can Start=Confirmed, Body=High, End=Probable?

**YES — x64 with .pdata:**
- Start = Confirmed (.pdata BeginAddress, weight 0.85)
- Body = High (valid disassembly)
- End = Probable (.pdata EndAddress exists but may include padding)

Current model collapses this to `Confirmed` (because .pdata weight 0.85 alone reaches threshold), which is acceptable for x64 but masks End uncertainty.

### 4.3 Q3: Is this a data model GAP or acceptable simplification?

**Architecture judgment: This is a GAP that will become blocking for Decompiler.**

For Function Discovery and CFG, a single confidence is acceptable. But for Decompiler:
- Unknown End → cannot safely decompile (may run into next function)
- Probable Start → decompilation may start at wrong address
- The Decompiler needs to know WHICH dimension is uncertain, not just that the overall confidence is "Probable"

**Decision: CHANGE LATER** — not now, but must be addressed before Decompiler (P1).

## 5. Evidence Claim Analysis

### 5.1 Core Insight: One Evidence, One Claim

An Evidence should answer: "What does this prove, and about what?"

Current model treats all evidence as proving "this is a function" (implicit claim). This is wrong.

### 5.2 Claim Type Taxonomy

| Claim Type | Meaning | Example Evidence |
|------------|---------|-----------------|
| `FunctionStartClaim` | "This address is a function entry" | EntryPoint, Export, Pdata, CALL target |
| `FunctionBodyClaim` | "Bytes from here form valid function body" | ValidFunctionBody, ValidInstructionDecoded |
| `FunctionEndClaim` | "Function ends here" | Pdata EndAddress, RET, FunctionEpilogue |
| `IdentityClaim` | "This address has identity X" | ImportThunk pattern, Thunk pattern |
| `ReachabilityClaim` | "This address is reachable from Y" | ReachableFromEntry, CallReference |
| `ControlFlowClaim` | "This is a CFG edge/BB" | BranchTarget, FallthroughEdge |
| `NegativeClaim` | "This is NOT a function/start/body" | NegativeNonExecutableSection, etc. |

### 5.3 Critical Question: Can one Evidence support one Claim but not another?

**YES.** This is the key architectural boundary.

| Evidence | Supports Start? | Supports Body? | Supports End? | Supports Identity? |
|----------|----------------|----------------|---------------|-------------------|
| EntryPoint | ✅ STRONG | ❌ | ❌ | ✅ (entry identity) |
| ExportEntry | ✅ STRONG | ❌ | ❌ | ✅ (export identity) |
| PdataEntry | ✅ STRONG | 🟡 | ✅ STRONG | ❌ |
| CALL Target | ✅ MEDIUM | ❌ | ❌ | ❌ |
| ValidFunctionBody | ❌ | ✅ MEDIUM | ❌ | ❌ |
| RET | ❌ | 🟡 | ✅ WEAK | ❌ |
| FunctionPrologue | ✅ WEAK | 🟡 | ❌ | ❌ |
| ImportThunk pattern | ❌ | ❌ | ❌ | ✅ (ImportThunk identity) |
| SEH registration | ✅ MEDIUM | ❌ | ❌ | ✅ (SEH region) |
| AddressTaken | 🟡 | ❌ | ❌ | ❌ |
| ReachableFromEntry | 🟡 (if CALL) | ❌ | ❌ | ❌ |

**Example**: `ValidFunctionBody` (weight 0.6) proves Body but NOT Start. Currently it contributes to the same confidence as `CallReference` (weight 0.7), which proves Start. This means a function with only ValidFunctionBody (no CALL target, no prologue) gets confidence 0.6 → High, even though its Start is completely unproven.

### 5.4 Decision: CHANGE NOW — Add Claim Type to Evidence

This is a non-breaking extension:
- Add `claim: Option<EvidenceClaim>` field to `Evidence`
- Default to `None` (backward compatible)
- Existing code continues to work
- New code can set Claim and use it for multi-dimensional confidence
- This is the foundation for all future Start/Body/End separation

## 7. Negative Evidence Analysis

### 7.1 Current Coverage

Only 4 negative evidence kinds exist. This is insufficient for x86 reality.

### 7.2 Required Negative Claims

| Negative Claim | Meaning | Current Status |
|----------------|---------|----------------|
| `NotFunctionStart` | Address is inside another confirmed function | ❌ Missing |
| `InternalBasicBlock` | Address is a JMP/JCC target within a function | ❌ Missing |
| `SwitchTarget` | Address is a jump table case target | ❌ Missing |
| `SEHHandler` | Address is an exception handler entry | ❌ Missing |
| `ImportThunkIdentity` | Address is an import thunk (not native func) | ✅ (identity, not negative) |
| `ThunkIdentity` | Address is an internal thunk | ✅ (identity, not negative) |
| `OutlinedCode` | Address is compiler-outlined code region | ❌ Missing |
| `CompilerHelper` | Address is a compiler-generated helper | ❌ Missing |
| `NonExecutableSection` | Address in non-executable section | ✅ |
| `InvalidInstructionBoundary` | Address doesn't start valid instruction | ✅ |
| `Unreachable` | No path from entry | ✅ |
| `DataAddress` | Address identified as data | ✅ |

### 7.3 Positive / Negative / Unknown Triad

Current model is binary: evidence exists → positive; no evidence → no contribution. Negative evidence exists but is underused.

A proper Function Reality model needs:
- **Positive Evidence**: supports a claim
- **Negative Evidence**: refutes a claim
- **Unknown**: no evidence either way (not "low confidence", but "no information")

This is especially important for x86: "no .pdata" is Unknown (not Negative), "address is inside another function" is Negative.

## 8. Confidence Model Analysis

### 8.1 Current: Single Scalar

`confidence ∈ [0,1]`, mapped to 5 tiers.

### 8.2 Required: Multi-Dimensional

A function in x86 commercial binary often has:
```
start_confidence = 0.72    (CALL target + prologue)
body_confidence  = 0.85    (valid body + RET)
end_confidence   = 0.35    (no reliable end)
identity_confidence = 0.90 (Canonical, confirmed by CALL)
```

Current model collapses this to ~0.76 → High, losing all dimensional information.

### 8.3 Architecture Decision

**CHANGE LATER** — multi-dimensional confidence depends on the Claim layer being in place first.

Implementation sequence:
1. **NOW (P0-5.4 recommendation)**: Add Claim type to Evidence (non-breaking)
2. **NEXT (P0-5.5?)**: Add `FunctionReality` with per-dimension confidence, using Claim-typed evidence
3. **LATER**: Migrate CLI/JSON to expose multi-dimensional confidence
4. **FINAL**: Deprecate single `confidence_tier` (keep as derived aggregate)

## 9. x86 vs x64 Unified Model

### 9.1 Principle

Evidence sources differ by architecture, but the Reality Model must be unified.

```
                    Function Reality Model
                   (Start / Body / End / Identity)
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
         x64 Evidence             x86 Evidence
         ├── .pdata (S)           ├── CALL target (M)
         ├── Entry (S)            ├── Entry (S)
         ├── Export (S)           ├── Export (S)
         ├── Prologue (W)         ├── Prologue (W)
         └── ...                  ├── SEH (M, rare)
                                  ├── ValidBody (M)
                                  └── ...
```

### 9.2 Decision: KEEP unified model, architecture-specific evidence

The `Function` / `FunctionReality` model must be architecture-agnostic. Evidence sources are architecture-specific. This is already the case (`.pdata` is x64-only, applied conditionally). The Claim layer makes this cleaner: x64 has Strong Start+End claims, x86 has Medium Start + Medium Body + Weak End claims, but both feed the same Reality model.

## 10. NtcMach.exe Dogfood Analysis

### 10.1 Entity Distribution

| Entity Type | Count | Current FOX Classification |
|-------------|-------|---------------------------|
| Normal functions (Canonical) | ~200-250 | Function (High/Probable) |
| Import thunks | ~110 | Function (High) — identity=ImportThunk |
| Internal thunks | ~23 | Function (High/Probable) |
| Entry point | 1 | Function (Confirmed) |
| SEH handler | 1 | Function (Probable?) |
| Internal Basic Blocks | 1179+ | Not functions (correct) |
| Indirect call sites | 2190 | N/A (call sites, not functions) |
| Indirect JMP sites | 154 | N/A |

### 10.2 How Current Model Fails

1. **Import thunks appear as High-confidence Functions** — they have valid bodies (1 instruction) and CALL references, but they're not real functions. Identity=ImportThunk is set in the separate table, but `confidence_tier` still says High.
2. **End address is None for most functions** — `end_address` is not reliably set, so `size` is None.
3. **Single confidence masks dimensional uncertainty** — a function with Confirmed Start (entry) but Unknown End is just "Confirmed".
4. **No negative evidence for internal BBs** — the 1179 internal BBs are not functions, but there's no `InternalBasicBlock` negative evidence recorded for them.

### 10.3 What the Model Should Express

For NtcMach.exe, the ideal output would be:
```
Function @ 0x408F50:
  Identity: Canonical (confidence 0.90)
  Start: High (CALL target + valid prologue)
  Body: High (valid instructions + RET)
  End: Probable (linear sweep estimate, no .pdata)
  Positive Evidence: [CallReference, ValidFunctionBody, Prologue]
  Negative Evidence: []
  Unknown: [End exact boundary]

ImportThunk @ 0x455E40:
  Identity: ImportThunk (confidence 0.95, IAT-proven)
  Start: Confirmed (identity implies start)
  Body: Confirmed (1 instruction: jmp [IAT])
  End: Confirmed (1 instruction)
  IsNativeFunction: false
  RedirectsTo: MSVCRT.dll!xxx
```

## 11. Architecture Alternatives

### Architecture A: Keep Current Model

```
Function { address, end_address, confidence_tier, evidence, blocks }
```

- **Expressiveness**: ❌ Cannot express Start/Body/End uncertainty separately
- **Backward Compat**: ✅ No changes
- **Implementation Cost**: ✅ Zero
- **Evidence Traceability**: 🟡 Evidence exists but no Claim type
- **CLI Compat**: ✅
- **Decompiler Readiness**: ❌ Decompiler cannot know which dimension is uncertain
- **Future AI**: ❌ AI cannot reason about dimensional uncertainty

**Verdict**: REJECT for long-term. Acceptable as interim.

### Architecture B: Full FunctionReality with Sub-Reality

```
FunctionReality {
    identity: IdentityReality,
    start: BoundaryReality,    // {status, confidence, evidence}
    body: BodyReality,         // {status, confidence, evidence}
    end: BoundaryReality,      // {status, confidence, evidence}
    positive_evidence: Vec<Evidence>,
    negative_evidence: Vec<Evidence>,
    cfg: CFG,
}
```

- **Expressiveness**: ✅ Full dimensional uncertainty
- **Backward Compat**: ❌ Breaking change to Function struct
- **Implementation Cost**: ❌ High (migrate all consumers)
- **Evidence Traceability**: ✅ Per-dimension evidence
- **CLI Compat**: ❌ Requires CLI rewrite
- **Decompiler Readiness**: ✅
- **Future AI**: ✅

**Verdict**: TARGET architecture, but too large for now. Should be implemented incrementally.

### Architecture C: Claim-typed Evidence + Optional Multi-Dim Confidence (RECOMMENDED)

```
// Non-breaking extension to existing model
Evidence {
    kind: EvidenceKind,
    claim: Option<EvidenceClaim>,  // NEW: what this proves
    subject: Option<EvidenceSubject>, // NEW: Start/Body/End/Identity
    weight: f64,
    address: Option<u64>,
    detail: Option<String>,
}

// Function gets optional fields (non-breaking)
Function {
    // ... existing fields ...
    reality: Option<FunctionReality>,  // NEW: populated when available
}

FunctionReality {
    start_confidence: Option<Confidence>,
    body_confidence: Option<Confidence>,
    end_confidence: Option<Confidence>,
    identity_confidence: Option<Confidence>,
}
```

- **Expressiveness**: 🟡 Full when `reality` is populated, falls back to scalar when not
- **Backward Compat**: ✅ All new fields are Option
- **Implementation Cost**: 🟡 Medium (add Claim to Evidence, populate reality incrementally)
- **Evidence Traceability**: ✅ Claim-typed evidence
- **CLI Compat**: ✅ Old CLI ignores new fields; new CLI can show them
- **Decompiler Readiness**: 🟡 Partial (reality is optional)
- **Future AI**: ✅ Claim-typed evidence is AI-friendly

**Verdict**: RECOMMENDED as first step. Enables Architecture B incrementally without breaking changes.

## 13. Recommended Canonical Model

```
Binary
  ↓
Code Region (executable section range)
  ↓
Function Candidate (address + initial evidence)
  ↓
Function Reality
  ├── Identity (Canonical/Thunk/ImportThunk/Folded/Alias/Unknown + confidence)
  ├── Start (status + confidence + evidence)
  ├── Body (status + confidence + evidence)
  ├── End (status + confidence + evidence)
  ├── Positive Evidence (Claim-typed)
  ├── Negative Evidence (Claim-typed)
  └── Aggregate Confidence (derived, for backward compat)
  ↓
CFG (uses Start/Body to determine BB scope)
  ↓
IR
  ↓
SSA (Register + Memory)
  ↓
DataFlow
  ↓
Decompiler (checks Start/Body/End certainty before decompiling)
```

**Implementation phases**:
1. **P0-5.4 (this audit)**: Design only
2. **P0-5.5 (next)**: Add Claim type to Evidence (non-breaking)
3. **P0-5.6**: Add FunctionReality optional struct, populate Start/Body/End from Claim-typed evidence
4. **P0-5.7**: Migrate CLI/JSON to expose multi-dimensional confidence
5. **P0-6+**: Decompiler uses dimensional confidence

## 15. Decompiler Implications

### 15.1 What Decompiler Needs

- **Start certainty**: Must be High or Confirmed to begin decompilation
- **Body certainty**: Must be at least Probable (valid instructions)
- **End certainty**: Unknown End → decompile with caution (may overlap next function)
- **Identity certainty**: ImportThunk → don't decompile as native function

### 15.2 Recommended Decompiler Gate

```
CanDecompile = 
  Start >= High 
  AND Body >= Probable 
  AND Identity != ImportThunk 
  AND Identity != Thunk
```

Functions with Unknown End can still decompile but must mark output as "partial / boundary uncertain".

## 16. Implementation Boundary

This audit recommends **NO production code changes now**.

If approved, the next implementation phase (P0-5.5) should:
1. Add `EvidenceClaim` enum and `claim: Option<EvidenceClaim>` to `Evidence`
2. Add `EvidenceSubject` enum (Start/Body/End/Identity/Reachability/ControlFlow/Negative)
3. Update existing evidence producers to set Claim (non-breaking — default None)
4. Add `FunctionReality` struct with optional per-dimension confidence
5. Add `reality: Option<FunctionReality>` to `Function`
6. Populate `reality` from Claim-typed evidence in FunctionDiscovery
7. Add CLI/JSON support for reality output

**NOT in P0-5.5**:
- Remove `confidence_tier`
- Change confidence formula
- Remove `end_address`
- Change FunctionDiscovery algorithm
- Add new evidence sources
