## 1. 修复的问题

### P0-1: GuardClause shortest-return-distance 大规模误报

**根因:** `detect_guard_clause()` 使用 BFS 最短返回路径距离比较。只要两个分支都能在 MAX_DEPTH=15 内到达 Return，且距离不同，就分类为 GuardClause。但在正常函数中，几乎所有路径最终都会到达 Return——这是函数的正常行为，不是 guard clause。

**NtcMach 实证（修复前）:**
- 5219 个条件分支中 3754 个（72%）被分类为 GuardClause
- 其中 3346 个（89%）的 body_block 也能在 10 步内到达 Return
- 2459 个（66%）的 body_block 能到达 return_block（交叉可达）

**修复:** 改为证据优先的 `is_immediate_return_path()`：
- 只有 branch target block **自身**在 CFG 中有 Return 边，才算 immediate return path
- GuardClause 条件：一侧 immediate return **且** 另一侧**不是** immediate return
- 双 return（两侧都 immediate return）→ 不分类为 GuardClause

```rust
fn is_immediate_return_path(cfg, start) -> bool {
    cfg.blocks[start].successors.iter()
        .any(|e| e.kind == EdgeKind::Return)
}
```

### P1-1: IfElse common-successor 直接后继过窄

**根因:** `find_common_successor()` 只检查 T 和 F 的**直接后继**交集。对于多 block if/else（T→T1→M, F→F1→M），直接后继没有交集，返回 None。

**NtcMach 实证（修复前）:** 148 个 Unknown 中 100% 在 8 步传递可达范围内存在共同 merge block。

**修复:** 替换为 `find_bounded_common_merge()`：
- BFS 从 T 和 F 出发，在深度 8 内找第一个共同可达块
- Loop/back-edge 排除：candidate merge 的 start_address 必须 >= branch_block 的 start_address
- 排除 T 和 F 自身作为 merge

### P1-2: equal-distance tiebreaker 语义过度声明

**根因:** 当两个分支返回距离相等时，默认 taken (ConditionalTrue) 分支为 early-return。但机器码本身没有告诉我们哪个分支是 "error/guard"。

**修复:** 完全删除 tiebreaker。双 return（两侧都 immediate return）→ Unknown。
- `detect_guard_clause()` 现在只在 `(true, false)` 或 `(false, true)` 时返回 Some
- `(true, true)` 和 `(false, false)` 都返回 None → 进入 Unknown

## 6. 已知限制

1. `is_immediate_return_path()` 只检查 block 自身是否有 Return 边。对于 `jmp common_return` 模式（branch target 是 UnconditionalJump 到 return block），当前不会检测为 immediate return。这是保守选择，未来可扩展。
2. `find_bounded_common_merge()` 深度限制为 8。超过 8 步的 merge 不会被检测。这是为了防止 loop/复杂 CFG 的假阳性。
3. Unknown 分类较粗，未来可细分（double_return / loop / switch / irreducible 等）。
