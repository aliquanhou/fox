## 2. Architecture

### 2.1 LiftedCall 结构

```rust
pub struct LiftedCall {
    pub target: CallTarget,
    pub arguments: Vec<Expression>,
    pub call_address: u64,
}
```

### 2.2 Statement 扩展

```rust
Statement::If {
    condition: ConditionRecovery,
    then_body: Vec<Statement>,
    else_body: Vec<Statement>,
    merge_block: Option<usize>,
    lifted_call: Option<LiftedCall>,  // NEW
    evidence: StatementEvidence,
}

Statement::GuardClause {
    condition: ConditionRecovery,
    body: Vec<Statement>,
    return_value: Option<Expression>,
    lifted_call: Option<LiftedCall>,  // NEW
    evidence: StatementEvidence,
}
```

### 2.3 Lifting 逻辑

`try_lift_call_into_condition()` 在 Phase 2 构建 If/GuardClause 时执行：

1. 检查 condition 是否是 `ConditionRecovery::Resolved`
2. 检查左操作数是否是 `eax`（返回值寄存器）
3. 在 branch_block 的 statements 中查找 CallStmt，其 `behavior.consumer_instruction == condition.flags_producer_address`
4. 如果找到，从 statements 中移除该 CallStmt，返回 `LiftedCall`

**Fail-closed**: 任何条件不满足 → 返回 None，保持原始 `call(); if(eax)` 形式。

## 3. Detection

### 3.1 支持的 Pattern

**Pattern 1 (test eax,eax)**:
```
call foo
test eax,eax
je label
```
→ `if (foo() == 0) { ... }`

**Pattern 2 (cmp eax,X)**:
```
call foo
cmp eax, 0x10
jne label
```
→ `if (foo() != 0x10) { ... }`

### 3.2 不支持的情况（Fail-closed）

- 左操作数不是 eax → 不 lift
- condition 不是 Resolved → 不 lift
- CallStmt 不在 branch_block 中 → 不 lift
- consumer_instruction 不匹配 → 不 lift
- 控制结构是 Unknown → 不 lift

## 4. Evidence

每个 LiftedCall 保留：
- `call_address`: 原始 CALL 指令地址
- `target`: CallTarget（Address/Symbol/Unknown）
- `arguments`: 已恢复的参数表达式

Condition 的 Evidence 仍然保留在 If/GuardClause 的 `evidence` 字段中。

完整 Evidence 链：
```
CALL @ 0x41F005
    ↓ Return Value (eax)
    ↓ TEST @ 0x41F007 (flags_producer)
    ↓ JZ @ 0x41F009 (branch)
    ↓ ConditionRecovery
    ↓ If/GuardClause + LiftedCall
```

### 5.2 0x41F000 实际输出

**P0-7.2.1**:
```c
void func_41F000() {
    esp_1 = (esp_0 - 40);
    call_unknown(4559240); /* return used in condition */
    if ((eax.v0 & eax.v0) == 0) {
        call_unknown(eax_0, 4559220); /* return used in condition */
        return <?void return>;
    }
    ...

```

**P0-7.3**:
```c
void func_41F000() {
    esp_1 = (esp_0 - 40);
    if (call_unknown(4559240) == 0) {
        call_unknown(eax_0, 4559220); /* return used in condition */
        return <?void return>;
    }
    ...
}
```

第一个 call 已成功合并进 if 条件。

### 5.3 Lift Ratio

309 个 ReturnUsedInCondition sites 中：
- 35 个成功 lift（11.3%）
- 274 个未 lift（88.7%）

未 lift 的主要原因：
1. CallStmt 在 branch_block 之前的 block 中（跨 block）
2. 对应的控制结构是 Unknown（不是 If/GuardClause）
3. condition 的 flags_producer_address 与 CallStmt.consumer_instruction 不匹配

这是预期的保守行为。当前实现只处理最简单的同 block pattern，跨 block lifting 留待后续阶段。

## 8. 已知 GAP

### GAP-P0-7.3-CROSS-BLOCK-LIFTING
当前只支持 CallStmt 与 condition 在同一 basic block 的 lifting。如果 CallStmt 在 branch_block 之前的 block 中（通过 SSA 跨块传播），则不 lift。
- 影响: 约 200+ 个 sites 未 lift
- 优先级: P1（不阻塞，当前 35 个已证明机制有效）

### GAP-P0-7.3-UNKNOWN-STRUCTURE
如果控制结构被分类为 Unknown（如 double-return、复杂 CFG），则不 lift。
- 影响: 部分 sites 未 lift
- 优先级: P2（依赖控制流恢复改进）

### GAP-P0-7.3-CMP-PATTERN
Pattern 2（cmp eax,X）理论上支持，但 NtcMach 中只有 3 个 cmp 模式，实际 lift 数量极少。
- 影响: 极小
- 优先级: P3
