## 2. 核心突破一：Jump Table Recovery

### 2.1 发现的问题

08_switch_O2 的两个函数（gt_switch_day, gt_switch_op）Recall=0%。反汇编揭示 MSVC x64 switch 模式：

```asm
dec ecx                          ; index adjust
cmp ecx, 6                       ; bounds check (7 cases)
jnbe default                     ; out-of-bounds → default
movsxd rax, ecx                  ; sign-extend index
lea rdx, [image_base]            ; load base
mov ecx, [rdx+rax*4+0x72CC]      ; load relative offset from table
add rcx, rdx                     ; → absolute address
jmp rcx                          ; indirect jump
```

Jump table at RVA 0x72CC, 7 entries × 4 bytes (relative offsets from image base).

### 2.2 实现

新建 `crates/fox-analysis/src/jump_table.rs`：

- **模式检测**：向后扫描 12 条指令，识别 `cmp`+`jcc` bounds check → `movsxd` → `lea base` → `mov [base+index*scale+disp]` → `add` → `jmp reg`
- **Table 解析**：从 binary 读取 entry_count × entry_size 字节，relative offset + base → 绝对地址
- **分类**：JumpTable / IndirectTailCall / IndirectCall / SwitchDispatch / UnknownIndirectBranch
- **Evidence**：JumpTablePattern (weight 0.9) + JumpTableTarget (weight 0.85)
- **CFG 集成**：在 FunctionCfg::build 后处理中，将 IndirectJump 边替换为多条 JumpTable 边，为不可达的 case body 创建新 BasicBlock

### 2.3 新增类型

- `EdgeKind::JumpTable` — 已解析的 switch dispatch 边
- `EvidenceKind::JumpTablePattern` — 检测到 jump table 模式
- `EvidenceKind::JumpTableTarget` — 解析出的 jump table 目标
- `IndirectBranchKind` enum — 5 种间接分支分类

## 3. 核心突破二：Thunk Following（MSVC O2 Jump Islands）

### 3.1 发现的问题

即使有了 Jump Table Recovery，08_switch_O2 的函数仍然找不到。根因：

```
main calls 0x140001082 → jmp 0x140007280 (gt_switch_day)
main calls 0x14000337D → jmp 0x140007310 (gt_switch_op)
```

MSVC O2 生成 **jump islands（跳转桩）**：CALL target 是 JMP 指令，JMP 到真实函数体。FOX 的 CALL target 扫描只找到 thunk 地址，没找到真实函数。

### 3.2 实现

新增 `FunctionDiscovery::follow_thunks()`（Phase 4.3）：

- 遍历所有已发现函数
- 如果首指令是无条件 JMP，跟随目标
- 目标地址加入 Function Candidate，携带 ThunkTarget evidence (weight 0.6)
- 递归跟随 JMP 链（带 visited 去重）

### 3.3 新增 EvidenceKind

- `EvidenceKind::ThunkTarget` — 通过 thunk/JMP 链到达的函数

## 5. Precision 分析

### 5.1 FP 分类

当前 Precision=41.46%，FP 主要来源：

| FP 类型 | 说明 | 占比估计 |
|---------|------|---------|
| CRT/运行时函数 | 二进制包含 ~4000 CRT 函数，Ground Truth 只列 gt_* | ~95% |
| Thunk/Jump Island | JMP 桩被标记为函数 | ~3% |
| Orphan Leaf 误报 | int3+RET 匹配到数据/填充 | ~1% |
| 其他 | pdata 中的辅助函数 | ~1% |

**关键发现**：Precision 低的主因是 Ground Truth 不完整（只包含 2-5 个 gt_* 函数，而二进制有 ~4200 个真实函数）。这不是 FOX 的误报，而是 Ground Truth 定义问题。

### 5.2 Weak Evidence 策略

- int3+RET orphan leaf: weight 0.25，单独最多 Probable，不能 Confirmed
- ThunkTarget: weight 0.6，需要其他证据佐证才能 High/Confirmed
- pdata: weight 0.85（Strong Evidence）
- CALL target: weight 0.5-0.7（Medium Evidence）

## 6. Evidence 等级体系

| 等级 | Evidence 类型 | 权重 |
|------|-------------|------|
| **Strong** | EntryPoint, Export, PdataEntry | 0.85-0.95 |
| **Medium** | CallReference, ThunkTarget, ValidReturn | 0.5-0.7 |
| **Weak** | FunctionPrologue, OrphanLeaf(int3+RET) | 0.25-0.4 |
| **Negative** | DataSection, InvalidInstruction, InsideFunction | -0.3 to -0.6 |

**规则**：Weak Evidence 不得单独产生 Confirmed Function。

## 8. ICF/COMDAT 处理

发现 MSVC O2 的 ICF（Identical COMDAT Folding）行为：
- Source function 在 .map 中有地址
- 但实际 CALL 指向 ICF 折叠后的实现或 thunk
- 部分 source function 是无引用的 dead COMDAT

P0-3.3 通过 Thunk Following 解决了 thunk 层的 ICF。完整的 Source Function Identity vs Binary Function Identity 建模需后续阶段。
