## 3. 四个核心审计问题

### 3.1 Memory SSA Use→Def 跨 CFG 路径

**结论：✅ 已正确工作。**

验证：
- 线性：Store → Load，use-def 精确到 (block, inst, version)
- if/else：两分支 Store → 合流点 Phi，Load 追溯到 Phi
- loop：循环头 Phi（pre-header + back-edge incoming），body Load 追溯到 Phi 或 Store
- 多 def：1 Store + 2 Load，def-use 列出 2 个 use

**限制：**
- use-def 基于 SSA version 追溯，不是独立的 iterative reaching definitions
- 如果 MemoryPhi 的 incoming 中有 version=0（undefined），use-def 追溯到 (usize::MAX, usize::MAX)
- 不处理跨函数的内存数据流（caller/callee memory interaction）

### 3.2 Heap/Unknown 保守合并的副作用

**结论：🟡 功能正确，但精度损失明显。**

当前策略：所有 Heap 访问合并为一个 MemoryVariable，所有 Unknown 合并为一个 MemoryVariable。

**副作用：**

| 副作用 | 说明 |
|--------|------|
| 过度 Phi | 两个无关 heap Store 在不同分支 → 合流点产生不必要的 MemoryPhi |
| 过度 kill | `mov [rax], 1` 被视为 kill 所有 heap 变量 → `mov [rbx], 2` 后的 Load 可能追溯到错误的 def |
| imprecise use-def | Load [rax+8] 可能追溯到任何 heap Store，而不是最近的相关 Store |
| 版本爆炸 | 大量 heap Store 导致单变量版本号快速增长 |

**这是保守但安全的选择。** 没有 Alias Analysis 时，宁可过度合并也不能错误地认为两个 heap 访问独立。精确化是 P0-4.4 的核心任务之一。

### 3.3 Memory SSA 与 Register DataFlow 的统一数据依赖

**结论：🔴 核心 GAP — 当前完全断开。**

这是 P0-4.4 最重要的发现。

**当前状态：**

```
mov [rsp+8], rax     → MemoryDef (stack[RSP+8])
                         Register def: RAX (but Register DataFlow doesn't know it's stored to memory)
                              │
                              ▼ 断开
mov rcx, [rsp+8]     → MemoryUse (stack[RSP+8]) → traces to MemoryDef above
                         Register def: RCX (but Register DataFlow doesn't know RCX came from memory)
```

**问题：**
1. Register DataFlow 看到 `RCX = ?` 但不知道值来自 `[rsp+8]`
2. Memory SSA 看到 Store 的 source 是 RAX，但不知道 RAX 的值来自哪里
3. 无法回答："这个 Load 得到的值，最终来自哪个原始常量/参数？"
4. 无法建立跨域 def-use：MemoryDef → Register destination → Register use → ...

**需要的统一数据依赖：**

```
Store [rsp+8], RAX
  ├── MemoryDef: stack[RSP+8] v1
  └── Register use: RAX.v3 → traces to Register Def (e.g., MOV RAX, 42)

Load RCX, [rsp+8]
  ├── MemoryUse: stack[RSP+8] v1 → traces to MemoryDef above
  └── Register def: RCX.v7 ← value came from memory
```

最终形成：
```
Constant 42 → RAX.v3 → MemoryDef(stack v1) → MemoryUse(stack v1) → RCX.v7 → use(RCX)
```

### 3.4 间接调用 / Function Pointer Propagation

**结论：🟡 分类完成，数据流驱动的解析完全缺失。**

**当前能力：**
- `call [rip+disp]` → IAT → External Symbol ✅
- `call rax` → Register IndirectCallKind（分类，未解析）
- `call [rax+8]` → VtableCandidate（分类，未解析）
- LEA reg, [rip+disp] → Address-Taken Function Discovery ✅

**缺失：**
```
lea rax, [foo]       → Address-Taken: foo
mov [rsp+10h], rax   → MemoryDef: stack[RSP+16] = &foo
...
mov rcx, [rsp+10h]   → MemoryUse: stack[RSP+16] → &foo
call rcx             → IndirectCall Register
                      ❌ 无法追溯 rcx = &foo
                      ❌ 无法解析为 call foo
```

**需要 Memory DataFlow 才能回答：**
- `call rax` 中 rax 的值来自哪个 Store？
- 那个 Store 的值是哪个函数的地址？
- 这个间接调用可能调用哪些函数？

## 5. P0-4.4 最小架构提案

### 5.1 核心概念：Cross-Domain Value Flow

P0-4.4 的目标不是再造一个分析，而是建立 **Register ↔ Memory 的统一数据依赖图**。

```
ValueNode
 ├── RegisterDef { block, inst, reg, version }
 ├── MemoryDef { block, inst, variable, version }
 ├── RegisterUse { block, inst, op_idx, reg, version }
 └── MemoryUse { block, inst, op_idx, variable, version }

ValueEdge
 ├── RegisterDef → RegisterUse (existing Register SSA use-def)
 ├── MemoryDef → MemoryUse (existing Memory SSA use-def)
 ├── MemoryDef → RegisterDef (NEW: Load produces register value from memory)
 └── RegisterUse → MemoryDef (NEW: Store's source register value goes to memory)
```

### 5.2 第一阶段：Memory→Register 桥接

最小实现：当 MemoryUse 有 destination_register 时，在 Register DataFlow 中标记该 register definition 为 "from memory"，并链接到 MemoryDef。

```
Load RCX, [rsp+8]
  → MemoryUse: stack[RSP+8] v1 → MemoryDef at (b0, i0)
  → RegisterDef: RCX.v7 with source = Memory(stack[RSP+8] v1)
```

### 5.3 第二阶段：Register→Memory 桥接

当 MemoryDef 有 source_register 时，追溯该 register 的 SSA definition。

```
Store [rsp+8], RAX
  → MemoryDef: stack[RSP+8] v2
  → source = RAX.v3 → RegisterDef at (b0, i0) → e.g., MOV RAX, 42
```

### 5.4 第三阶段：Alias-aware Memory SSA 增强

- 引入基础 Alias Classification：MustAlias, MayAlias, NoAlias
- Stack：MustAlias if same (base, disp)，NoAlias if different disp
- Global：MustAlias if same address
- Heap：MayAlias（保守）
- 用 Alias 信息减少过度 Phi 和过度 kill

### 5.5 第四阶段：Function Pointer Propagation

- 利用 Cross-domain value flow 追踪 `call rax` 中 rax 的来源
- 如果 rax 来自 LEA reg, [function_address]，则解析为 DirectInternal
- 如果 rax 来自 Load of a function pointer table，解析为候选集合

## 9. Audit 结论

**P0-4.4 Reality Audit：PASS — 可以进入 Architecture / Implementation。**

P0-4.3 Memory SSA 已经建立了内存侧的版本化和 use-def。Register SSA/DataFlow 已经建立了寄存器侧的版本化和数据流。

**核心 GAP 是 G1/G2/G3：Memory 和 Register 之间的值传递完全断开。**

P0-4.4 的最小可行目标是建立 Cross-domain Value Flow 桥接层，让 FOX 能够回答：
> "这个 Load 得到的值，来自哪个 Store？那个 Store 的值来自哪个 Register？那个 Register 又来自哪里？"

这是 Decompiler / Type Recovery / Semantic Analysis 的真正基础。
