## 1. Executive Summary

P0-5.6B implements the four-dimensional Function Reality Model approved by the architect in P0-5.6 Architecture Audit, incorporating all 11 semantic freeze conditions and the 4 required corrections (claim conflict adjudication, Body ≠ byte range, End Unknown → no range, no forced old API migration) plus Freeze 11 (Negative Evidence dimension-precise mapping).

The model upgrades FOX from a single `confidence_tier` scalar to independent Start / Body / End / Identity reality dimensions, each with its own status, positive claims, negative claims, and evidence traceability.

**Key principle**: Reality is multi-dimensional, not a score. A function can be `Start=Confirmed, Body=High, End=Unknown, Identity=Unknown` and still be a valid function entity.

## 2. Data Model

### 2.1 RealityStatus

```rust
pub enum RealityStatus {
    Confirmed,   // Strong positive, no significant negative
    High,        // Multiple supporting, or Strong + minor negative
    Probable,    // Single supporting, or supporting + negative
    #[default]
    Unknown,     // Insufficient or conflicting evidence
    Rejected,    // Negative evidence dominates
}
```

### 2.2 BoundaryReality (used for Start and End)

```rust
pub struct BoundaryReality {
    pub address: Option<u64>,
    pub status: RealityStatus,
    pub confidence: Confidence,
    pub positive_claims: Vec<EvidenceClaim>,
    pub negative_claims: Vec<EvidenceClaim>,
    pub contradictions: Vec<ClaimContradiction>,
}
```

### 2.3 BodyReality

```rust
pub struct BodyReality {
    pub instruction_count: usize,
    pub basic_block_count: usize,
    pub status: RealityStatus,
    pub confidence: Confidence,
    pub positive_claims: Vec<EvidenceClaim>,
    pub negative_claims: Vec<EvidenceClaim>,
    pub contradictions: Vec<ClaimContradiction>,
}
```

**Body is NOT a continuous byte range.** It is defined as instruction/basic-block ownership plus control-flow region. `FunctionRange` is a separate boundary expression.

### 2.4 IdentityReality

```rust
pub struct IdentityReality {
    pub kind: String,           // Canonical / Thunk / ImportThunk / Folded / Alias / Unknown
    pub status: RealityStatus,
    pub positive_claims: Vec<EvidenceClaim>,
    pub negative_claims: Vec<EvidenceClaim>,
}
```

**Identity does NOT determine Function Existence.** A function with `Identity=Unknown` is still a real function if Start/Body/End are established.

### 2.5 FunctionRange

```rust
pub struct FunctionRange {
    pub start: u64,
    pub end_exclusive: u64,   // Semantics: [start, end_exclusive)
}
```

**Range is `Option<FunctionRange>`**. It is only constructed when both Start and End have status ≥ Probable and an end address is available. When End is Unknown, `range = None`. **Never fabricate an estimated end and label it Confirmed.**

### 2.6 FunctionReality

```rust
pub struct FunctionReality {
    pub start: BoundaryReality,
    pub body: BodyReality,
    pub end: BoundaryReality,
    pub identity: IdentityReality,
    pub range: Option<FunctionRange>,
}
```

### 2.7 Function struct (backward compatible)

```rust
pub struct Function {
    // ... existing fields unchanged ...
    pub reality: Option<FunctionReality>,  // NEW: None when not built
}
```

## 3. Claim Adjudication

### 3.1 Principle

`ClaimStrength ≠ RealityStatus`. Reality is the result of:

```
Evidence → Claims → Claim Aggregation → Reality Adjudication → RealityStatus
```

Not:

```
ClaimStrength → RealityStatus  (WRONG)
```

### 3.2 Strength Rank

```
Unknown=0, Contextual=1, Supporting=2, Strong=3, Negative=4
```

### 3.3 Adjudication Rules

| Positive | Negative | Result |
|----------|----------|--------|
| None | None | Unknown |
| None | Any | Rejected |
| Any | None | strongest positive → status |
| Strong | Negative | Unknown (conflict, not rejection) |
| Supporting+ | Negative (≥ positive) | Rejected |
| Positive stronger | Negative weaker | downgrade one tier |

### 3.4 Contradictions

When positive and negative claims coexist, a `ClaimContradiction` is recorded listing both sides, preserving full traceability.

## 4. Evidence → Claim → Reality Dimension Mapping

### 4.1 Positive Evidence Mapping

| EvidenceKind | ClaimType | Strength | Reality Dimension |
|---|---|---|---|
| EntryPoint | FunctionStart | Strong | Start |
| Export | FunctionStart | Strong | Start |
| PdataFunction | FunctionStart + FunctionEnd | Strong | Start + End |
| CallTarget | FunctionStart | Supporting | Start |
| CallReference | FunctionStart | Supporting | Start |
| ValidFunctionBody | FunctionBody | Supporting | Body |
| ValidReturn | FunctionEnd | Contextual | End |
| TailCall | FunctionEnd | Contextual | End |
| ThunkTarget | FunctionIdentity | Supporting | Identity |
| ImportThunk | ExternalIdentity | Strong | Identity |
| AddressTaken | (no default claim) | — | — |
| ReachableFromEntry | Reachability | Contextual | (not Start) |

### 4.2 Negative Evidence Mapping (Freeze 11)

| EvidenceKind | ClaimType | Strength | Reality Dimension |
|---|---|---|---|
| InvalidFunctionBody | FunctionBody | Negative | **Body** (NOT Boundary) |
| NonExecutableSection | FunctionStart | Negative | Start |
| InvalidInstructionBoundary | FunctionStart | Negative | Start |
| DataAddress | FunctionStart | Negative | Start |
| Unreachable | Reachability | Negative | Reachability |

**Critical**: `InvalidFunctionBody` negates Body, not Start/End. This prevents semantic pollution where an invalid body would incorrectly downgrade boundary reality.

## 5. Pdata EndAddress Precision (P0-5.5 P2 Resolution)

### Problem (P0-5.5 P2)

`PdataEntry` had `BeginAddress` and `EndAddress`, but `Evidence` only had a single `address` field. The FunctionEnd claim used `BeginAddress` as its subject, producing zero-length ranges.

### Solution

Added `Evidence.end_address: Option<u64>`:

```rust
pub struct Evidence {
    pub kind: EvidenceKind,
    pub address: Option<u64>,
    pub end_address: Option<u64>,   // NEW: Pdata observed EndAddress
    pub detail: Option<String>,
    pub weight: f64,
    pub claim: Option<EvidenceClaim>,
}
```

`discover_from_pdata()` now sets `with_end_address(rf.end_va)`. `default_claims()` for PdataEntry produces:
- `FunctionStart → Address(BeginAddress)` — Strong
- `FunctionEnd → Address(EndAddress)` — Strong (precise)

This is defined as **Pdata's raw observed reality**, not a field fabricated for FunctionReality.

## 6. End Address Resolution (Post-Audit Fix)

### Audit Finding

The architect flagged that `validation.estimated_end` must NOT enter Reality, and that TailCall/ValidReturn evidence uses `address = function_start`, causing their FunctionEnd claim subject to be the function entry address (not the actual end instruction). This produced zero-length ranges `[start, start)`.

### Fix (commit `cc3204f`)

In `build_function_reality()`:

```
end_addr = precise claim subject (≠ function start)  [e.g. Pdata EndAddress]
        → Function.end_address (.pdata, authoritative)
```

**Removed**: `validation.estimated_end` fallback — estimates do not enter Reality.
**Added**: claim subject filter `a != addr` — skips imprecise subjects located at function entry.

### Result

| End Status | Count | end_addr | Range |
|---|---|---|---|
| Probable (TailCall) | 28 | None | None |
| Unknown | 331 | None | None |

The 28 Probable functions have evidence that they terminate properly (TailCall claim, Contextual strength → Probable status), but no precise end address. This is honest: **we know the function ends, but not exactly where.**

For x64 binaries with .pdata, End=Confirmed and end_addr = precise EndAddress, producing valid `[start, end_exclusive)` ranges.

**Observed End ≠ Estimated End ≠ Confirmed End.** Estimated end remains in `FunctionValidation` only, never promoted to Reality.

## 9. NtcMach.exe Real-World Verification

**Sample**: NtcMach.exe (PE32 x86 Native, 359 functions)

### Reality Distribution

| Dimension | Confirmed | High | Probable | Unknown | Rejected |
|---|---|---|---|---|---|
| Start | 1 | 323 | 34 | 1 | 0 |
| Body | 0 | 356 | 0 | 0 | 3 |
| End | 0 | 0 | 28 | 331 | 0 |
| Identity | 0 | 0 | 0 | 359 | 0 |

### Key Observations

1. **Start=Confirmed=1**: Only the entry point has strong evidence (EntryPoint). This is correct for x86 without .pdata.
2. **Body=Rejected=3**: Three functions correctly identified as having invalid bodies (likely data misdiscovered as code).
3. **End=Unknown=331 (92.2%)**: x86 lacks .pdata, and most functions don't have a clear RET in linear sweep. This is honest — the old single confidence_tier hid this uncertainty.
4. **End=Probable=28**: Functions with ValidReturn or TailCall evidence.
5. **Identity=Unknown=359**: No symbol names in this binary; Identity is separate from Function Existence.
6. **Range=None for ALL 359 functions**: Correctly no fabricated ranges. x86 has no .pdata, and TailCall evidence subjects are at function entry (not precise end addresses). No zero-length ranges.

### Comparison with Old Model

Old model showed: Confirmed=1, High=156, Probable=199, Unknown=3 (single scalar).

New model reveals: the "High" and "Probable" functions actually have very different boundary certainties — most have solid Start+Body but unknown End. This is exactly the architectural insight P0-5.4/P0-5.6 aimed for.

## 12. Known Limitations / GAPs

1. **x86 End uncertainty**: 92% of x86 functions have End=Unknown. This is a binary reality, not a bug. Future work may improve end detection via CFG-based boundary analysis.
2. **IdentityReality is minimal**: Currently only carries the IdentityKind string. Full identity evidence (name resolution, alias chains) is future work.
3. **estimated_end is linear-sweep**: May be imprecise for functions with cold blocks, outlined code, or shared tails. Marked Contextual/Probable, never Confirmed.
4. **No Start/Body/End confidence in CLI JSON**: The reality struct is serializable but CLI JSON output for functions doesn't yet include reality detail (only `--reality` text view).
5. **MixedMode/Unknown ExecutionModel**: Still reserved enums from P0-4.5, not implemented.
