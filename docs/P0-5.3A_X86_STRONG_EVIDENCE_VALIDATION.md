## 3. ReachableFromEntry Validation

### 3.1 Definition Clarification

Two possible definitions were tested:

- **Definition A: Call-graph reachability** — address is reachable from entry point via chains of direct CALL instructions only.
- **Definition B: CFG reachability** — address is reachable from entry point via any CFG edge (CALL + JMP + JCC).

### 3.2 Methodology

Independent Python script scanned .text section for:
- Direct CALL: `E8 rel32` (3606 found)
- Direct JMP: `E9 rel32` (1260 found)

Built call graph from entry point (0x455E4C) using BFS through CALL targets.

### 3.3 Positive Validation (Definition A — Call-graph reachability)

- **164 functions** reachable from entry via direct CALL chains
- All 164 are direct CALL targets
- Manual verification of 5 sampled addresses (0x401390, 0x408F50, 0x4090E0, 0x416260, 0x427880):
  - 0x401390: `sub esp, 8; push ebx; ...` — valid O2 function prologue ✅
  - 0x408F50: `mov eax, [esp+8]; mov ecx, [esp+C]; ...` — valid function (reads args) ✅
  - 0x427880: `mov eax, [global]; push esi; ...` — valid function ✅
- **0 false positives** among reachable set

### 3.4 Negative Validation

#### Negative 1: Internal Basic Block
- **1179 internal BBs** identified: JMP targets within the same function, NOT CALL targets
- Example: `JMP 0x40160A -> 0x4017F5` (inside function 0x401390)
  - Bytes at 0x4017F5: `8B 44 24 14 83 F8 08` = `mov eax, [esp+0x14]; cmp eax, 0x08`
  - This is clearly an internal comparison block, NOT a function start
- If ReachableFromEntry used **Definition B (CFG-reachability)**, all 1179 internal BBs would be marked reachable → **massive FP**

#### Negative 2: Switch Target
- Switch targets are indirect JMP targets (`jmp [table]`), not direct CALL targets
- They are internal BBs, not function starts
- Covered by the 1179 internal BB count (indirect JMP targets not separately counted but included in CFG)

#### Negative 3: Loop Header
- Loop headers are JMP/JCC targets within the same function
- Also covered by 1179 internal BB count
- Example: any `jmp` backward to a loop header would be CFG-reachable but not a function start

#### Negative 4: SEH Handler
- Entry point SEH prologue pushes handler address 0x455FCC
- This handler is reachable via SEH mechanism but is NOT a normal function entry
- 0x455FCC is not a CALL target → not in call-graph reachable set ✅
- If CFG-reachability included exception edges, handler could be FP

#### Negative 5: Tail-Call
- 81 tail-call JMPs identified (JMP to another function)
- Tail-call targets ARE function starts and ARE CALL-reachable (the caller is reachable, and the tail-call target is typically also called directly elsewhere)
- No FP observed for tail-call targets

### 3.5 Metrics (Definition A — Call-graph reachability)

| Metric | Value |
|--------|-------|
| Reachable addresses | 164 |
| TP (real function starts) | 164 |
| FP (not function starts) | 0 |
| FN (functions not reachable) | 195 |
| Precision (evidence-level) | 164/164 = **100%** |
| Recall (of 359 FOX functions) | 164/359 = **45.7%** |
| F1 | **62.7%** |

### 3.6 Boundary-level Metrics

ReachableFromEntry does NOT determine function boundaries (start/end). It only confirms existence.
- StartBoundaryError: N/A (not a boundary evidence)
- EndBoundaryError: N/A

### 3.7 Critical Finding

ReachableFromEntry (Definition A) is **redundant with CallReference**:
- Every reachable address is a CALL target
- CallReference evidence already exists (weight 0.7 for >=3 calls, 0.5 for <3)
- ReachableFromEntry adds: "this CALL target is in the entry point's call graph"
- This is a **supporting boost**, not an independent strong evidence

Functions not reachable from entry include:
- Callback functions (registered via function pointer)
- Functions called only via indirect call
- Functions in dead code / unused modules
- Library functions not invoked from this binary's entry path

### 3.8 Classification: **SUPPORTING**

ReachableFromEntry (call-graph reachability) can boost confidence of CALL-target-discovered functions, but:
- Cannot independently prove function start (depends on CALL target)
- 45.7% recall means most functions are not covered
- If defined as CFG-reachability, causes massive FP (1179 internal BBs)

## 4. SEH Registration Validation

### 4.1 What is SEH Registration?

x86 Windows uses `FS:[0]` linked-list exception handling. A function with SEH setup:
```asm
push ebp
mov ebp, esp
push -1
push offset seh_table
push offset seh_handler
mov eax, fs:[0]    ; save old handler
push eax
mov fs:[0], esp    ; install new handler
```

### 4.2 Detection in NtcMach.exe

Byte pattern scan of .text section:
- `mov eax, fs:[0]` (`64 A1 00 00 00 00`): **1 occurrence** at 0x455E5B
- `mov fs:[0], esp` (`64 89 25 00 00 00 00`): **1 occurrence** at 0x455E62
- `push fs:[0]`: 0 occurrences
- Other `mov reg, fs:[0]`: 0 occurrences

Both occurrences are in the **entry point function** (0x455E4C), 7 bytes apart.

### 4.3 Manual Verification

Disassembly at 0x455E4C:
```
0x455E4C: push ebp
0x455E4D: mov ebp, esp
0x455E4F: push -1
0x455E51: push 0x456370     ; SEH scope table
0x455E56: push 0x455FCC     ; SEH handler
0x455E5B: mov eax, fs:[0]   ; save old handler
0x455E61: push eax
0x455E62: mov fs:[0], esp   ; install handler
```

This is the standard MSVC `__SEH_prolog` pattern. It occurs at the **function entry** (0x455E4C), confirming SEH registration is a function-start signal.

### 4.4 Import Confirmation

`_except_handler3` is imported from MSVCRT.dll, confirming SEH is used in this binary.

### 4.5 Coverage Analysis

| Metric | Value |
|--------|-------|
| Functions with SEH setup | 1 (entry point) |
| Total FOX functions | 359 |
| Coverage | **0.3%** |
| TP | 1 (verified at function start) |
| FP | 0 |
| FN | 358 (no SEH setup) |
| Precision | 1/1 = 100% |
| Recall | 1/359 = 0.3% |

### 4.6 SEH Handler vs Function Entry

The SEH handler address (0x455FCC) is pushed in the prologue. This handler:
- Is NOT a normal function entry (no prologue, called by OS exception dispatcher)
- Could be confused as a function start if SEH detection is naive
- Must be classified separately (ExceptionHandler, not FunctionStart)

### 4.7 Why Coverage Is So Low

NtcMach.exe appears to be compiled with:
- Minimal C++ exception handling (only CRT startup uses SEH)
- Possibly /EHs-c- (no C++ exceptions) or structured exceptions only in CRT
- Most business logic functions do not use SEH

### 4.8 Classification: **SUPPORTING**

SEH Registration has **high reliability** when present (SEH setup only occurs at function entry), but:
- Coverage is near-zero (0.3%) in this commercial binary
- In binaries with heavy C++ exceptions / SEH, coverage would be higher
- Must distinguish SEH handler address from function entry
- Cannot serve as general Strong Evidence due to low coverage

## 5. /GS Security Cookie Validation

### 5.1 What is /GS?

MSVC /GS (Buffer Security Check) inserts a security cookie at function entry:
```asm
mov eax, dword ptr [___security_cookie]
xor eax, esp
push eax
...
call __security_check_cookie
```

### 5.2 Detection in NtcMach.exe

Import table scan:
- `___security_cookie`: **NOT imported**
- `__security_check_cookie`: **NOT imported**
- No references to security cookie global in .data section

### 5.3 Conclusion

NtcMach.exe was compiled **without /GS** (or with /GS-). This means:
- 0 functions have /GS cookie setup
- /GS Security Cookie evidence has **0% coverage** in this binary
- **Cannot be validated** with this sample

### 5.4 Classification: **UNVERIFIED**

Need a /GS-enabled x86 binary to validate:
- Whether /GS cookie setup always occurs at function entry
- Whether leaf functions / small functions skip /GS
- Whether /GS can occur inside function body (e.g., in outlined code)
- Coverage rate in typical /GS-enabled binaries

## 9. False Positive Analysis

### 9.1 ReachableFromEntry
- **0 FP observed** with call-graph definition
- **1179 potential FP** if CFG-reachability definition is used (internal BBs)
- Root cause of potential FP: CFG includes JMP/JCC edges to internal BBs
- Mitigation: MUST define as call-graph reachability (direct CALL only), NOT CFG reachability

### 9.2 SEH Registration
- **0 FP observed**
- Potential FP: SEH handler address (0x455FCC) could be misidentified
- Mitigation: SEH detection must look for the full prologue sequence (push fs:[0] + mov fs:[0], esp), not just fs:[0] reference

### 9.3 /GS Security Cookie
- **N/A** (not present in sample)

## 11. Limitations

1. **Single binary sample**: NtcMach.exe is one commercial x86 binary. Results may differ for other binaries (e.g., C++ heavy applications with SEH, /GS-enabled binaries).

2. **No x86 .map Ground Truth**: Existing GT corpus is x64 only. x86 validation relies on manual disassembly + PE metadata, not linker .map files.

3. **/GS not testable**: NtcMach.exe lacks /GS, so this candidate is UNVERIFIED. Need a /GS-enabled x86 binary for proper validation.

4. **ReachableFromEntry depends on FOX's CFG**: The call-graph reachability was computed with an independent Python script, but function boundary inference used CALL targets as proxy. A full implementation would use FOX's CFG/CallGraph.

5. **Indirect calls not followed**: Reachability only follows direct CALL (E8). Indirect calls (call eax, call [mem]) are not resolved, so functions called only indirectly are not reachable.

## 12. Recommendation

### 12.1 What to Implement (if P0-5.3B is approved)

**Priority 1: ReachableFromEntry as SUPPORTING evidence**
- Weight: 0.65 (not 0.80 as originally proposed)
- Definition: call-graph reachability (direct CALL chains from entry point ONLY)
- Must NOT use CFG reachability (would cause 1179 FPs)
- Boosts CALL-target functions that are in the entry call graph
- Does not independently prove function start

**Priority 2: SEH Registration as SUPPORTING evidence**
- Weight: 0.75 (high reliability when present)
- Must detect full SEH prologue sequence, not just fs:[0]
- Must exclude SEH handler addresses
- Low coverage (0.3% in this sample) but high precision
- More valuable in C++ exception-heavy binaries

**Priority 3: /GS Security Cookie — DEFER**
- UNVERIFIED with current sample
- Need /GS-enabled x86 binary before implementation
- If implemented later, weight: 0.75-0.80 (similar to SEH)

### 12.2 What NOT to Do

- ❌ Do NOT implement ReachableFromEntry as STRONG (0.85+) — it's redundant with CallReference
- ❌ Do NOT use CFG-reachability — 1179 internal BBs would be FPs
- ❌ Do NOT implement /GS without a /GS-enabled validation sample
- ❌ Do NOT lower Confirmed threshold to accommodate these candidates
- ❌ Do NOT inflate CallReference weight

### 12.3 Expected Impact

If ReachableFromEntry (0.65) + SEH (0.75) are implemented as SUPPORTING:
- Functions with CallReference(0.7) + ReachableFromEntry(0.65) + ValidFunctionBody(0.6):
  - max = 0.70, extra = 2, bonus = 0.1*2*0.3 = 0.06, conf = 0.76 → still High
- Functions with SEH(0.75) + CallReference(0.7) + ValidFunctionBody(0.6):
  - max = 0.75, extra = 2, bonus = 0.1*2*0.25 = 0.05, conf = 0.80 → still High
- Functions with SEH(0.75) + ReachableFromEntry(0.65) + CallReference(0.7) + ValidFunctionBody(0.6):
  - max = 0.75, extra = 3, bonus = 0.1*3*0.25 = 0.075, conf = 0.825 → still High (just below 0.85)

**Key finding**: Even with all three candidates implemented as SUPPORTING, most x86 functions will NOT reach Confirmed (0.85). The confidence formula's diminishing returns prevent medium evidence accumulation from reaching the threshold.

To actually increase Confirmed count on x86, one of these is needed:
1. A true STRONG evidence source (>= 0.85) for x86 (none identified in this audit)
2. A revised confidence model that allows convergent medium evidence to reach Confirmed (architectural change, not evidence addition)
3. Accept that x86 Confirmed count will remain low and focus on High/Probable quality
