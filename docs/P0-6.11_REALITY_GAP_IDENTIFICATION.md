## 核心问题

P0-6.10 后 NtcMach 反编译输出中：
- **CALL 参数：0 个成功恢复**（全部 `/* arguments unresolved */`）

## 缺口 1：CALL 参数恢复为 0 — 🔴 根因已定位

### 现象
整个 1.59MB 输出中，**没有任何一个调用有实际恢复的参数**。

### 根因：API 用错（不是 SSA/DataFlow 缺能力）

`structured_ir.rs` 的 `recover_call_arguments()` 对每个 PUSH 调用：
```rust
self.expr_engine.recover_definition(ssa, block_id, idx)
```

但 `expression.rs:631` 明确写着：
```rust
| "Leave" | "Push" | "SetFlag" | "ClearFlag" => Expression::Unknown {
    reason: format!("{} does not produce a recoverable value", op),
},
```

**`recover_definition()` 问的是"这条指令定义了什么值"。**
- PUSH 定义的是 ESP（隐式）和栈内存（隐式）
- `destination_operand_idx` = None（无显式寄存器写入）
- 所以正确返回 Unknown

**但参数恢复需要问的是"PUSH 的源操作数是什么"。**
- `push 42` → 源操作数是 Constant(42)
- `push eax` → 源操作数是 eax 的 SSA 值
- `push [esp+8]` → 源操作数是内存加载

**正确的 API 是 `recover_use(ssa, block_id, idx, 0)`**，恢复第 0 个操作数（PUSH 的源）。

### 证据链
```
recover_call_arguments()
    ↓ 对每个 PUSH 调用
recover_definition(push_idx)
    ↓
recover_instruction_expression()
    ↓ match op { "Push" => Unknown("Push does not produce a recoverable value") }
    ↓
Expression::Unknown
    ↓ .filter(|e| !matches!(e, Expression::Unknown))
    ↓
参数列表为空 → arguments_complete=false
    ↓
输出: call_xxx(/* arguments unresolved */)
```

### 修复方案（极小）
将 `recover_call_arguments()` 中的：
```rust
self.expr_engine.recover_definition(ssa, block_id, idx)
```
改为：
```rust
self.expr_engine.recover_use(ssa, block_id, idx, 0)
```

`recover_use` 是 ExpressionRecovery 的公开方法（expression.rs:148），用于恢复指定操作数的值。对 PUSH 来说，operand[0] 就是被压入的值。

### 预期效果
- `push 42` → `Constant(42)` → 输出 `call_xxx(42)`
- `push eax`（eax 之前有定义）→ 递归恢复 eax 的表达式 → `call_xxx(eax_1)` 或更复杂表达式
- `push [esp+8]` → `Load(...)` → `call_xxx(*(esp+8))`
- 大量 cdecl/stdcall 调用的参数将立即可见

### 不涉及
- ❌ 不修改 expression.rs（已封板）
- ❌ 不修改 SSA
- ❌ 不修改 CallGraph
- ✅ 只改 structured_ir.rs 中一行 API 调用

## 缺口 2：变量名是 SSA 占位符 — 🟡 可读性问题，非阻塞

### 现象
输出中变量全部是：
```c
eax_1 = (esp_0 - 40);
ecx_2 = <?memory operand: [esp+0x2c]>;
ebx_1 = (ebx_0 ^ (ebx_0 ^ <?cycle detected at ebx.1>));
```

### 根因
- Structured IR 的 `AssignTarget::Variable { origin: SSAPlaceholder }`
- Emitter 直接输出 `name_version`（如 `eax_1`）
- 没有 Variable Recovery 层将 SSA 变量映射为逻辑变量

### 为什么不是第一优先级
1. **不影响正确性**：`eax_1` 虽然难看，但语义是准确的
2. **工程量大**：需要建立变量生命周期分析、栈变量识别、寄存器重命名等
3. **可以渐进改进**：先做简单的（如 `esp_0` → `stack_pointer`，函数入口参数标记），不需要完整 Variable Recovery
4. **参数恢复修复后可读性提升更大**：`call_xxx(42, eax_1)` 比 `call_xxx(/* unresolved */)` 进步明显

### 后续方向（不立即做）
- 栈变量：`[esp+0x20]` → `local_20`
- 函数参数：`[esp+4]`（caller 栈帧）→ `arg_0`
- 寄存器变量：保留 `eax_1` 但去掉版本号或简化

## 缺口 3：1219 个 indirect call 未知 — 🟡 需 Value Flow 增强

### 现象
1219 个 `call_unknown`，全部是 indirect call（`call eax` / `call [memory]`）。

### 根因
CallGraph 对 indirect call 的解析能力有限：
- `call eax` → 无法静态确定 eax 指向哪个函数
- `call [esp+4]` → 无法确定内存内容
- vtable call → 需要对象类型分析

### 为什么不是第一优先级
1. indirect call 解析需要 Value Flow / 指针分析，工程量大
2. 1437 direct call 已经恢复，覆盖了大部分调用
3. 可以通过引入 Ghidra/rev.ng 交叉分析来补充

## 结论

**第一个最值得修的阻塞点是：PUSH 参数恢复用错了 API。**

不是 Argument Recovery 本身缺能力，也不是 SSA/DataFlow 没传出来——SSA 已经有 PUSH 的源操作数信息，ExpressionRecovery 已经有 `recover_use()` 能力，只是 `recover_call_arguments()` 调用了错误的方法。

修复成本：1 行代码。
预期收益：NtcMach 中大量 cdecl/stdcall 调用的参数将立即可见，反编译可读性显著提升。

变量名问题（eax_1, ecx_2）是可读性问题，不是正确性阻塞，留到后续阶段。

**没有 Evidence，不生成 Claim。**
**缺什么补什么，不重复建设。**
